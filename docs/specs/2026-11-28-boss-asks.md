## Why

An agent asks the boss in nine ways, and each keeps its own record. Nothing says, in one place, that someone waits on him: a question in another tab's pane, a wait card the tower recorded, and a teammate's wait each show only where their owner draws them. Slice 1 gives sb one record of a question, the Ask, kept by the sb server, and one answer path for the questions it owns. The others are mirrored as Asks without changing their owners, so the boss sees all of them in pi and in the GUI.

Nothing on the wire between devices changes: the store is this computer's, and a box on an older sb keeps working with this one.

## The Ask record

`<slot>/asks/<id>.json`, one file per Ask, written by the sb server of that Herdr slot only (`<slot>` is record.ts `Slot.dir`: the state folder for the default Herdr, `<state>/servers/<hash>/` for another; each Herdr server keeps its own store, so no two processes write one folder), each write a temp file renamed over the old one (`writeDurable`). The server loads them at its start, so an open Ask outlives a restart; `<slot>/asks/seq.json` holds the next display number.

```ts
interface AskRecord {
  v: 1;
  id: string;                 // 32 hex, random
  n: number;                  // shown as "Q<n>"
  kind: "boss" | "dialog" | "wait" | "link";
  blocking: boolean;          // the asker's tool call waits on it (kind boss); a mirror never blocks here
  mirror?: string;            // the owner's key of a mirrored question: "wait:<workspace>:<W id>" or "dialog:<unit key>:<tool call id>"
  asker: { session: string; name: string; role?: string; workspace?: string; workspaceLabel?: string; tab?: string; tabLabel?: string; pane?: string; device?: string };
  subject: string;            // one line of at most 200 characters, in the asker's words
  questions?: { question: string; options: string[] }[]; // only on an Ask the store takes answers for (kind boss); every question also takes the boss's own words
  digest?: string;            // over the questions (owners.ts questionsDigest), so an answer cannot be meant for other words
  toolCallId?: string;
  item?: { session: string; id: number }; // the todo it blocks
  since: number;              // epoch ms
  state: "open" | "answered" | "cancelled" | "closed";
  answer?: { by: "terminal" | "gui" | "phone" | "owner"; at: number; answerId: string; replies?: { choices?: number[]; text?: string; note?: string }[]; cancel?: true };
  closed?: { at: number; why: "esc" | "abort" | "auto" | "owner" | "asker-ended" };
}
```

`answered` and `cancelled` carry the `answer` that won; `closed` says why it ended with no answer: the boss pressed Escape in the pane (`esc`), the asker's turn was stopped (`abort`), auto mode began (`auto`), the owner of a mirrored question closed it (`owner`), or its asker left the net (`asker-ended`: two readings at least a minute apart found no unit of its session, or, for a blocking Ask, found its session file with the tool call that asked it no longer open). An open Ask is kept however long it waits (the boss chose no timeout); an ended one is kept 7 days, for a resent answer and for the list of what was asked, and at most 500 of them.

## The answer path

One judgement for every way in, decided under the store:

- **First valid answer wins.** An answer must name the Ask's `digest` and reply to every question (an option by its index, or the boss's own words, as `checkAnswer` in dialogs.ts reads them), or be a cancel. The first one taken sets `answered` or `cancelled`.
- **A late answer gets 409**, `{ outcome: "closed", by, at }`: where it was answered (`terminal`, `gui`, `phone`), or that it ended with no answer.
- **A resent `answerId` replays the result** the first send had, so a page's Check again or a retry after a lost reply is not a second answer.
- **A mirror takes no answer here**: 403 `owner`, answer it where it is (its pane, or its card).

The ways in:

| from | how | `by` |
|---|---|---|
| the asker's pane | control socket `ask-answer` | `terminal` |
| this computer's page | `POST api/asks/<id>/answer {answerId, digest, replies \| cancel}`, or the session's dialog panel as before (the bridge relays the answer to the asker, which takes it to the store) | `gui` |
| a paired phone | the same route or panel over remote access | `phone` |

### `call_tower` boss questions

`call_tower` with `why: blocked` and `boss` opens a blocking Ask (`ask-open`) before it draws the question in the main's pane, and relays the same question to the page as it did. The first answer, wherever it comes from, closes the others:

- answered in the pane: the store takes it as `terminal`; the relay is closed, so the page's panel goes; a 409 there means the page or phone was first, and the result is that answer;
- answered on the page or phone through the panel: the relay takes the answer to the store first and accepts it only when the store did; the pane's dialog then closes;
- answered through `api/asks/<id>/answer`: the asker looks at its Ask once a second while the dialog is open, and closes the dialog and the relay when it is answered.

Escape, a stopped turn, and auto mode starting close the Ask with that reason; the close answers the Ask as it stands, and when an answer won there first (the phone's just before Escape), that answer is the result. Auto mode's own cancel of the open dialogs (bridge.ts, an answerId `auto-…`) is no answer: it closes the Ask as `closed/auto`. When no sb server answers `ask-open`, the question is still asked in the pane and on the page as before, and nothing is recorded; `ask-open` is sent once. Once the Ask is open, there is no going back to that path: an answer with no reply is sent again with the same answerId (three tries in all) and the Ask read back; an Ask read back still open gets the answer once more, and is read back again after it. Only an answer the store confirms is the result: one it never confirmed is not delivered as the boss's, and the tool's result is of its own kind (`unconfirmed`: the server did not confirm it, do not act on it, ask again), while the page's panel hears that its answer is not known to stand. The close of the relayed questionnaire names the answerId that won, and the bridge tells a page's answer accepted only when it is that one; any other hears the dialog was closed by another answer. A close with no reply is sent again the same way; an Ask whose close never arrived is ended by the session-file check above. `boss.item` (a todo id of the asker) names the todo the question blocks.

## Questions recorded as mirrors

At each reading of the net the server mirrors these, and closes the mirror when its source is gone (`owner`) or its asker left the net (`asker-ended`):

- **Wait cards** (`W<n>`, tower memory): every open wait for the boss (not resolved, not answered), parked ones included, the head tower's too (`wait:@head:<W id>`, opened on the head page). The asker is the card's raiser, else the workspace's tower (the head tower for its own).
- **Link waits** (`L<n>`) raised to the boss: the card a teammate's wait put on the boss's list (its raiser is the device) is kind `link`, its asker the teammate's device.
- **Dialogs**: a unit that waits on `ask_user_question` (rpiv's, through its adapter in owners.ts, or the open call in its session file) or `ask_user`. A `call_tower` call is not mirrored: its Ask is its own.

## The todo an Ask blocks

`item` is bound once, when the Ask is first recorded:

1. an explicit item: `call_tower`'s `boss.item`, or an `item` (a todo id) in the `ask_user_question` call's arguments;
2. for a subagent's question, its launcher's open todo whose `metadata.herdr` binding (`id`, or one of `runs[].id`) is the subagent's run id, counted only while that binding's `name` is the todo's `owner` (a run of a former owner binds nothing); the item is then the launcher's (`{ session: launcher, id }`);
3. the asker's todo in progress (its bridge relays the id of the first one, `todo.doing`).

None of these found: no `item`. A wait card binds through its raiser the same way.

## The probe: `straw-boss:ask-rows:v1`

On `pi.events`, as `straw-boss:car-rows:v1` is: the reader emits a plain object and sb's handler, synchronous, fills `rows` on it. sb answers in every pi in a Herdr pane that is no subagent; it asks its server for the rows every 15 seconds (`asks-rows`), and a session that knows of none answers `{ version: 1, rows: [] }`.

```ts
// pi.events.emit("straw-boss:ask-rows:v1", probe); afterwards probe.rows is set, or absent when sb is not loaded.
interface AskRowsProbe { rows?: { version: 1; rows: AskRowV1[] } }
interface AskRowV1 {
  id: string;        // "Q<n>", stable for the Ask's life
  subject: string;   // one line, the asker's words
  asker: string;     // the asker's name (a session's, or a teammate device's label)
  where: string;     // "<workspace> › <tab>" of the asker, the workspace alone, or the device's label
  kind: "boss" | "dialog" | "wait" | "link";
  since: number;     // ms since the epoch: when it was asked
  mine: boolean;     // the asker is this session or one of its subagents
  item?: { session: string; id: number }; // the todo it blocks
}
```

The rows are every open Ask of this Herdr server, the oldest first. The probe answers the rows of the server's last answer for 45 seconds (three asks); past that it answers `{ version: 1, rows: [] }` until the server answers again. A reader draws a row whose `item.session` is its own session under that todo, as blocked on the boss (`◐ #12 … ⏸ 等你：<subject> 5m`); every other row, and one whose todo it does not have, goes in a group `等你` / `Waiting on you`, its own (`mine`) first. The time is `duration(now - since)` as the run and car rows have it. A reader that finds `rows.version` other than 1, or a row whose `id`, `subject` or `kind` is missing or whose `since` is not finite, skips that row (or all of them).

## `/boss asks`

Prints the open Asks, this session's and its subagents' first: `Q3 · 5m · <asker> · <where> · <subject>`, and the todo each blocks. It asks the server first; when that ask fails (no server, or one without `asks-rows`), it says the questions are not known and prints no older list. It needs no ledger and no GUI.

## The GUI

The net carries `asks`, this computer's open Asks (never sent to a teammate, a remote turn or the operate slice, neither the list nor a plate's count). Each unit's plate shows a count badge of the open Asks whose asker is that unit, a wait card's on its raiser (or on the tower when it has none). The head page and each workspace page list the open Asks (the workspace's on its page, every one on the head page): `Q3 · asker · where · subject · 5m`. A tap opens its card (the unit's dialog, or the wait card), else the unit's comms; **Terminal** opens the asker's pane.
