# pi-straw-boss 0.80.2

Unreleased. A fix release on [0.80.1](0.80.1.md).

## Train

- **The server checks a submodule app's car against the app's own remote.** `received` refuses a head that is already on the base (a car lands once), and `landed` takes a commit only when it is on the base. Both fetched the base from the project's remote, where the commits of an app that is a git submodule are on no branch: a landed car of such an app was received again, a train's `landed` was refused with `landed.commit … is not on <base> of the project's remote` (or passed for a commit of the project that happened to be on a branch of that name), and an app whose base is no branch of the project was refused with `could not be checked … try again`. For an app whose folder is a repository of its own (the rule the delta check of 0.80.1 uses), the server now fetches from the `origin` of the app's checkout inside the project's checkout: at `received` as it reads it then, in the integrator's workspace checkout, and at `landed` as it read it when the train opened, before the train existed. The project's remote never stands in for it: an app's remote that names no `https` or `ssh` URL is received unchecked (`the remote of app <app>'s own repository in the integrator's workspace checkout could not be read`), and its `landed` is refused. The refusals name `the remote of app <app>'s repository` where they named the project's remote. Nothing else of the two checks changed: a remote the server cannot reach or authenticate with is still received unchecked with its reason (`auth`, `connection`, `repository-not-found`), the mirror of each check is made and removed as before, and an app in the project's own repository is checked against the project's remote. The remote a first open read is remembered per app beside the project's, so a later open that reads another one for the app is not trusted for `landed`, and the two are never compared with each other.
- **A project whose git dir is outside its folder keeps the 0.80.1 fix.** A project that is itself a submodule of another repository, or was cloned with `--separate-git-dir`, keeps its submodules' git dirs under its own git dir and not in its folder. 0.80.1 accepted an app's git dir only inside the project's folder, so for those layouts a submodule app's delta evidence was still refused with `on.head is not the car's head`. A git dir inside the project's own git dir or common dir is now accepted too.
- **An app whose `dir` is a folder inside a submodule is asked in that submodule.** The app's repository is the nearest folder holding a `.git` from the app's `dir` up to below the project's root, so a submodule that holds several apps works. 0.80.1 listed this as a known limit.
- **What 0.80.1 said about staying inside the project now holds.** Its note said that no `apps.json` entry leads git outside the project. Two ways were left, both open only to someone who can already write the checkout: an app folder whose `.git` is a symlink to a git dir elsewhere, and a git dir inside the project whose `commondir` names a repository elsewhere. The git dir an app folder's `.git` is or names (a folder, a `gitdir:` file, or a symlink) and the common dir that one names must now both be, after symlinks are resolved, inside the checkout, the project's main checkout, or the project's own git dir. The ancestor check of delta evidence, in the integrator's guard and in `train check --accept`, also runs with replace refs off (`--no-replace-objects`), so a graft in the repository asked cannot make a commit an ancestor.

## Known limits

- An app that is a submodule of the project but is not checked out in the integrator's workspace checkout, nor in the project's main checkout, has no `.git` to find: it is checked as an app of the project's own repository, against the project's remote.
- A linked worktree of a project whose git dir is outside its folder finds a submodule app only when the worktree checks the submodule out itself; the main checkout's copy is not found from there.
- The server's git still has no credential helper, so against a private remote the check at `received` is still `received unchecked` with reason `auth`, and no project sets `landed` yet. This release changes which remote is asked once that is no longer so.
