# pi-straw-boss 0.80.12

Released 2026-11-18. A fix release on [0.80.11](0.80.11.md).

## Fixes

- **A coordinator's role section no longer changes when its plan's graph does.** Within a session the `straw-boss` section keeps the graph it was rendered with. A graph that changed since reaches the model once, as the steer a change during a run already sent (`Your plan's graph is now …`, saying what it adds to, replaces in, or drops from the section): during the run when a `todo` call changes it, else at the start of the next run. Before, every run start after a graph change re-rendered the section's `## Dispatch` and `## Graph:` parts, so the whole system prompt changed and the prompt cache was rewritten (traced: 22 + 22 strict cache misses, about 3.9M tokens a day).
- **That steer counts as told once pi delivers it, not when it is sent.** A steer pi's queue drops before delivery (Esc, pi's dequeue key, or the page's **Edit**, which presses that key) is told again at the start of the next run, and the next change is written against what the model last received: a dropped "drop your sections" steer no longer leaves a later "Add to your instructions" beside the section's own `## Graph:`. One such steer waits in pi's queue at a time; a change meanwhile is told once it arrived. A steer pi stores at once because it is idle (while it awaits the end of a run's handlers, or after a run that failed to start) counts as told when sent. When a steer an abort left queued arrives at the next run's start after a newer one written against the older state, the next steer is the whole role prompt.
- **The section is rendered anew, with the plan's graph, where the cache or the steers are gone anyway:** every session start (startup, `/reload`, `/new`, `/resume`, `/fork`), after a compaction, after a `/tree` move, and on a role or kind change, as before.
- **Each compaction in the middle of a run tells that run again what its section lacks**, the second as well as the first: a steer when pi retries the turn, a stored message when not, so no ended run is continued for it.

## Known limits

- What else is the session's own still rewrites the section at the next run start: its tab's or workspace's label (a `boss_rename`, a renamed tab), and a member whose tab gains or loses its main. A tower's section also takes its `Since your last run:` lines at each run that has them.
- A `/reload` renders the section anew, with the plan's graph, even when nothing else changed: the extension starts over and reads the prompt files again.
- When pi's dequeue key or the page's **Edit** drops a role steer while the run goes on, later changes in that run wait for the next run's start: sb cannot tell a dropped steer from one still queued until the run ends. Each compaction in that run tells the run nothing again either, while the dropped steer still counts as waiting.
- A steer an abort left queued (a compaction in the middle of a run, an abort over RPC or the SDK, or a run that failed to start; sb's own aborts clear the queue in pi's TUI) and a newer one written against the older state reach the model one after the other at the next run's start, and can disagree for a turn, until the whole role prompt that follows them arrives.
- A compaction in the middle of a run that retries no turn (pi's threshold compaction before the next response) stores its message, which pi adds at the end of the turn: the first response after the compaction lacks it. A steer would reach that response, but would make pi continue a run that ended with the compaction (0.80.7).
