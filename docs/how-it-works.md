# How pi-straw-boss works

The full behavior behind the [README](../README.md).

## How it works

Joining is automatic; the chain of command is earned.

1. Every joinable pi in Herdr joins its tab's net at session start as a **member**: no reminder, no question. It does not join outside Herdr, as a pi-herdr-agents subagent (`PI_SUBAGENT_ID`, its parent represents it), in a sub workspace (below), or as the tower itself.
2. A member becomes its tab's **main agent** by promotion. The agent calls `boss_promote` when its work grows (several steps, dispatching workers, more than one app); the member prompt says so. A member that calls pi-herdr-agents' `subagent` or `subagent_resume` tool without promoting is promoted automatically, before the subagent starts or resumes. A join that failed at start and retries after the session's pane moved to another tab registers on the tab it is in now, so it never becomes a second main there.
3. A tab has one main. An agent never takes over an existing one: while the tab's main is live, `boss_promote` is refused with a message and the automatic promotion is skipped. The member may still dispatch its own subagents, but its prompt tells it to first message the main through intercom with what it will do and which resources it will use.
4. A main never demotes. When its session ends, the tab has no main until a member promotes (the members' prompt then offers promotion). `/boss` is the user's manual takeover: it makes this session the tab's main even when another is.
5. The workspace tower opens when agents start to collide: a member dispatches a subagent (it promotes itself first, and a promotion opens the tower), the workspace has two members while another workspace already has a live tower, or `/boss tower` asks for it. Mains and the tower go together. The owner of each tab channel (its earliest member) checks when Herdr reports an event that can change the answer (`workspace.metadata_updated` for any workspace, `pane.closed` and `pane.agent_detected` in its own, over one `events.subscribe` connection per session), when the tab channel's owner changes or a session leaves it, and once every 4 minutes for what no event reports (a tower that crashed); a member that joins checks the two-member rule once. A check that must wait out a grace sets one timer for it instead of polling: under a live tower a tab with no live main promotes it; with no tower, every main is turned back into a member, at once when the tower quit (`sb_tower_quit=<members it left>` on the workspace; the two-member rule then waits until the workspace has more members than that, so a tower closed on purpose stays closed, while a subagent or `/boss tower` opens it any time) or after 15 s otherwise (a `/reload` comes back within that), except a main younger than 60 s, whose tower may still be opening. A demoted main keeps its subagents; subagents never promote. A tower dispatches no subagents: its `subagent` and `subagent_resume` calls are blocked with a pointer to `boss_open_main`, so nothing outlives it with no one to take the result. A tower that quits closes its own pane (an emptied tab closes with it); a reload, `/new`, resume or fork keeps it. The tower stays open when mains leave.
6. A promoted session keeps the subagents it launched: the dashboard and the browser view link subagents through the launcher's session file, not through its role, so they count under it as main with no re-registration.
7. A **sub workspace** is treated like a subagent too. `herdr worktree create` opens a linked git worktree as its own workspace (`worktree.is_linked_worktree: true`); its parent is the workspace with the same `repo_key` that is not linked. Sessions there never join, `/boss` is refused, and they receive only scope `all` broadcasts. A sub workspace never gets a tower: `call_tower` from it, or aimed at it, goes to the parent workspace's tower (opened there on demand), and fails with a clear error when no parent workspace is open.

| Role | Who | Gets |
|---|---|---|
| main agent | the member that promotes first in a tab, or the `/boss` taker-over | a short prompt: split work by app, plan before the first dispatch, brief workers, check results, ask the boss before merging or deploying |
| member | every other joined session | a short prompt: with a main in the tab, tell it before dispatching subagents; without one, promote when the work grows |
| tower | one per workspace, in its own tab labelled with the Nerd Font radio tower glyph (U+F043B) | a prompt for coordinating agents and repairing coordination friction, and for opening a main when no session owns a request; it never asks the user |

Before its first dispatch a main reads `prompts/planning.md`, as it reads `prompts/apps-config.md` when it splits work, so the planning rules stay out of every run's system prompt. It chooses a coordination graph: single-loop (one task, carried by itself or one subagent) needs no plan. For fan-out/fan-in and orchestrator-worker it writes the plan as pi `todo` items: one per task, its `owner` the subagent (or `self`), `blockedBy` for the tasks it depends on (which leaves the rest parallel, up to a cap of 4), and in its description and metadata the anchor that checks it. Tasks that share one anchor share one checkpoint todo instead of each branch checking the same thing. The anchors are testing, pseudo-human, human, and adversarial-review, each the lightest check that can fail before the change. The main dispatches without asking the boss to confirm the plan; it asks the boss only for decisions the plan cannot settle, before the task they block: a requirement that is unclear or contradicts the architecture, and an authorization such as a merge to a shared branch or a deploy. The browser view shows the todos as the plan's progress.

The tower is opened by a main, by `/boss tower` from any session, or by the rule above (`call_tower` from a member opens nothing), without taking focus, and answers through intercom. Its tab is moved to the first position of the workspace right after it is created (or adopted), through Herdr's socket API (`tab.move`, no focus change); a failed move is reported as a warning and ignored. A tower tab is recognised by the `sb_role=tower` pane token that only Straw Boss writes, never by its label, because a pi-herdr-agents subagent can be named `tower`. A tab that lost its token because its tower quit is still adopted when its label is exactly the radio tower glyph (U+F043B), it holds a single pane, and no agent runs in that pane (a shell prompt): the next opening starts pi there instead of creating a second tower tab, marks the pane again, and moves the tab first. When several such leftover tabs exist, one is reused and the other shell-only ones are closed. A tab labelled only `tower`, or one whose pane runs an agent, is never adopted or typed into. When a tower quits (pi's `session_shutdown` with reason `quit`; a reload, `/new`, resume or fork keeps the tab), it clears its tokens and, once pi has exited, closes its own pane; Herdr closes the tab with its last pane, and other panes in the tab stay. If two towers ever race in one workspace, the live token holder wins, otherwise the lower tab id, and the other closes its own tab. Towers of different workspaces reach each other with `tower_list` and `tower_send` ([Talking between towers](#talking-between-towers)), or with `call_tower` from any session; the **head tower** is the tower of the first workspace in `herdr workspace list` order that is not a sub workspace, so there is no election, and it is a mark and no rank.

### The tower's digest

A tower learns what changed in its workspace without asking. Each session in the workspace's net writes one line when it joins (`a1 joined tab billing`), when its `subagent` or `subagent_resume` call returns without an error (`MP-1 export started subagent lint-sweep (worker)`), and when it calls `boss_rename` (`a1 renamed itself "MP-1 export" (tab billing)`). Each line starts with the local time (`HH:MM`). At the start of each run the tower reads the lines, oldest first, into its role section under `Since your last run:`, and clears them, so it reads each line once. A member's or main's run never reads them.

The lines live in Herdr's memory as workspace tokens (`sbd_<time>`, one line each), written under their own source, `straw-boss-digest`, without the TTL of Straw Boss's role tokens, so they wait however long the tower is idle. Herdr keeps at most 32 tokens on a workspace, changes at most 16 per report, and cuts a value to 80 characters without its newlines: the digest keeps the newest 20 lines, a note that finds 20 drops the oldest in the same report, and a line is cut to 80 characters. A new Herdr server starts without them, as it does without every other token; the role tokens are written again, the digest is not. A line that cannot be written is dropped without failing the join, the launch, or the rename. A tower also writes `head tower is now <workspace>` in its own digest when the head tower changes ([Talking between towers](#talking-between-towers)).

### Talking between towers

Towers coordinate with each other directly, with two tools only a tower has, and every message the net carries for a session tells its reader who sent it.

**The header.** The code writes a line before the text of every `call_tower`, `boss_broadcast`, `tower_send`, and handoff message (never the model, so a name or a message cannot change it):

```text
[straw net from=<name> id=<session id> role=<tower|main|member|session> [head=yes] workspace=<label> kind=<call_tower|broadcast|tower_send|handoff> scope=<scope> to=<recipients> reply=<expected|none> [why=<milestone|shared|blocked|unspecified>]] <message>
```

It has the shape of the line a net sidecar types before a message ([From Claude Code or Codex](#from-claude-code-or-codex)), with the sender's own fields added. `role` is the sender's role as its pane's `sb_role` token publishes it (`session` for a pi that did not join the net, which only a scope `all` broadcast reaches); `head=yes` marks the tower of the head workspace. `scope` is `tab`, `workspace`, `towers`, or `all` for a broadcast and a `tower_send` to all, `tower` for a message to one tower, and `main` for a handoff. `to` names every recipient as `<name> (<role> of <workspace>)`, `head tower` for the head tower, separated by `;`, at most 20 and then `+N more`: all recipients read the same line, so a tower that gets a message knows who else got it and does not send it on to them. `reply=expected` means the sender waits for an answer; `none` means a notice. `why=` is on a `call_tower` header only: the reason the main calls, written by the code from a closed set (see [When a main calls the tower](#when-a-main-calls-the-tower)), so the tower reads it from the line and not from the message. Control characters and runs of whitespace in a name fold to one space, and a name with a space, quote, `]`, `=`, or `;` is written in double quotes with any quote inside it replaced by `'`. A net sidecar receiving it types its own `[straw net from=… role=…]` line first, with the role Herdr's tokens give the sender, so the two lines are not merged and the sender's cannot stand in for the verified one.

**`tower_list`** (tower only) reads the net once and answers, for every workspace that is not a sub workspace: its id and label, `head`, `self`, `reach` (`tower`, `main`, `member`, or `none`: who a message for it reaches, see below), the sessions it reaches with their state (the same mark as the dashboard: `idle`, `working`, `waiting`), and its tabs with the label, the main's name, and the members' names. A main names itself with `boss_rename` for its current work, and the tab takes that name, so the tabs say what the workspace is working on. The answer is JSON, as `boss_status` is.

**`tower_send`** (tower only) takes a message, an optional `workspace` (id or exact label; a sub workspace goes to its parent workspace), and `reply` (default false). With no workspace it goes to every other tower. It never opens a tower.

**Workspaces without a tower.** A workspace without a live tower (no `tower` token, or the session is not on the net) is reached through its main agents, else its members: the sessions of the workspace that joined the net, the tower's own session excluded. Both `tower_send` and `boss_broadcast` with scope `towers` do this, and the result labels each such recipient, as in `kb-main: sent [no tower in 知識庫: main]`. A workspace with no tower and no joined session is skipped (`tower_send` to it alone is an error that says so). The sender's own workspace never answers for a tower: a session never reaches itself, and a main in a workspace without a tower does not reach its sibling mains by scope `towers`; the tower of its own workspace, when there is one, is a recipient. Sub workspaces keep their rules (they have no tower and their sessions receive only scope `all`).

**`boss_broadcast`** with scope `towers` stays for sessions that are not towers, under the same header. `call_tower` has an optional `reply` too, default true (the tower answers); a notice sets it to false. It also takes `why`, which pi's tool requires ([When a main calls the tower](#when-a-main-calls-the-tower)).

**When the head tower changes.** Every tower watches Herdr's workspace events (`workspace.created`, `closed`, `moved`, `reordered`) over one `events.subscribe` connection of its own, reads the workspace list, and when the first workspace that is not a sub workspace is another than it was, writes one digest line in its own workspace (`head tower is now <label>`, see [the digest](#the-towers-digest)). The first reading after the connection is the baseline and writes nothing, so a tower never announces the head it started under. The connection closes with the tower's session. The prompt tells a tower the head is a mark and no rank, that it relays nothing to a tower the header already names, and that it reports back once after it acts on another tower's or a main's request.

### Straw Link: towers across computers (the link holder)

Design: [docs/specs/2026-10-25-straw-link.md](specs/2026-10-25-straw-link.md). This is what the code does so far (the holder, delivery, the tools, remote turns, and the GUI's team settings); unattended devices' controllers and joining over a tailnet are later steps. A computer with no team set up (nothing under `link.teams` in `config.json`, no team file) runs none of it: no channel, no election, no files. The holder runs in the [sb server](#the-sb-server) (`src/link/service.ts`); a pi session only asks it.

**Files.** `<pi agent dir>/straw-boss/link/` (`PI_CODING_AGENT_DIR` aware, mode 700, files 600 where the OS has modes; paths are used as Unicode paths and never become a shell command): `device.json` (the keys, the label, and the next sequence number), `device.id`, `teams/<team>.json` (the roster copy, the team keys by epoch, the relay URL, the last event id, and the last sequence number taken from each sender), `inbox/<envelope id>.json`, `holder.json` with `holder.lock`, and `link.log` (one JSON line per dropped envelope, notice, or send). Every write goes through the lock; a write outside it throws. A lock whose process is gone, or that is older than 10 s, is taken over. A team file that is missing or damaged makes the team stop: nothing is taken and nothing is acknowledged, and the only way back is to join again, because a fresh file would forget which sequence numbers were already taken.

**The link holder.** It runs in the primary sb server (the server of the default Herdr; a secondary server holds no link, and a session on another Herdr is told so), and the server is its only candidate: no pi session or tower takes part in the election any more. The election is still its own, not the GUI's: `holder.json` (session id, version, PID, start time) names the server, whose id is `sb-server-<8 hex>`, and `holder.lock` guards it as before. The server ranks as a tower of its own version, so a session of the previous build, which is still a candidate there, can neither outrank it by build nor by role: it contests only a record that is vacant or whose process is gone, and the server takes the record back at its next look (every 2 s). The server starts the holder after it has connected to the broker and before it reports ready, waiting at most 3 s for the first look; a stop or restart removes the record first, so the next server takes it at its first look. A holder that finds the record names another process stops. `status` shows the link's state (`inUse`, `holding`, `active`, and the last notices); the notices that a session used to see on its screen go to `server.log` (`link-notice`) and to `status`.

**Requests from sessions.** A session asks the holder over the server's control socket, one request per connection: `{cmd: "link", from: <the session's intercom id>, body: {op, …}}` answered by `{ok: true, answer: <the holder's answer>}`. The ops are the ones the channel carried (`send`, `list`, `board-read`, `confirm-request`, `confirms`, `answer-confirm`, `forget-confirm`, `gui`, `request-open`, `request-run`, `request-drop`) and `taken` (the tower says an inbox message is in its session). There is no 16 KiB limit and no chunking. `from` is self-reported, as pi-intercom's ids are; the GUI's requests are still taken only from the session `gui.json` names (and from the server itself once it hosts the GUI). A session finds the server through `server.json` and the `hello` secret; with no server running, or none holding the link yet, a request fails with "No link holder is running", and a server that is restarting says so. The channel `straw-boss/link` is kept for the previous build: the server answers a session of that build's chunked `req` with chunked `res`, takes its `taken`, and offers inbox messages to resident towers on it. Nothing the server loads imports pi-tui, `tools.ts`, `pairing.ts`, or the trust question (a test walks its imports).

**Receiving.** A stream resumes from the team file's last event id (the relay sends every envelope this device has not acknowledged on a new stream anyway). Each `tower` envelope is checked and decrypted under the lock, written to the inbox, and the sender's high-water mark moved in the same locked write; only then does the stream acknowledge it to the relay. A crash before the inbox write gets the envelope again and delivers it once; a crash after it and before the acknowledgement gets it again and the sequence guard drops the copy. A displaced holder (the record names another session) keeps the envelope for the next stream.

**Delivery.** A message goes only to a tower whose pane's cwd is inside the team's `project`: the one closest to the project root, then the first in Herdr's workspace order (a named `workspace` restricts it to that workspace's tower). Mains and members never receive one. The holder offers the inbox item to that tower over the intercom channel `straw-boss/link` (not owner-eligible; only a tower registers it now); a tower takes an offer only from the session `holder.json` names, the server. The tower keeps it until it is idle (`isIdle()` and no pending message, checked in the same tick), then sends it as a custom message of type `straw-link` with `triggerTurn`, under the header below, one message per tick, and tells the holder (`taken`, on the control socket), which removes it from the inbox. The session entry `straw-link-seen` remembers what a session took, so a restart does not take it twice. With no such tower the message waits in the inbox for 7 days with one notice; the sender's membership is checked again when a tower would get it. When the tower is the sb server's (the default), nothing of this paragraph's offer-and-take happens: the server starts an ally run for the sender instead ([Ally runs](#ally-runs-b6)); the offer over `straw-boss/link` is kept for towers that are still resident and for the reply to a main.

```text
[straw net from=<sender label> id=link:<sender device id> role=tower workspace=<label> remote=<device label> device=<short id> team=<project folder name> verified=yes kind=tower_send scope=tower to=… reply=<expected|none>] <message>
```

`from`, `workspace`, and `remote` are cut to the label character set (ASCII letters, digits, space, `.`, `_`, `-`; anything else becomes `_`) and 40 characters before they are quoted, and `id=` is always `link:` and the sender's device id, never a session id of this computer. `team=` is this computer's own name for the team, so it keeps its characters (cleaned, quoted, at most 80).

**Sending.** `tower_send` with `device` (a short id, an id, or a label; `workspace` then names a workspace label on that device) hands the message to the holder in the sb server over the control socket. The holder checks that the caller is a tower whose cwd is inside a team's project, resolves the device (a name that fits two devices, or this device, is an error that lists the candidates), reserves the next sequence number, builds and signs the envelope, and writes it to `link/outbox/` under one lock before the first post, then posts it in order with retries and answers once the relay has it or after 10 s with "queued". The file goes once the relay holds the envelope or refuses it for good (a refusal that comes after the answer is told to the boss), and the next holder of the computer posts what is left, first, in order. A 401 from the relay halts the team's posts for 60 s (a clock that was off), and a send meanwhile is refused with the reason. A team that forks, loses its team file, or refuses the stream (the device was removed) stays stopped, on disk too, until its team file is replaced by joining again. A message may hold 192 KB; the inbox keeps at most 100 messages per sender and 500 in all, and the relay keeps the rest. `tower_list` adds `remote`: the teammates' devices from their last presence, with the workspaces and tab states they chose to share. A presence goes out every 30 s (`share: "status"` adds the bound workspaces and their tabs; `"presence"` only that the device is online) and a device with none for 90 s is offline.

**Remote turns** (`src/link/{turn,allow,gate,policy,hooks}.ts`; `hooks.ts` registers the pi hooks, `runtime.ts` wires it to the holder in the server). A run is a remote turn from the first `message_start` or `message_end` of a `straw-link` custom message until `agent_settled`, however the message got into it (a delivery, a steer into a run that began local); `agent_end`, a retry, a compaction, or a continuation does not end it, and a local message that joins leaves it as it is. Its level is the lowest of its remote senders'. A sender's level is `reply` unless this computer names it: `link.trust` in `config.json` (device id to `reply`, `forward`, or `dispatch`), or, on a device whose `/etc/straw-link/policy.json` says `unattended` and passes the owner check (the file and its folder owned by another user, not symlinks, not writable by this user), that file's `trust` (`true` means `dispatch`) and `config.json`'s `link` section is ignored. A policy file that is there but fails the check refuses unattended mode: every sender stays at `reply` and the boss is told once. A message that names no sender this code put there is remote at `reply`.

- `link_request` is blocked at every level, `dispatch` included, with no dialog (the tool is the boss's alone, in a local turn).
- At `dispatch` nothing else is held. At `reply` and `forward` the `tool_call` hook allows by exact tool name: `read` of a file `git ls-files` lists in the bound project (after `realpath`, so a symlink out of the project is not); `grep`, `find`, and `ls` with every path inside the project, whose output the `tool_result` hook cuts to the lines and entries that belong to a tracked path (a line it cannot attribute, such as a notice, is dropped; the structured copy goes with the replaced content); `tower_list`, `board_read`, `boss_status`, `todo` (the first two answer a remote turn only what its senders already receive: [The work board](#the-work-board)); and `tower_send` whose `device` is a sender of the run (id, short id, or label). Paths are read the way pi's own tools read them (a leading `@`, `~`, odd spaces). Any tool that names a path under `~/.pi`, `~/.ssh`, `~/.aws`, `~/.config`, `~/.gnupg`, the agent dir, the `link/` dir, or a file named `.env*`, `*.pem`, `*.key`, `id_*`, `*.p12` (as written or once resolved) is refused outright, not confirmed. Everything else opens the gate.
- **The gate** shows its own dialog through the dialog contract (owner `straw-link-gate`, prefix `straw-link:gate`, a gate keyed by `toolCallId`, so it is answerable from a page even in a parallel batch): the sender's label and short id, the tool, and its arguments in full (a call whose arguments are over 12 000 characters is refused). The terminal shows the same confirm; the first answer, from the terminal, from a page (this computer's or a paired device's), or at `forward` from the sender's device, ends the other two. Deny, no answer within 10 minutes, and the abort of the call all block it with "the boss declined a remote request"; the output of a call the boss allowed is not filtered.
- **`forward`**: the run's lowest-level sender's device also gets a `confirm-request` (dialog id, digest, tool, full arguments). Its holder keeps up to 20 for 10 minutes (`confirmRequests()`, `answerConfirm()`; the GUI that shows them is a later step), and sends a `confirm-answer`. The asking holder takes an answer only from the device it asked, with the dialog's id and digest, once; any other is dropped and does not use the dialog up.
- **After the turn**, in a later local run the `context` event replaces the text of each `straw-link` message that did not start the current remote run with a marker naming its device and saying it is a peer's request, not the boss's instruction; and a message the tower sends to a local session during a remote turn carries `origin=remote:<sender device id>` in its header. A reply to the sender already expects no answer unless the tower asks for one. Two limits are documented, not guarded: a compaction summary is written by the model from the whole conversation and pi's `session_before_compact` hook can only replace the whole compaction (it cannot hide messages from the summarizer), so a peer's text can survive in a summary unmarked; and a message sent through pi-intercom's own tool after a gate approval carries no `origin=` header, since only the tower's `tower_send` adds it.

**Team settings in the GUI** (`gui/link.ts`, `gui/linkbar.ts`, `gui/linkmodel.ts`; the holder's side is `src/link/admin.ts`, reached through `runtime.ts`'s `gui` port and `control.ts`'s `link/<name>` routes). The settings panel's Teams button opens the tile. A computer that has not set Straw Link up shows one button, which starts the election; the first team or join then runs it as above. The page never holds a key, a team secret, or an invite secret: it asks the holder, which returns a view (the roster with each device's label, short id, role, attended or not, last presence, and trust level; the open invites; the join in progress; the notices).

- **Create** takes the relay's origin (default `link.relay`), the operator's one-time team token, a label, the project folder (a folder picker that opens on the folders the open bases work in), and what to share. A teammate outside the default relay writes their own relay.
- **Invite** shows the invite as a QR (drawn from the text the holder made) and as its text, with a 10-minute countdown and Cancel. **Invite an unattended device** takes the device's 26-character id and makes an invite pinned to it.
- **Join** is a paste field first; a camera button appears only where the browser has `BarcodeDetector` (Electron on Windows has none, and the camera permission is the host's). The joiner picks the project folder, and the page shows the four safety words to read out. The inviter taps the matching set among three decoys; a wrong tap, a cancel, or the countdown ends the invite. An unattended device is approved with a button instead, since the id in the invite stands in for the words.
- **Roster.** A label that two devices share shows the short id beside it. Admins remove a device, change a role, and rotate the key (each asks twice); anyone leaves (the holder refuses the only attended admin's leave unless the page says `force`, which its button does only after the second press: a team with no attended admin cannot remove a device or rotate its key). When there are two attended devices and the founder is the only attended admin, the page offers to make the other an admin. Trust per device (`reply`, `forward`, `dispatch`) is written to `config.json`'s `link.trust`.
- **Teammates' bases** (`net.link.allies`) are drawn beside the local bases from the latest presence: the device's label and short id, the team, the tower's state, and each tab's state. They are not openable, and nothing connects to them.
- **Notices** (the header's Link button, shown only while there is one): a join request waiting, a roster mismatch or fork, the relay unreachable for more than 2 minutes, a message waiting for a tower, a message held more than 10 minutes, and a forwarded confirm. A forwarded confirm is answered in the list with Allow or Deny, the tool's arguments in full, through the holder's `confirmRequests()` and `answerConfirm()`.
- **A paired device** may read the state and answer a forwarded confirm, and nothing else: every other action changes who may command this computer, so only this computer's own page (a request on the loopback listener) does it. An invite text is only ever returned to that page, and a paired device's state leaves out what an agent put into the join or create screen.

**`link_request`.** An agent asks for `create`, `invite`, `invite-unattended`, `join`, `trust`, `leave`, `remove`, `role`, or `rotate` with its arguments and a reason. It never runs unasked: the holder checks and words the request (the dialog shows these lines, never the agent's own description), and a dialog through the dialog contract (owner `straw-link-request`, prefix `straw-link:request`, keyed by `toolCallId`) shows the action, every argument, the reason, and the requesting session. Only an explicit Approve runs it; for `trust`, `remove`, `role`, `rotate`, and `leave` (the high-risk actions) Approve can be given only from this computer's own page or terminal: a paired device sees the dialog with Approve disabled, can still deny, and its approval is refused (403 `local_only`, decided by the listener), while the other actions are approvable from a paired device too; Deny, a timeout (10 minutes), the end of the tool call, and a dialog that cannot show everything all refuse. Each request is its own dialog; no setting skips it. The holder carries the action out, and an approved `invite` returns the invite text to the asker. An approved `join` or `create` only opens the screen prefilled: the words are still compared. A computer set up as unattended refuses the tool outright, and a remote turn refuses it at every level. While a request is open (its call in the session file, or its dialog relayed by the owner), a paired device sends only Escape (No) and no prompt; this computer keeps every key, and the terminal confirm comes up 1.5 s after the dialog is published, so a key already on its way cannot be taken as Yes. A call nested in another tool (codemode) is blocked, since the session file would not show it. Residual assumption: a Herdr or GUI stall of more than 1.5 s after a key passed its last check can still deliver that key late.

### The work board

A main says what it is doing in one place, and a tower reads it before it routes work (`src/board.ts`, `boardauto.ts`, `boardfill.ts`, `boardset.ts`, `boardread.ts`; the design is `docs/specs/2026-10-25-straw-link.md`, Work board). It works on one computer without Straw Link, and crosses to allies' towers when a team is set up.

- **An entry** is `now` (1 to 120 characters, one line) and 0 to 8 checklist items (`t` of 1 to 80 characters, `done`). Whitespace folds to one space; a control or format character (an escape, a bidi override, a zero-width mark) is refused on write with the reason, never cut silently. Every reader checks the same rules and cuts again, so a file that skipped them is held to them, and a file that fails the structure check is ignored. The entry carries no name, workspace, tab, or state: a reader joins those from the net when it reads. The file also says who wrote it (`src`: `set` for `board_set`, `todo` for the auto-fill, with the todo list's `count` of tasks done and in all); `src` and `count` stay on this computer and are not in the `board` message.
- **`board_set({ now, items })`** replaces the session's whole entry; it overrides the auto-fill (below). It is registered for joined sessions that are not towers, and refused unless the session is its tab's main at the call (a member, a demoted main, a tower, and a subagent do not write). It writes only `<state dir>/board/<own session id>.json` (folder 700, file 600, a temporary file renamed over it); no parameter names another session's file. Its answer says where the text goes: `local towers`, and `team <name> (<n> devices)` for each team whose project holds the main's pane directory and whose `share` is `status`. `board_set({ auto: true })` (no text) hands the board back to auto-fill at once. A sidecar main (Claude Code, Codex) calls `straw-net.py board --now N [--item '[x] done step'] [--item '[ ] open step']…`, the same code; it has no todo list to fill from.
- **Auto-fill** (`src/boardauto.ts`, `src/boardfill.ts`). The board fills itself in the main's own session; the server takes no part. At the end of a turn, after a tool call, and after a move in the session tree or a compaction, a main reads its todo list (rpiv-todo's snapshots on its branch, the same reading as the card's todo summary) and its name (`boss_rename`, or `/name`; pi's default name, the session id, is no name) and writes the entry. `now` is `<name>: <task in progress>` (its `activeForm`, else its subject), else `<name>: next <first pending>`, else `<name>: done (n/n)`, and with no todo list the name alone; with no name the line has no prefix, and with neither there is no entry. The items are the tasks, in progress first, then pending in id order, then completed (highest id first), at most 8. `boss_rename` refills the line at once.
  - **Scrub.** The text is cleaned (NFKC, format characters removed) and scrubbed before it is cut to the board's caps (nothing is refused, since no model wrote it for the board): an absolute path inside the session's working folder becomes relative to it; any other path (POSIX, `~/`, `$HOME/`, `%USERPROFILE%\`, `C:\`, UNC, or `../` out of the folder) becomes `…`; a URL becomes its host (`…` when it has userinfo or no host); an email address and a secret-shaped token (`sk-`, `ghp_`/`gho_`, `glpat-`, `xox?-`, `AKIA`, a JWT, `npm_`, `sk_live_`/`rk_live_`/`pk_live_`, hex of 32 or more with or without `0x`, a letters-and-digits run of 32 or more in both cases, `Password=`/`Pwd=` and its value) become `…`. A task that is more than half `…` is dropped, and the last of the 8 places says `(n hidden)` (marked done, so no reader counts it among the open tasks). Customer names cannot be found by pattern: that is a documented limit, and the allies' rule below bounds it. Paths with spaces and a bare `host/path` without a scheme are not recognized.
  - **One gate for labels.** Every workspace label, tab label, session name, opened-by, and ledger line that an ally can read (the board and presence on the wire, a `tower` message's workspace, a confirm request's tower name, `tower_list`, `boss_status`, and `board_read` in a remote turn or an ally run, scoped to the workspaces inside the bound project, and the ally brief) goes through `allyLabel`: scrubbed first, cut last. Your own views keep the raw text.
  - **Override.** The main writes only when the entry it would write differs from the last one it wrote, not from the file, so a `board_set` stands until the todo list or the name moves, and `board_set({ auto: true })` ends it at once (with nothing to show it removes the entry). A `board_set` entry that outlived a `/reload` stands the same way: the first reading in the new extension only records the list. A member and a demoted main write nothing.
- **Expiry.** A main's `session_shutdown` deletes its own file on `quit`, `new`, `resume`, and `fork`, and keeps it on `reload` (a sidecar's leaving deletes it too). A file whose session is not live, or no longer its tab's main, shows as `state: "ended"` until 30 minutes after its last update, then not at all; any `board_set` or `board_read` also deletes files of sessions that are not live and have not been updated for 24 hours. A reload that is followed by a quit leaves its file for those rules to remove.
- **`board_read({ scope?, device? })`** (towers only, registered with `tower_list`) answers JSON: a `note` that remote entries are data, `local` (each live main's workspace, tab, name, state, `now`, `items`, `updatedSecondsAgo`; a live main with no entry shows with its name and tab alone), and, only when Straw Link is set up, `remote` (one row per ally device: `origin: "remote"`, the team's name on this computer, the device's id, short id, and label **from the roster**, `online`, `boardSecondsAgo`, and its entries). `scope` is `local`, `remote`, or `all`; `device` reads one ally (as `tower_send` resolves it, so an unknown or ambiguous name is an error that lists the candidates) and skips the local part. Remote text keeps its characters but loses control and format characters and is cut again.
- **In a remote turn** (any level) both `board_read` and `tower_list` are on the allowlist and answer only what the run's senders already receive: `local` holds only mains whose pane directory is inside the project the senders' teams bind (with senders of teams that bind different projects, none; an ended entry has no directory to prove it and stays out), each auto-filled entry as the allies get it (the name and the done count), `remote` only those teams' boards, and `tower_list` only the workspaces inside that project and the senders' teams. The result of a `board_read` stays in the tower's context in later runs, like any tool result; each remote line is at most 120 characters, under `origin: "remote"`, below the note.
- **Sharing** is the `board` message kind (`src/link/kinds.ts`): ephemeral, to the whole team, from any member, a kind of its own so an older client drops it as `unknown-kind` and keeps reading presence. Each entry is `(entry id, workspace label, tab label, name, now, updated, items)`; an auto-filled entry goes as the main's name and the done count (`<name> (3/5)`), no task text and no items, and a `board_set` entry whole; the id is the first 8 bytes of `sha256(device id ‖ session id)` in hex, so no local session id leaves the computer. At most 24 entries (newest first), labels and names 40 characters. The holder looks at the board folder on its 5-second tick, once per team per 15 seconds (a change goes out within about 20 seconds): it sends the live mains whose pane directory is inside that team's project, when `share` is `status` (`presence` sends none), when the board differs from the last one it sent (compared by hash, without `ts`), when the stream (re)started or the epoch changed, and once an hour unchanged; the last bound entry going sends one empty board, which clears the allies' copy. A relay that refuses the kind (`unknown-kind`) is logged once and left alone for an hour; nobody is told. `ts` rises by at least 1 per board.
- **Holding allies' boards.** The holder keeps each ally's last board in memory only (the relay gives it back at the next stream). A device that leaves the roster loses its board at once; one offline for more than 2 hours, or whose board is older than 7 days, is not shown. A board never starts a turn, enters the inbox, or reaches a main, a member, or the GUI.

### Opening a main

A tower routes a request to the main that owns it, or to the member doing that work. When no session owns it, the tower no longer returns it to the sender: it calls its own tool, `boss_open_main`, and does not ask the user first. Its other limits stay: it runs no shell command, sends no process signal, and edits no file. The tool is registered in the tower only, takes the request (verbatim, with every user decision it quotes kept verbatim), the sender (intercom name or session id), and an optional tab label, and does this:

1. Resolves the sender to one live session; no live session of that name or id fails before anything opens, because the new main could not report back.
2. Creates one tab in the tower's own workspace, in the workspace's checkout path (the tower's cwd when it has none), with `--no-focus` and `STRAW_BOSS_ROLE=main`. It never switches the user's focus and never types into a pane that already exists. Work for another workspace goes to that workspace's tower with `call_tower`; the tool opens nowhere else.
3. Starts pi in that tab's pane under the Herdr agent name `main-<8 hex>`, with pi's default model (the `towerModel` setting is for towers only). A pi started with `STRAW_BOSS_ROLE=main` joins like any session and then promotes itself as `boss_promote` would: a tab that has a live main refuses it and the pi stays a member with a warning.
4. Waits up to 60 s for that pane to publish `sb_role=main`, then sends the new main one intercom message, under the [header](#talking-between-towers) (`kind=handoff`, `reply=expected`), with the sender's name and session id, the tower's name and session id, and the request verbatim, so its first prompt is the main agent's. The message tells the main to report the outcome to the sender and to the tower that opened it, then wait: the tower closes it ([Closing an opened main](#closing-an-opened-main)).

Limits, counted from live Herdr panes so they survive a tower restart: the tool marks the new pane with a token (`sb_opened_by=<sender session id>`, kept fresh by the opened main) and refuses, with an error the tower relays to the sender, when the workspace already has 2 live mains opened by towers or the sender already has one (opens are serialised, so one in flight counts). A refusal is not remembered, so the same request may be tried again once a main has finished. `STRAW_BOSS_ROLE=main` stays in the new tab's shell, so a pi promotes itself only when the pane also carries the one-time token `sb_open_main`, which the first such pi consumes; a later pi started in that shell stays a member.

Any failure (the start, the wait, the delivery) closes the tab the tool created, nothing having been handed over, and reaches the tower's model as an error that its prompt tells it to relay to the sender. The tower remembers each sender and request for the life of its session: the same request never opens a second main, whether the first attempt is still running, succeeded (the repeat answers that a main was already opened), or failed (the repeat is refused, not retried). A tower restarted in between forgets, and different wording is a different request.

### Before pi starts in a folder: the settings check

pi 1.4.0 reads `<folder>/.pi/settings.json` at startup, whole and with no size limit, before any extension loads and before the trust question (`SettingsManager.create(cwd, agentDir)` with the project trusted by default, in `dist/main.js`; upstream issue [earendil-works/pi#11421](https://github.com/earendil-works/pi/issues/11421)). A link to `/dev/zero` makes pi grow without bound, `/dev/stdin` or a FIFO blocks it for good, and a huge file is read whole. No extension can step in, so whoever starts pi looks first: Straw Boss does it before it creates anything for a new pi (`src/trust/settings.ts`).

- **The probe.** Inspecting the path in the boss's own process always diverges from what the kernel does for pi (`.pi -> /proc/self/cwd` means whoever looks, link targets that are not UTF-8, `/DEV` on a case-insensitive disk, Windows paths), so the kernel resolves it. Cost: one `lstat` of `<folder>/.pi` when there is no `.pi` (`ENOENT`/`ENOTDIR` means no file, no child); when `.pi` exists, one short child process (`process.execPath`, `--max-old-space-size=32`, no input, working directory `<folder>`, the same as pi's). The child first `lstat`s `.pi` and `.pi/settings.json` relative to that directory. With no link involved, `ENOENT`, `ENOTDIR`, or `EACCES` means no file (pi's `existsSync` is false or its read error is caught: `tryLoadFromStorage` in `core/settings-manager.js`); a link it cannot follow or open is refused, whatever the error. It then `stat`s the path, following links, before it opens anything: a directory is fine (pi catches `EISDIR`), and anything but a regular file is `special` and is never opened, so a FIFO's writer is not released and no device is touched. A regular file is opened with `O_RDONLY|O_NONBLOCK`, `fstat`ed again, and read through the descriptor with a fixed buffer, whatever `st_size` says (so `/proc/self/pagemap`, size 0 and endless, stops at once), `large` when more than 256 KB arrive. It prints one JSON line (the parent cuts its output at 4 KB). Any other error, a link loop (`ELOOP`) included, refuses as `unreadable`.
- **What is refused.** A `settings.json` that is not a plain file (a device, FIFO, or socket, or a link that ends at one), one over 256 KB, one that cannot be looked at (`unreadable`), a link the check could not follow or open, whatever the reason (a dangling link is refused too, though pi itself would skip it: a per-process link such as `/proc/self/fd/17` is missing for the check but is pi's own terminal for pi), and one the check did not finish (also a failed start of the check itself): no answer in 5 seconds (the child is killed), a crash, or output that is not the expected line is `unchecked` ("could not be checked in time"). **What is fine.** No `.pi`, no file, a directory at the path, and a plain file of at most 256 KB, also through links. A file swapped for a device or a link between the check and pi's start is not covered; the window is the few seconds of the opening. The look is asynchronous, so the boss's event loop is not blocked; every opening (a new main, member, or base, the tower's tab, an opened main, a pop) refuses before it creates anything. An adopted tower pane that reports no folder is checked as the folder the tower is for (the workspace's checkout, else the opening cwd), since herdr gave nothing better.
- **Bounded stall (SP-R002).** A `settings.json` on a hung network or FUSE mount can stall the read; the child's timeout bounds it, and the opening is then refused as `unchecked`. **Remaining gap.** The child's file descriptors differ from pi's: its `/dev/stdin` and `/dev/fd/0` are `/dev/null`, its stdout and stderr are pipes. A link to `/dev/stdin` or `/dev/fd/N` therefore never shows pi's real descriptor: the child's pipes, sockets, and devices are `special`, and a number the child has not opened is refused as a link it cannot follow. On macOS the child's `/dev/fd/6`, `8`, and `10` are the directory `/`, as pi's are, so such a link is allowed as a directory. The check is wrong only if pi holds a regular file at a number where the child holds something else, which no tab Straw Boss opens arranges.
- **Where it runs.** Every path that starts pi in a folder: the GUI's + New base, + New member (new tab and split), and + Main (`spawn.ts`), the tower's `boss_open_main` (`opener.ts`), a tower's own tab (`towertab.ts`, new or adopted), and a stash pop from the GUI or `/boss pop` (`stash.ts`; every folder of the stash is looked at before the new workspace is made). A refusal comes before the workspace, tab, or pane is created, so there is nothing to clean up; a stash stays under its name.
- **What the person sees.** The deploy panel fails its first step (`create`) and says, in the page's language (zh-TW first, English), that nothing was started, which file, and why; a refused pop shows the same in its dialog. The server's answer carries the facts (`settings: {path, why, size?, limit?, code?}`) and the page words them. A tool or the LLM (`boss_open_main`, `/boss pop`) gets one English sentence with the same path and reason. The upstream issue is named here only, never in the interface.

This guard can be removed once pi fixes #11421. When pi is newer than 1.4.0, check `SettingsManager.create` in its `dist/main.js` (and `FileSettingsStorage` in `core/settings-manager.js`): once it skips an untrusted project's `settings.json` until the trust question is answered, or reads it with a size and file-type limit, delete `src/trust/settings.ts`, its calls in the paths above, and the `deploy_settings_*` messages.

### Closing an opened main

A main a tower opened (`boss_open_main`) tells the sender and the tower when its work is done, then waits; the tower closes it with `boss_close_main`, unless the main says it awaits a boss decision. The handoff message names both (`Sender:` and `Tower:` with their session ids) and says to report the outcome to the sender with `intercom send` and to the tower with `call_tower` (`why: milestone`, no reply); the main prompt repeats it for a tab a tower opened. The tool is registered in towers only and takes a main's intercom name or session id. The tower checks first, from Herdr's view:

- the session is in the tower's own workspace and is a main (`sb_role=main`);
- its pane carries `sb_opened_by`, so a tower opened it: a main the boss opened is never closed by a tower;
- Herdr reports it `idle` or `done`.

Then it asks the main's own extension to quit as `/boss close` does, over the intercom extension channel `straw-boss/control` (the "capable" audience; a message is for one session, `to`; the sender id is self-reported like every pi-intercom identity, so the channel rests on the same-user trust boundary: a same-user process posing as the tower could close an idle tower-opened main, which that user can already do with `herdr pane close`). It does not use the GUI server, which may be stopped, and a bridge's `close` answers only that server. Only a main opened by a tower registers the channel (right after it consumes `sb_open_main`), and so does every tower. The opener is saved in the session with its pane, and only the same pi in that pane restores it: after a `/reload`, `/resume`, or `/fork` there the main writes `sb_opened_by` again and registers the channel again. A pi started anew (`pi --session`, `pi -c`, a restart after `/boss pop`) and a session in any other pane count as the boss's main, which no tower closes, and so does a `/new` session, which carries no opener. A later claim (a pop's) saves its own opener, none, over the earlier one.

```text
{type: "close-main", to: <main session id>, reqId}                              tower → main
{type: "close-main-result", to: <tower session id>, reqId, accepted, reason?, busy?}   main → tower
```

The main decides, and accepts only when all of these hold: the sender is the tower token holder of its workspace, its own pane carries `sb_opened_by`, and nothing running would be lost, checked as a stash checks a session (no running turn, no queued message, no open dialog, no running background monitor, from the bridge's `stashCheck`) plus no subagent still running (pi-herdr-agents' activity files under its session). On accept it answers and then quits the way `/boss close` does: pi shuts down, its tokens are cleared, and its pane closes (an emptied tab with it). A refusal says why. One for something running (`busy: true`) is asked again every 3 s for up to 15 s, since a main sends its done report from the turn that ends right after; any other refusal is final. A main that does not answer within 10 s (a pi-straw-boss without the channel) leaves the tool with an error and closes nothing. After an accept the tool waits up to 30 s for the session to leave intercom and says whether it did.

The tower runs pi's default model unless you set one for it in `~/.pi/agent/straw-boss/config.json` (under `PI_CODING_AGENT_DIR` when that is set):

```json
{ "towerModel": "claude-bridge/claude-sonnet-5-5" }
```

Straw Boss passes it to pi as `--model` whenever it starts a tower, and reads the file at each start, so a change applies to the next tower without a reload. A tower already running keeps its model; restart it (or switch with `/model` in its pane) to change that one.

## Tower dashboard

A tower session with a TUI shows a monitoring widget above its editor. It is read-only: it never takes focus, never prompts, and is shown only while the session holds the tower role (a tower that yields, a headless tower, and main agents never show it). Its first lines say what the pane is, the channel main agents reach each other through with `call_tower`, and give the straw net GUI's link while a GUI server answers (otherwise that `/boss gui` opens it).

```text
╭─ ? 󰐻 Alpha ───────────────────────────────────────────────── head tower ─╮
│ Control tower: main agents talk here (call_tower).                       │
│ GUI  http://127.0.0.1:52662/<token>/                                     │
│                                                                          │
│ this net                                                                 │
│ ├─ tab api-main                                                          │
│ │  ├─ ○  api-main            main                                       │
│ │  │  └─ ⠸ [sub] psb-sleeper  subagent  bash                             │
│ │  └─ ○  docs-member         member                                     │
│ └─ tab other                                                             │
│    └─ ?  ops-main            main      waiting on a question            │
│ other towers                                                             │
│ ✓ 󰐻 Beta                      tower                                      │
╰──────────────────────────────────────────────────────────────────────────╯
```

- **This net**, in detail: the sessions that joined in this workspace, by tab (main agent first, then members), each with the subagents it launched, and this workspace's sub workspaces. Sessions that did not join are not listed, and neither is anything in other workspaces.
- **Other towers**: one line per workspace that has a live tower (workspace, status, and `head tower` for the head one).
- Each row carries the role mark Herdr's sidebar shows (see [Sidebar net view](#sidebar-net-view)), in Nerd Font glyphs one column wide: the radio tower (U+F043B) for a tower and in the title, Font Awesome's star (U+F005) for a main agent and person (U+F007) for a member, and `[sub]` for a subagent. A tab and a sub workspace have none. Their colors are pi theme roles, so they follow the active theme: the tower `warning`, the star `accent`, the person `success`, all bold, and `[sub]` `dim`.
- One glyph and theme color per state: a spinner in the accent color for working, `?` warning for waiting on a question, `◈` in the bold title color for commanding (an idle session whose subagent works or waits), `○` dim for idle, `✓` success for done, `✗` error. Colors come from the active pi theme. The title mark shows the most urgent state of the net.
- The spinner runs at 1 fps, and only while something is working and the tower's tab is on screen (the active tab of Herdr's focused workspace): every frame redraws the tower's whole TUI, and at 8 fps each idle tower burned 5–13% CPU for as long as anything in the net worked (0.33.3). The data is re-read when Herdr reports a change (0.27.0): the dashboard subscribes to Herdr's `pane.*` (created, closed, updated, moved, exited, agent detected), `tab.*` (created, closed, renamed, moved, focused) and `workspace.*` (created, updated, metadata updated, renamed, moved, reordered, closed, focused) events, and a burst of them is one read 0.5 s after the first. An intercom presence, join, or leave event re-reads at once. No two reads are closer than 0.5 s, and a request that comes inside that gap, or while a read runs, is read when it ends instead of being dropped. A poll every 30 s is the safety net: it catches an event that was missed, and what no event tells (a subagent's activity file, which holds the tool it is running), and a reconnection of the event stream re-reads after the same 0.5 s, so a missed event never leaves the screen wrong for longer than that. Shutdown, or losing the tower role, removes the widget, the subscription and every timer.

Where the data comes from: pi-intercom `listSessions()` (status `idle`, `thinking`, `tool:<name>`, and the Herdr location of each session), Herdr's pane list (`sb_role` token, Herdr's agent status where `blocked` means waiting on a question, and the pi session file) and workspace list (workspace status, `tower` token, linked-worktree fields), which one `session.snapshot` request answers together (0.27.0; the snapshot's panes and workspaces are what `herdr pane list` and `herdr workspace list` print). Subagents are linked to their parent through pi-herdr-agents' own layout: the parent's session file names its artifacts directory, `subagent-activity/<child id>.json` there records each child's activity, and the child's pane session file contains the child id. So a subagent is grouped under the session that launched it wherever it runs, and it never counts as a net member of the workspace or tab it sits in. The pane of each child is found by one pass over the panes (their session file names are indexed by child id), the two directories are listed again only when their timestamp changes (a directory changed in the last two seconds is always listed), and a launch script is read again only when it changes.

**How Herdr is read (0.27.0).** The listings (`pane list`, `workspace list`, `tab list --workspace`) are requests on Herdr's socket (`pane.list`, `workspace.list`, `tab.list`), not spawned `herdr` commands; the reply is the same as the CLI's, so every reader is the same. Every write (`report-metadata`, `tab create`, `agent start`, closing, and the rest) still runs the CLI. A listing that fails rejects with Herdr's own error, and nothing falls back to the CLI. The dashboard and the browser view read the panes and workspaces together from one `session.snapshot`. The browser view's poll (every 2 s while a page listens) stays a poll: its net also holds what only the session files and intercom know (what a unit waits on, its queue, its dialogs), which no Herdr event tells.

## Orphaned subagents

A subagent's result reaches the session that launched it only while that session's own process keeps pi-herdr-agents' watchers and its registry of launched children (`runningSubagents`, in the process-wide slot `globalThis[Symbol.for("pi-subagents/runtime")]`).
`/reload`, `/new`, `/resume` and `/fork` keep them, quitting pi suppresses the delivery, and a crash or restart drops them for good: pi-herdr-agents does not recover watchers after a full restart.
A subagent that stays open after it finished, an interactive one for instance, is then stranded: it sits done in its pane and nobody is told.

Every session in Herdr that is not itself a subagent checks for this every 15 seconds.
While no subagent of the session is stranded, a check reads the registry and one directory; only a subagent that is not tracked and whose own activity says it waits brings a pi-intercom session listing, and after that one `herdr pane list` per check (and one `herdr pane process-info` when it is about to be asked).
A subagent is asked to report when all of these hold:

- **Its launcher no longer tracks it.** Its id is not in that registry. When the registry cannot be read (pi-herdr-agents is not loaded, or no longer keeps it there) nothing is known to be lost, so nothing is sent.
- **Its result is not in the launcher's transcript.** No `subagent_result` or `subagent_ping` message names the child's session file.
- **It has finished.** Its activity file says `waiting` (it ended its turn), its pane runs pi and Herdr says `done` (or `idle`, which a pane becomes once someone has looked at it), and pi-intercom says the session in that pane is `idle`. A child that works, waits on a question, or has not started is left alone.
- **It was found so twice in a row,** 15 seconds apart, so that a delivery just going out is not taken for a lost one.
- **Its pane runs the child itself.** The foreground processes of the pane (`herdr pane process-info`) include the launch script this session wrote for that run, `artifacts/<session id>/subagent-scripts/<name>-<run id>.sh`. A pane that only reuses the run's session file, such as a run another session resumed or a pi someone started on that file, is not the child, and neither is a pane whose processes Herdr does not list.

Straw Boss then sends that session one intercom message: the launcher's session id and name, and the request to send its final report to that session through intercom and stop.
The launcher shows a notification.
It sends at most one message per run, where a run is a child id: its activity file is named after it, and the child's own `/reload` starts that file again, so its creation time says nothing about a run.
The run is written to the launcher's session (a `straw-boss` entry with a `nudged` key) before the message goes out, so a restart does not repeat it, and a send that fails is shown as a warning and not tried again.
A child whose pane cannot be found or does not run its launch script, or that has no pi-intercom session of its own, is given up on after four looks, until the next session start (a reload counts).
A subagent whose process has exited cannot be asked; its result stays in its session file.
A resumed run (`subagent_resume`) has an id of its own that nothing in its pane's session file names, so it is never found and never asked.
The subagent's own launcher does this, not a tower: only the launcher's process knows what it tracks, so a tower never nudges the subagents of other sessions, and a subagent that launches subagents of its own does not (it runs no Straw Boss).

### Subagents a Herdr restore brought back plain

The nudge above needs the child to still be what pi-herdr-agents started. A Herdr restart does not leave that: with `resume_agents_on_restore` (on by default) Herdr starts a plain `pi --session <file>` in every pane that had reported an agent session, subagent panes included.
That pi has none of the child's setup (no `subagent-done.ts` extension, no `PI_SUBAGENT_*` environment, no `caller_ping`, no auto-exit, no `<session>.exit` sidecar), so it sits idle at its prompt with the task unfinished and will never report, and the restored launcher's registry is empty and is never filled again.
Nothing can ask it to report by itself, so the launcher resumes the run instead, through pi-herdr-agents' public `subagent_resume`.
The same check every 15 seconds (`restored.ts`) finds such a run when all of these hold. It lists Herdr's panes only while some run could still be noted or found: a run that can never qualify (a persistent specialist, or a launch script that is missing or does not name the run's own session) is dropped before that, so it costs no list and no process look.

- **The launcher does not track it, and its result is not in the transcript.** As for the nudge: its id is not in the registry, and no `subagent_result` or `subagent_ping` names the child's session file. It is not a persistent specialist (`PI_SUBAGENT_PERSISTENT=1` in its launch script), which pi-herdr-agents cannot resume.
- **It never ended.** There is no `<session>.exit` beside its session file, and Straw Boss has not acted on it before (no `resumed` or `nudged` key for it in the `straw-boss` session entries).
- **Its pane is the restored one.** The launch script's header (`# Session:` and `# Surface:`) names the child's session file and the pane it ran in, and a restore keeps pane ids. Herdr lists that same pane with agent `pi` on that session file, `idle` or `done`.
- **A restore happened.** While the child runs as pi-herdr-agents started it (its pane's foreground runs the launch script), the launcher notes the pane's `terminal_id` in its session (a `straw-boss` entry with `seen` and `terminal`). Herdr gives a restored pane a new terminal while the pane id stays, so the pane counts only when its terminal differs from the noted one. A pi someone started by hand in the same pane (same terminal), a run never seen running (the restart came before the first look), and a Herdr that reports no `terminal_id` are all unknown, and unknown is never closed.
- **Nothing else runs there.** `herdr pane process-info` lists exactly one foreground process whose argv0 is `pi`, and every other process has a readable argv with no launch or resume script (a path with `/` or `\`). A pane that still runs the launch script is the nudge's case; a run another session resumed sits in a pane of its own and runs a resume script; none of them is touched. On Windows the list cannot prove the absence of the script, so a pane there is never taken for restored.
- **The launcher is no subagent itself, and the run is an ordinary one.** A session with a `.pi-herdr-subagent-policy.json` beside its file (a restored nested subagent) does nothing. The child's own policy sidecar decides: `persistent` runs are left alone, and an owner other than `public` is handled as a worktree run.
- **It was found so twice in a row,** 15 seconds apart, because a pane may still be coming up after the restart. A run with no such pane is given up on after eight looks, until the next session start.

Then, in this order: a `closing` key for the run is written to the launcher's session, the restored pane, and only that pane, is closed with `herdr pane close` (the old pi must not hold the session file beside the resumed one) and Straw Boss waits up to five seconds for it to be gone, and the launcher gets one custom message; once the session has taken it, a `resumed` key is written. A reload or quit between the close and the message leaves `closing` without `resumed`: the next instance of the launcher finds the run, sees that its pane is gone, and sends the message then. If the pane is still open, the close never took effect (the process died first): the `closing` key is taken back (an `unclosed` key in the session, so a reload does not read it again) and the run goes through the proof of a restore from the start. A run that then can no longer qualify (no restored pane, the same terminal, not a plain pi) is counted as a miss like any other, and when the eighth miss gives up on it one warning names its session path.
The message names each run with its `sessionPath` and name, quotes the follow-up to pass (finish the task you were given, and report your result), and tells the model to call `subagent_resume` once per run (with `autoExit` false for a run launched with `PI_SUBAGENT_AUTO_EXIT=0`); the resumed run then reports as a normal `subagent_result`.
It is a steering message that triggers a turn, the way pi-herdr-agents delivers `subagent_result` itself and the way a tower run is driven: an idle launcher wakes at once and a busy one gets it at its next step.
Straw Boss does not call the tool, import pi-herdr-agents, or write a result for the child: whether and how the run is resumed stays pi-herdr-agents' and the model's.
A launcher that is a tower does none of this (a tower is driven by the server's queue, not by messages of this kind).
Each step that fails is shown as a warning, recorded as `gaveUp`, and not tried again: a pane that cannot be closed (or stays open) is not resumed, and a message that cannot be put into the session is shown with the sessions it would have named, so they can be resumed by hand.

A **managed-worktree** run (it has a manifest under `artifacts/<session id>/worktree-runs/`) is the exception. Its pane is the root pane of the retained worktree workspace, so Straw Boss does not close it, and pi-herdr-agents' `subagent_resume` neither reattaches the worktree's lifecycle nor accepts such a session. The message says so, names the pane, worktree and branch, tells the model not to call `subagent_resume` for it, and leaves the restored pi waiting at its prompt for the user to continue.
Not covered: a run that was itself resumed (`subagent_resume`) is not recovered by a second restart. Its resume script is named `<name>-resume-<time>.sh` and its header (`# Session:`, `# Surface:`) does give the session file and pane, but not the run's id (that is only in the script's command, as `PI_SUBAGENT_ID`), and the id is what every other proof here hangs on. The resumed run reuses the original session file, whose name carries the original id, so the pane and the transcript cannot be matched to the new id (`ownFile`), and the original run's `subagent_result` names the same session file, so the transcript cannot say whether the resumed run finished. Covering it would mean closing a pane on a guess, so a restart after a resume stays unknown and nothing is closed; and a `.exit` sidecar left unconsumed means the child finished, so the run is left alone and its result has to be read from the session file.

## Browser view

`/boss gui` shows the whole net in your default browser: a game-style map, live and animated, where you can read any unit's comms and type into its session.

![The browser view](straw-net-gui.png)

- **Any session can open it**, in a Herdr workspace or a sub workspace, joined or not. It changes no role and writes no token; a joined session reads the sessions through its tab channel, and one that cannot join (a sub workspace) through a channel of its own (`straw-boss/view/<hex of the pane id>`, never owner-eligible) that takes no part in any tab. Outside Herdr the extension is inactive, so there is no command.
- **What it shows.** Each workspace the net reaches is a **base**: one with a live tower or with sessions that joined. Workspaces with neither are not shown, and neither are sessions that did not join. A base has its **control tower** (the head tower wears a crown; a base without a tower shows a dim ghost), each tab's main agent and members as units, subagents under the session that launched them, the tower's own under the tower (linked exactly as the dashboard does, wherever they run), and sub workspaces as **outposts** under their parent. Each unit's card says how long it has been in its state (once the server has seen it take that state), its todo list in short (done of total and the task in progress, from rpiv-todo, relayed by the session's bridge), and its last steps as a row of marks along its foot. Under the map, a **timeline** marks the net's joins, leaves, and state changes of the last 30 minutes (after [zoetrope](https://github.com/furkankly/zoetrope)'s): waiting and errors on top, work in the middle, the rest below, each named on hover and a link to its unit; the server keeps them, so a page that reloads still has them, and a phone folds the strip to its newest event. The bases pack like masonry in reading order; while the map runs past the window, an overview in the corner shows each base in its state's colour and scrolls where you click. The palette follows Tokyo Night.
- **States** look the same everywhere: working is a spinning ring (and a spinner badge), waiting on a question an amber `?` that hops with a pulsing ring, idle a dim `z`, finished a green `✓`, error a red `!`. Changes animate; the page honors `prefers-reduced-motion`.
- **Routes.** The map is `/<token>/`.
  A base opens as `/<token>/w/<workspace id>` and a unit as `/<token>/w/<workspace id>/s/<session key>`, optionally with `?at=<entry id>` to open its comms at one entry.
  Links are real links (middle-click and copy-link work); a plain click, Back, and Forward change the view without reloading, and Escape goes up one level.
  The **Straw Net** title in the header goes back to the map.
  A deep link loads straight into its view.
- **A base, zoomed in.** The workspace route draws the base large on the map's grid: its control tower, each tab as a squad of unit tokens with the same icons and state badges, subagents tethered under the unit or the tower that launched them, outposts, and the workspace's other pi panes as unaligned units (outside the net, grey, with a dashed ring).
  Each unit shows its last assistant line, read from the end of its session file.
  Entering a base zooms out of its spot on the map.
- **A unit's comms.** The session route shows the session's chat as a comms log: your messages in gold on the right, the unit's transmissions on the left with its icon, each tool call as a collapsed action card with a state badge (running, done, failed), thinking folded behind its length, compactions as dividers.
  The side column shows the unit's dossier (portrait, role, state, model, context use, directory, base, squad, launcher, dispatched subagents).
  Its **Terminal** button opens the unit's **terminal mirror** as a tile beside the comms: what its pane shows, with colours and attributes, updated within a second while it changes (at most 4 reads a second, shared by every page that shows it, and none while no page does). On a phone the mirror is display only: typing or tapping in it sends nothing. The server keeps only colour and attribute escapes in what it sends, and the page builds the rows from text. **Fit width** scales it to the tile and scrolls to the bottom, where pi's editor is; otherwise it keeps its size and scrolls sideways, as on a phone. While the session waits for a secret (`secret_drop`) nothing is read and the tile says so; a tile pauses 5 s after its browser tab is hidden and resumes when it shows. A read-only question panel offers **Show terminal** too. Under the mirror, the **key pad** sends one key per tap: `esc`, `tab`, `⇧tab`, the arrows, `enter`, `space`, `⌫`, `home`, `end`, `pgup`, `pgdn`, and `1`–`9` (folded away). It has no letters, `/`, Ctrl, or Alt, and the server refuses them as keys; it works only while the tile shows the terminal live (a frame in the last 3 s), at most 8 keys a second, and only Escape while the session waits for a secret or on a question its panel answers; a paired device likewise sends only Escape, and no prompt, while a `link_request` is open. Before **enter** the server asks the session what Enter would submit; a command that ends or replaces the session (`/reload`, `/new`, …, recalled from history too), another `/` or `!` command, or an editor it could not read asks to confirm first, and so does a second Escape within a second on an idle session, which opens pi's tree (or fork); the confirm puts the focus on Cancel.
  On a desktop (a fine pointer) a click into the mirror gives it the keyboard until a click elsewhere (0.24.0); a drag that selects text to copy does not, and since 0.25.0 switching the session view to its terminal does it once. On a phone nothing takes the keyboard by itself, because a pane is not a text field and a tap into it opens no soft keyboard: the terminal's **Keyboard** button (鍵盤) focuses the same invisible text box, which opens the soft keyboard (a second tap, or leaving the terminal, closes it), and what it types goes out as text (an input method's composition as one write when it ends), with Backspace and Enter read from the soft keyboard's `beforeinput` where it sends no key for them. Switching to the terminal also makes the composer's box let go of the focus, so keys never land in the hidden chat. A ring sweeps out from its edge as it takes the keyboard, the edge stays lit, each key flashes it, and the bar above says so. The keys land in an invisible text box by the mirror's corner, so an input method shows its candidates there. What goes, all on the same `keys` endpoint and under the same guards:
  - the pad's keys by their own key (arrows, Enter, Escape, Tab, Shift+Tab, Backspace, Home, End, Page Up, Page Down), and Delete as its sequence;
  - Ctrl or Alt with a letter, Alt+Enter, Alt+Backspace, and Ctrl or Alt with ← or →, as Herdr names them (the letter from the key's position, since Alt on a Mac types å for A). Ctrl+Z never goes: pi would stop in the background, where nothing here brings it back. Ctrl+D asks first (it leaves pi on an empty editor), and so does a second Ctrl+C within a second (pi leaves on the second). ⌘ stays the browser's, and so do Ctrl+V and Ctrl+C on a selection off a Mac;
  - characters, `/` and `!` and an input method's text included, as typed text (`{text}`): one raw write of 1 to 64 printable characters, so no line break, tab, or escape sequence rides along and Enter still comes alone and asks first;
  - a paste as one paste (`{paste}`): up to 4,000 characters with line breaks and tabs but no other control character, which the server wraps in the terminal's bracketed-paste markers, so pi takes it as a paste and a line break in it submits nothing.
  Writes go one at a time, at most one every 130 ms, under the same 8 a second; characters typed meanwhile join the next write, a held key repeats only into an empty queue (never Enter, Escape, Tab, or a chord), and a refusal or a confirm drops what was still queued. Since 0.25.0 the pad's buttons join the same queue: a press while a write is on its way waits its turn, and the buttons stay enabled meanwhile, so they no longer flicker as you type. Escape goes to the pane, not to the page. While the session waits for a secret only Escape goes; otherwise nothing.
  New entries appear when pi writes them; text still being streamed is not in the file yet, so it shows at the end of the reply.
  The log opens at the newest entry and stays pinned there as new ones arrive.
  Scrolled up, it stays where you are and a floating button offers the way back (**jump to latest**, or **N new** once entries arrived); the button scrolls to the end and pins the log again.
  Older pages load as you scroll up; at most 600 entries stay in the page.
  An assistant message's header names the unit's role (tower, main agent, member, subagent) with the model and the time, not the session's name, which the page header already shows; a message relayed from another agent still names its sender.
  Under the log, the **composer** types into the unit's terminal through Herdr, as if typed there: **Send** (Enter; Shift+Enter adds a line, off while the box is empty) sends a prompt when it is idle and a steering message while it works, **After this** (Alt+Enter, shown while it works) queues one for when the current task is done, and **Stop** sends Escape after a confirm. While the box holds only `/` and a name being typed, a menu above it lists the session's commands that match (extension commands, prompt templates, and skills, as its own pi lists them; pi's built-in commands are not listed): ↑ and ↓ move, Enter or Tab or a click puts `/name ` in the box, and Escape closes it. The session's dialog bridge answers the list, so it is the session's own set, and the menu shows nothing when it does not answer within a second. A **closed channel** takes no typing: the box is disabled and says why ("This session is no longer live; its history stays readable."), the comms head shows "channel closed", and the server refuses input and keys to it (409 `not_live`). A channel is closed when its session left the net, or when it is a finished subagent that no pane runs pi for any more (its pane is gone or back at a shell); a finished subagent whose pi still runs (an interactive one, not auto-exited) keeps its composer, on a paired device's page as on this computer's.
  A leading `/` or `!` runs a pi or shell command; commands that end or replace the session (`/quit`, `/exit`, `/new`, `/resume`, `/fork`, `/clone`, `/import`, `/reload`) ask first.
  Text lands after anything still unsent in the terminal's editor and is submitted with it.
  The box clears only once Herdr confirmed the input, keeping anything typed meanwhile; a send that was not confirmed is never repeated (check the terminal). What the page could not say when the answer came (you were on another session, or the page reloaded) is kept and shown when you come back: why a send was refused, that it was not confirmed, or, if you edited text that had already been sent, that the original already went. It never says "your edits stayed" about an empty box (the browser refused storage).
  It is disabled, with the reason, while the stream is down, the session is gone, or it waits on a dialog (answer that in the panel above it when it can be answered there, else in the terminal).
  Subagents are typed into directly, like any session. Ctrl+C and Ctrl+D are never sent from the browser.
  On a touch screen Enter adds a line and Send sends; drafts survive a reload.
  Markdown is rendered by the page's own renderer into DOM nodes, never as HTML, and only `http`, `https`, and `mailto` links are links; block quotes and lists nest at most 16 deep, and deeper levels stay text.
- **Alerts and panels.** Only a unit that needs you to answer raises the prominent alert: one waiting on a question or a dialog (mark waiting, or a pending dialog). A unit that fails (mark error, or a monitor that failed or went quiet) and a subagent that finishes are **notices**: they never take the header's alert, queue a dialog, or steal focus.
  An alert never opens anything by itself: it joins the queue in the header (questions first, then notices, oldest first in each), and leaves it again when the unit moves on. The header's alert, Space, and the dialogs' queue count hold questions only; notices wait under a **Notices** button beside it (named Done before this change, when only finishes were there and errors ranked with questions), shown only when there is one, and tinted red while one of them is a failure. A notice raised before the page opened is not news. Map and unit marks still show the error colour.
  You open alerts from the queue or by clicking a unit that waits; they open as dialogs in the dock over the side column.
  A second dialog you open stacks on top, with the one beneath peeking out; click the part that peeks out to bring it up (a click that really lands on a control under the strip, such as the Phone button, goes to that control). A dialog you are reading is never covered by one you did not open: alerts only queue, and the overlay model puts any open without your action beneath the top dialog, without focus (no such open exists yet; it is the rule for later arrivals). Closing the top reveals the one beneath, and with none beneath, the next queued question or error.
  **Later** puts the alert back in the queue and opens nothing else; if the unit moved on while its dialog was open, the alert is stale and leaves instead. A dialog is never closed under you: if its unit leaves the net while it is open, the dialog shows **gone** ("left the net"), without its question or Open comms.
  The queue is counted the same way in the header (its tooltip) and in every dialog ("Also queued: 1 needs you · 1 finished"): questions and errors need you and are what closing a dialog reveals next; a unit that only finished waits in the queue for you to open it and is counted apart.
  **Open comms** goes to the unit's comms at the entry the alert was about (read when the alert arrived: the reply with the tool call it waits on, else its last reply), loading older pages when needed, and lights that entry for a moment; the comms log stays there with **jump to latest** until you go down. It closes the alert without opening the next queued one, so nothing covers the comms you went to.
  The entry is in the URL (`?at=`), so Back, Forward, and the link itself land on it again; an entry no longer in the history opens at the newest one, as does opening a unit any other way.
  Escape closes the top dialog only, focus returns to where it was, and dialogs are not modal (the page stays usable, nothing traps focus).
  Documents open as **tiles** beside the current view instead, sharing its width; a tile that arrives by itself takes no focus, and narrow windows show tiles as tabs.
  A dialog shows the unit, its last line, and the tool call it waits on, with a link to its comms.
- **Questions and selectors.** When a unit waits on a dialog, its alert dialog and its session view (above the composer) show it. Four kinds can be answered from the page (the first two since 0.6.0): pi-robot-hand's selector (`robot_hand` ≥ 0.3.0: its title as written, each choice with where it acts and the terminal's number, **Copy command**, which copies through the browser and answers nothing) and @juicesharp/rpiv-ask-user-question's questionnaires (`ask_user_question`: one to four questions, each with its header tag, options with descriptions as radio buttons or, when it takes several, checkboxes, "Or type your own answer", and "Note (optional)"), and pi-code's hook gate (its confirmation before a gated tool call, such as "Allow bash?": **Allow** or **Deny**, for a call of any tool, such as bash or edit), and any extension's own `ctx.ui.select` or `ctx.ui.confirm` (see **Any extension's select and confirm** below). **Send answer** goes to the package that opened the dialog, which settles it exactly as a terminal answer would, so the terminal's dialog closes and the agent gets the answer once; the panel then says "Answered.", or "It was already answered in the terminal." when the terminal was first, the owner's reason when it refused (still answerable), and "Not confirmed. Check the terminal" with **Check again** (which resends the same answer, never a new one) when no confirmation came. A question is answered from the keyboard alone (`gui/askkeys.ts`): a dialog opens with the focus on its first question's chosen or first option instead of Open comms, the arrows move between options (a single choice selects as the focus moves; a multiple choice only moves, and Space toggles), Tab and Shift+Tab move between questions (from the last one on to its own words, its note, and Send), and Enter, or Space on a single choice, confirms an option and goes on to the next unanswered question and then to Send, where Enter sends; Enter in the own-words box does the same, Shift+Enter breaks a line there, and Down past a question's last option reaches its box. While the focus is in a text box the page's own keys are off, Escape excepted. A choice that acts on this computer (robot_hand's clipboard) is offered on a paired device's page too, with the note that says where it acts, and accepted from it. No key is sent and the screen is never read: each session's dialog bridge (`src/bridge.ts`, in every pi in Herdr, subagents too) relays the dialogs its packages publish on pi's event bus to the GUI server's session over an intercom extension channel only that session may own, and the server lets the page answer a dialog only when it is the session's one open dialog, belongs to one of the session file's open calls (the call of the owner's own tool, or for the hook gate the call it names, whatever the tool), and matches what the page showed (dialog id and digest; see [Answering pi dialogs](specs/2026-10-18-dialog-answers.md)). Everything else stays read-only with the reason and **Show terminal**, which opens its screen on the page: `ask_user` (pi-ask-user), several open dialogs (the page says so only when the bridge relays more than one, or when the one it relays names no open call; a session whose last message left several calls unanswered is answerable while its one relayed dialog names one of them), an answer already on its way, a dialog too long to relay, or one that differs from the session file. `secret_drop` is never answerable from a page (SB-F001): a secret is entered in the terminal only. pi-intercom identities are self-reported, so a same-user process could pose as the asking session's bridge, relay a secret dialog under its own key, and receive the value the page seals to it; until intercom can verify who a bridge is, the bridge does not relay a secret dialog at all (no label, steps, destination, or key leave the session) and refuses any answer to one, and the server takes no `value` from any request (400 from this computer's page, 403 from a paired device) and sends none. The panel is a read-only wait on every page, with no field and no Show terminal (the mirror stays hidden and the key pad Escape-only): this computer's page says a secret is entered in the terminal only, and a paired device's page words it as "For security, entering a secret is not supported remotely" (安全考量，遠端不支援); both name the terminal. The encryption (`src/seal.ts`: X25519, HKDF-SHA256, AES-256-GCM bound to the dialog, its digest, the answer, and the bridge) stays in the tree for the day the path comes back, and the spec says what blocks it ([Answering pi dialogs](specs/2026-10-18-dialog-answers.md), "Why a secret is terminal only"). The `secret_drop` call itself is still shown in a device's comms history with its arguments (label, steps, and destination) as any tool call is; the value never is. Beside another open dialog the unit shows only that it waits for a secret. A unit with an open dialog counts as waiting at once; otherwise it is waiting while Herdr reports its pane `blocked`, which pi reports from the `herdr:blocked` event; Straw Boss's extension entry `src/blocked.ts` relays rpiv's `rpiv:ask-user:blocked` into it, once per open questionnaire, and pi's own dialogs too (see [Blocked dialogs](#blocked-dialogs)). The question shown is the newest unanswered call on the session's current branch (for a hook gate answered among several open calls, the call it gates); a call longer than 256 KB is read from further back in the file (up to 16 MB, shown clipped), and a longer one says it is too long to read.
- **Any extension's select and confirm.** Every extension's `ctx.ui` is one object, the runner's `uiContext`, so Straw Boss (`src/intercept.ts`, in every pi in Herdr, subagents too) replaces its `select` and `confirm` and leaves `input`, `editor`, and `custom` alone (a secret may be typed there). A wrapped call opens pi's own terminal dialog exactly as before and, in the same call, publishes the dialog on pi's event bus as a dialog-contract v1 owner under `straw-boss:ui` (`pending`, `answer`, `answer-result`, `closed`; adapter `uiPrompt` in `src/owners.ts`), so the bridge, hub, and answer route handle it like any owner's dialog and every existing check applies (one open dialog, the digest, an answer already on its way, `secret_drop` open, too long). A `select` is relayed with its options; a `confirm` as one dialog whose text is its title, a blank line, and its message, with **Yes** and **No**. The first answer wins and the other side is dismissed: an answer from the page aborts the terminal dialog through its `signal` (combined with the caller's own) and the extension's call resolves with that answer (the chosen option, or `true` for Yes and `false` for No), once; an answer in the terminal closes the page's dialog (`stale`, answered in the terminal). The dialog is never made worse: a call that cannot be relayed, or whose relay fails to start, is the original call with nothing left behind, and a dialog that throws or rejects passes its error on unchanged.
  - *When it binds.* A dialog is relayed only while exactly one tool call is in flight, and it binds to that call (an `mp-infra` hook's confirmation inside a bash `tool_call` handler is the case that motivated it; the hub then needs the call among the session file's open calls, as for pi-code's gate). The page words it as "opened while {tool} was running", since it may be unrelated to that call. With no call, two or more calls, or a `secret_drop` in flight, it stays in the terminal; so does a call whose tool has a contract owner (`robot_hand`) when the owner relays nothing. Text the page shows has Unicode format characters (bidi overrides, zero-width marks) drawn as U+FFFD. Only the outermost dialog is relayed (`input`, `editor`, and `custom` only count, passing through untouched; the count resets at `agent_end` and when pi swaps its ui object): a dialog that opens while another is open withdraws the relayed one (the page could not tell which dialog an answer would dismiss) and is not relayed itself. A `select` over 100 options, or a title and options over 12,000 characters, are not relayed.
  - *Owners win.* A dialog with a contract owner (`robot_hand`, pi-code's gate) is relayed by its owner, and the intercepted twin on the same tool call is dropped, whichever opened first (`twin` on the adapter; the rule is in `src/bridge.ts`). `ask_user_question` opens its questionnaire through `ctx.ui.custom`, which is not wrapped.

- **Project trust** (design record `docs/specs/2026-10-26-project-trust.md`). - **The server** runs in one session at a time, the one that opened it or a survivor that took it over (see One server per machine), on `127.0.0.1` with two random free ports: the local listener, for this computer's browser, and the remote listener, the only target `tailscale serve` is pointed at. Which request is local is decided by the listener it arrived on, not by what it says about itself: a request on the remote listener is remote whatever its `Host` or headers say, and the local listener lets in only a request with `Host: 127.0.0.1:<port>` and none of the forwarding headers `tailscale serve` adds (`X-Forwarded-*`, `Tailscale-*`, `Forwarded`, `Via`), and refuses the rest with 403 (a second guard). Every URL starts with a random token (`http://127.0.0.1:<port>/<token>/`); a request without it or with another `Host` header is refused with 403, so other local pages cannot read the net. The only writes are POSTs under `/<token>/api/sessions/<key>/` (`input`, `keys`, which takes one key pad key from a page that shows that terminal live, or Stop's Escape, `focus` (not offered by the page since 0.14.0: from a browser it changed nothing you could see), `commands`, which asks the session's bridge for the commands that match a typed `/name` and calls no Herdr method, `answer`, which carries a dialog's answer to its owner and sends no key, and `mirror`, which shows the pane's screen on the page's own stream), plus the ones only this computer's page may send (403 from a paired device): `server/stop`, `remote/pair` (a new one-time pairing code: pairing is the desktop's), `remote/on`, `remote/off`, `remote/devices`, `remote/unpair`, and `remote/unpair-all`, and `/<token>/api/dismiss` (one finished subagent, or `all`); each needs the page's own `Origin`, `Sec-Fetch-Site: same-origin` when sent, a JSON body of at most 64 KB, and the CSRF secret written into the page, and for `input`, `keys`, `focus`, and `answer` the server asks Herdr right then that the pane still runs pi on that session's file (a mirror checks it before its first read and every 2 s, and starts afresh when the session moved to another pane). Typed text is never logged. The page is a built static bundle (`dist/gui`); any route answers the same page, which carries a `<base href>` so it loads from any depth. The stream (`/<token>/events`) names itself first (`hello`, a random id the page attaches terminal mirrors to; a server that has not read the net yet names it after its first reading), then sends the full snapshot on connect and on every change, a `ping` every 15 s, and a `problem` event when Herdr or intercom cannot be read; `events?watch=<session key>` adds that session's history, and `events?watch=w:<workspace id>` the last line of each unit there. `/<token>/api/history/<key>` and `/<token>/api/entry/<key>/<entry id>` page through a session and fetch one entry in full (capped at 1 MB). Documents are served by capability, a random 128-bit value the server gives each listed document, never by path: `/<token>/doc/<cap>/` is an HTML document (at most 2 MB) with each `cgi-bin:pi-answer` form pointed at a one-time nonce (30 minutes, bound to that document), `/<token>/doc/<cap>/<file>` an image, stylesheet, or font under the document's own directory (at most 8 MB, no `..`, no symlink out of it), `/<token>/doc/<cap>/answer/<nonce>` one form answer (at most 64 fields, 16 KB of query, 12 KB of answer, no control characters other than tab and line breaks), and `/<token>/api/doc/<cap>` a text document as JSON. Only documents a session lists now are served. Every `/doc/` response carries a CSP `sandbox` without `allow-scripts` or `allow-same-origin`, and its sources name the server's origin (WebKit does not match `'self'` in a sandboxed document); the app may frame only its own pages and sends `Cross-Origin-Opener-Policy: same-origin`. The rewrite also drops a document's own `<base>`, referrer policy, and its buttons' `formaction`, `formmethod`, `formtarget`; that is a best effort on HTML text, and the sandbox and policy are what hold. While a page listens the net is read every 2 s; with none it is still read every 10 s, so the timeline keeps what happened while a phone slept (before 0.42.7 nothing was read then, and a page that came back after a minute found a fresh start with no events). The page is installable as an app (0.42.2): the bundle carries `manifest.webmanifest` (its `id`, `start_url`, and `scope` are `./`, so they resolve under the token path), PNG and SVG icons, and `apple-touch-icon.png`; the page's policy adds `manifest-src 'self'` and links the manifest with `crossorigin="use-credentials"`, so a paired device's cookie goes with it. There is no service worker: every page comes from the running server's own build.
- **Session files.** The server reads only the session files of units in the net it just read (joined sessions, towers, subagents through their pane or launch script, and the other pi panes of a base); a path never comes from the browser. A file is read only from a pane running pi, only as a `.jsonl` under pi's sessions directory (`sessions/` in `PI_CODING_AGENT_DIR` or `~/.pi/agent`, symlinks resolved on both sides), and for an intercom session only when it is named for that session, so a net read during `/new` cannot pair the old session with the next file; a watched session whose file changes re-attaches to the new one. A file is indexed in 1 MB chunks from the first and last bytes of each line, about 25 ms for a 54 MB session, and only the index stays in memory; entries are read by offset for the page being sent. Indexing, appends, and reads run one at a time in order, so entries pi writes during the first index wait for it, and a read never uses the index of a file that was replaced. A rewritten file or a branch move resets the page. A first page that cannot be read is tried again on the next net reading. A unit that leaves the net stays readable for ten minutes, with a link to the pane's new session when there is one. A session file is opened without following a symlink at its last step (`O_NOFOLLOW`): a file swapped for a link after the net resolved its path is not read. Where the platform has no `O_NOFOLLOW` (Windows) the link is looked for just before the open, which leaves a short window between the look and the open; a process of the same user that can swap files in pi's sessions directory can use it to make the GUI show another `.jsonl` under that directory, and only the user and their paired devices read the result.
  Sessions stored elsewhere (`--session-dir`, `PI_CODING_AGENT_SESSION_DIR`, or pi's `sessionDir` setting) show on the map but have no history and cannot be typed into.
- **Remote access.** `/boss gui remote`, from any pi session, asks the sb server to put the GUI on your tailnet: it adds one `tailscale serve` entry, HTTPS on port 8443 proxying to the server's remote listener (never Funnel, and never the local port), and the session shows a QR code in a pi overlay, drawn here from the server's answer, so the QR and its one-time links never reach the server's log or the model's conversation. Scan it with a phone signed in to Tailscale as this machine's user (or, in an installed app, type the short code printed under the QR: see **The installed app's entry** below). In the overlay, **c** copies a link and **o** opens one in this computer's browser (a session in a desk stack, `STRAW_BOSS_DESK=1`, has no **o** key and lists none: the shell shows the page itself); every QR, copy, and open is its own one-time link that works once, within ten minutes, and **Esc** or **q** closes it. While the overlay is open the session counts as waiting, so input from the browser is refused rather than lost in it. The HUD's **Phone** button shows a fresh QR in the page too; it shows only on this computer's page (127.0.0.1), not on a paired device's (0.25.1), and not in a desk window ([Desk mode in the page](#browser-view)). A paired device gets a session cookie (HttpOnly, Secure, SameSite=Strict, 90 days, scoped to the token path) and stays paired until the desktop unpairs it, the GUI gets a new token (a pairing belongs to the token: a restart keeps it, but a taken port, a missing or corrupt `gui-secrets.json`, or `/boss gui rotate` makes a new one and needs a new QR), this machine's Tailscale identity (host or login) changes, or 90 days pass without a use; every use renews it, and the response then sets the cookie again (the stored expiry moves at most once an hour). The server keeps only the cookie's SHA-256, with the device's name (platform and browser, read from its User-Agent when it paired), when it paired and when it was last used, in `paired.json` (mode 600) beside `gui.json`; it survives remote off and on and a restart of the server, but a new GUI token unpairs every device, because their cookies are scoped to the old token's path and could not connect anyway; the identity and the wish to have remote on stay, the log says `devices-cleared`, and a phone scans a new QR code (see [One GUI per machine](#browser-view)). Every remote request arrives on the remote listener and must also carry this machine's Tailscale user in `Tailscale-User-Login`, which `tailscale serve` sets, and the exact MagicDNS host. Secrets are entered only on a page of the local listener, so a proxy that dropped its forwarding headers, or a serve entry that still points at the local port, cannot turn a remote request into a local one. A document's own requests (`/<token>/doc/…`) need that identity and the document's capability but not the cookie, because Chrome withholds a SameSite=Strict cookie from a sandboxed frame's requests: on the tailnet, a device of the same Tailscale user that holds a document's link can read it and answer its form without pairing. Port 8443 is taken only when it is free or already this server's, including an entry from before the remote listener that points at this server's local port: turning remote on (or the page's Turn on remote access) points it at the remote listener, and if Tailscale does not take the change, remote stays off with "tailscale serve did not take the entry as asked" and nothing is recorded, so a request through the old target is refused 403 by the local listener rather than served as local. An entry that points anywhere else is never touched. Turning remote off, and starting a server that does not resume remote, remove the old-target entry; a server started with remote wanted on repoints it to the remote listener instead (the same "free or already ours" rule), and removes it only when it stays off. `/boss gui remote off` (or **Turn off remote access** in the Phone tile of this computer's page) removes only that entry (other serve entries are never touched), ends every remote stream, and forgets that remote was wanted; the paired devices stay paired. `/boss gui stop` does not touch it (the entry points at the remote listener, which stops with the GUI), but the end of the server removes the entry for as long as the server is gone, and remote stays wanted: the next server that starts (from `/boss gui`, `cli.mjs up`, a restart, an upgrade, or a pi session's look) turns remote on again by itself, with the same safety checks and without the QR, and when it cannot (Tailscale down, 8443 taken) it says why in `cli.mjs status` (`remote.note`) and in the `remote_off` warning of `up`, and tries again at the next start. **Unpair**: the Phone tile on this computer's page lists the paired devices (name, paired, last used) with Unpair for each and Unpair all, which end that device's open streams at once; a device list is never offered to a paired device. A device whose Tailscale identity changed, which was unused for 90 days, or whose GUI token was replaced, needs a new QR (or, in an app, a new code). **Resuming checks the identity**: a new server turns remote on by itself only as the Tailscale identity (host and login) the devices were paired under, which paired.json remembers; as another one (another user or tailnet signed in) it stays off, removes any serve entry it finds, tells why (a warning), and leaves the wish and the old devices as they are, so the next start as the remembered identity turns it on again and tells the same again until then; turning remote on by hand as the new identity (`/boss gui remote`) is what voids the old devices. A `paired.json` that cannot be written (a full disk, a directory without write permission) does not throw out of the request, and the change stays in effect in memory until the server stops (an unpaired device stays unpaired, remote off stays off), but it is reported: Unpair, Unpair all, Turn on and Turn off remote answer `500 save_failed` with the reason (the Phone tile shows it) and the session shows a warning, because after a restart the revoked device would be paired again or remote would come back. `access.saveError` holds the raw error. A legacy `paired.json` (0.32.1) counts as wanted only while one of its sessions has not expired. Remote off keeps `remote.json` when its entry still exists under another host name (the Tailscale identity changed), so a later off can remove it. It says why and changes nothing when Tailscale is missing, signed out, a tagged node, without MagicDNS, or 8443 serves something else. The layout works on a phone: no sideways scrolling, larger touch targets, safe-area insets, and the composer stays above the on-screen keyboard. Since 0.26.0 a session on a phone takes the whole screen (‹ goes back to its base, **Info** opens its dossier full-screen, and a tower's dossier lists its base's squads and units on every screen since 0.26.1), its composer fixed at the bottom over the keyboard, and a tile opens over it the same way; the composer puts its box on top with **+** on Send's row, its note line taking no room while empty. While a finger holds or flings the comms log, nothing pulls it back to the newest entry (0.26.1). The net log folds away from its heading, and on a phone shows only its two newest entries. To use it as an app, pair in the browser first and then add it to the home screen: iOS copies the browser's cookies into the app only once, at install, and after that the two keep separate cookies, so a pairing link (which opens in the browser) never reaches the app; the pairing code typed into the app's own entry does. On Android an app installed from Chrome shares Chrome's cookies, but launching it is a navigation from another site, which leaves the SameSite=Strict cookie behind: a page load without the cookie whose `Sec-Fetch-Site` is not `same-origin` gets a page that reloads itself once, and that same-origin reload carries the cookie (0.42.4). 

  **The installed app's entry.** An installed app cannot follow a token that changes (a new one comes with a taken port, a lost store, or `/boss gui rotate`), and on iOS it has a cookie jar of its own that a link opened in Safari never reaches. So the remote listener (only; on the local one `/sb-app/` is a wrong token and answers 403) also answers a fixed, token-free path, `/sb-app/`, and the manifest it serves a remote page has `start_url` `/sb-app/` and `scope` `/`; the local page's manifest is as before. The entry runs the same identity checks as a page (remote on, the exact MagicDNS host, no Funnel marker, this machine's `Tailscale-User-Login`), and its pages hold no token and no secret. A GET with a valid device cookie answers 302 to the current `/<token>/` and sets the cookies again; one without it shows a page with a field for the **pairing code** (its own `form-action 'self'`, no script), or, for a document load that is not `Sec-Fetch-Site: same-origin` (Android launching the app, which leaves the SameSite=Strict cookie behind), the same one-time self-reload as a tokened page. The POST `/sb-app/pair` takes the code: it must be a form post from the entry's own page (`Origin` equal to the https name, `Sec-Fetch-Site` `same-origin` when sent, `application/x-www-form-urlencoded`, at most 1 KB), so a post from another site never reaches the code or counts for anything. The code is 8 characters from a 32-symbol alphabet without I, L, O, and U (40 bits, shown `ABCD-EFGH`; case, spaces, hyphen, and look-alikes are forgiven), drawn when `/boss gui remote` runs (under the QR in its overlay, never in the text the conversation shows) and when the Phone tile asks (beside the QR); it works once, within ten minutes, and ends with remote off or an identity change; at most sixteen wait. After five wrong codes every waiting code is void and the entry answers 429 until this computer asks for a new code (which gives the five tries back), so a device on the tailnet cannot grind through the 40 bits. A pairing made by the code is the same as a scanned one (a device with a name, 90 days, renewed by use), and its response sets the session cookie twice: `Path=/<token>/` for the page and `Path=/sb-app/` for the entry, each HttpOnly, Secure, SameSite=Strict, so the pairing is never sent to another path on the host; a QR pairing and a renewal set both too. A document load at a dead token by this machine's user, or at the current token with no pairing and `Sec-Fetch-Site: same-origin`, answers 302 to `/sb-app/`, so an app installed before the entry existed (its start URL is an old tokened address) finds it by itself; any other request gets the refusals as before. The 401 text for everything else says to type the code in an installed app. A restart keeps the token and the pairing (D27), so a paired app goes on by itself; the code is for a first pairing and for a device that a new token unpaired.
- **The server panel.** The header's **Server** button, on this computer's page only (127.0.0.1; a paired device does not see it, and the server answers it 403 `local_only`), opens the sb server's state (live, restarting, or stopped; version; mode; uptime; last error), **Restart server** (a confirm in place that says the page keeps its address and reconnects by itself, then the server restarts and the page reconnects when it is back, with a note to open `/boss gui` if it does not: the address changes only when a port was taken) and **Show log** (the last 200 lines of `server.log`, which holds no message text or secret). Restarting from the page names the asker "GUI" in the log; the reason is one line of at most 200 characters.
- **One GUI per machine, served by the sb server.** The GUI runs in the sb server ([The sb server](#the-sb-server)), not in a pi session: the server binds its two listeners (the local one and the remote one) after it has registered its intercom id, and `/boss gui`, `/boss gui stop`, `/boss gui remote`, `/boss stash`, and `/boss close all` ask the server over its control socket. A pi session hosts nothing, adopts nothing, takes nothing over, and holds no dialog hub, so the page does not depend on which pi lives. The server writes `gui.json` and records the same port and token in `server.json` (`gui: { port, token, stopped }`). **The token outlives the listener (D27).** The boss chose to keep the GUI token, the CSRF secret, and the paired devices across restarts. The token and the CSRF secret live in `gui-secrets.json` (mode 600, written by rename, beside `paired.json` in the owner-only folder; on Windows covered by the state folder's ACL; the ACL read-back lists it in the primary slot's folder only, a secondary slot's copy inherits the folder's protection without being read back) with the pair of ports they were bound to. A restart or an upgrade of the server, a server that starts after a crash or an unclean exit, a reboot, and a start after `/boss gui stop` bind the recorded ports again (a port the old server is still letting go is waited for up to 5 s) and keep the token, the CSRF secret, and `paired.json`'s devices: an open page and the desk shell reconnect by themselves, a phone's tokened start URL and the installed app's fixed entry go on, and remote access, when it was wanted, comes back with the serve entry pointed at the new remote listener. Both records carry the token before `restarting` is cleared. A **new** token, with every device unpaired (the log says `devices-cleared`; the identity and the wish stay), comes in three cases: `gui-secrets.json` is missing, corrupt or stale (one log line, `newToken=true why=missing`, `corrupt` or `stale`; the first start after an upgrade from 0.47 has none; a link or a file another account owns in its place is `corrupt`; `stale` is a store whose token is not the one the records name, left behind when a build that ignores the store ran on the ports in between: a downgrade, or a 0.45 host), the listener could not get both of its ports back and moved (`why=moved`; the remote port counts), and `/boss gui rotate` (after a confirm; a new token and CSRF secret on the same ports, every phone unpaired, a stopped GUI started, the new address opened; `why=rotate`). Then the old token and CSRF secret get 403, a page left open says the address does not work here (a page load at the old address gets the same note as a short HTML 403, in Traditional Chinese when `Accept-Language` asks for it), and a phone scans a new QR code (an installed app types the pairing code). **The risk, accepted by the boss:** another account that binds a port in the gap between two servers receives what an open page or the app sends (the token in the URL, the CSRF secret in its requests), and the secrets stay valid when it frees the port. On the remote port the gap is wider: a clean leave (and a fatal JavaScript error) takes the serve entry down, but a SIGKILL, an out-of-memory kill or a power loss leaves it pointing at the dead port, so a squatter there is sent a paired phone's requests with the token in the path. What it then gets is more than that phone: with the token it can open this computer's page on the local port (the local listener admits on the token and a `Host` header the process sets itself) and read the CSRF secret, which is the full power of the local page (restart, link settings, spawn, secret entry). Unpairing the phone does not end it; only `/boss gui rotate` does, and the "port is taken" rule catches only a squatter that still holds a port when the next server starts, not one that let go. `/boss gui rotate` is the answer to a gap you do not trust. The first server after an upgrade can find a pi session of 0.45 or older still hosting the GUI: it asks that session to hand over, as a newer build always could (`server/stop` with `take`; its serve entry goes with it), waits up to 5 s until nothing accepts a connection on its port (it sends the port nothing during that wait), and binds the same port, under a token of its own (the older host never stored one), when it gets it back (only when the process `gui.json` names runs, and its start time is known and the one `gui.json` records: nothing is sent to a port whose recorded process is gone, and nothing to one whose process's start time is not known yet or was not recorded, because on Windows a crashed host's pid is often another process's, which may hold the port. The start time is waited for up to 6 s; when it does not come, the hand-over is skipped and logged as `gui-reclaim-skipped`, and the server's GUI moves to another port), so remote access comes back on the server's listener (the page the older host served stops working: its token is the older listener's). The server itself is never taken over: a takeover asked of it is answered 409, and the older session then reports the GUI as stale and leaves it alone (only that build's plain `/boss gui stop` is taken, as a stop on purpose). `/boss gui` is the boss's own start: it starts the sb server when none runs, starts a GUI that was stopped on purpose, opens the browser, and prints the URL. `/boss gui stop` stops the GUI listeners only (`stopped` in `gui.json` and `gui.stopped` in `server.json`); the server goes on running its other services, and a restart keeps the stop, the boss's own `/boss server restart` too (it clears only the server's own stop on purpose, as `/boss server` and `cli.mjs serve` do; only `/boss gui` and `cli.mjs up`'s gui step start a GUI that was stopped). No automatic ask starts a GUI that was stopped on purpose: `/boss stash` and `/boss close all` say it was stopped and leave it to `/boss gui` or `cli.mjs up`. `remote.json` records the serve entry's target, the server's PID, and when that process started while remote access is on (`paired.json` outlives the server: whether remote is wanted on, the identity, and the devices, which go only with a new GUI token), so the next server removes an entry a crashed one left: a recorded entry counts as stale only when its PID is gone or belongs to a process that started at another time, so a server that really runs keeps its entry. If the remote port is taken (two servers, or another process) the server gets another free one, which `remote.json` and the next serve entry then name.
- **`gui.json` is a contract.** Besides the sessions, a program that shows the GUI (the straw-boss-desk shell) reads `gui.json` in the state directory, `$PI_CODING_AGENT_DIR/straw-boss/` (a pi without that variable uses `~/.pi/agent/straw-boss/`). It may read `port`, `token`, `pid`, `started`, `stopped`, `version`, `herdr`, and `owner`; `csrf` and the rest are for the sessions (`trust: 1` tells a pi that the server reads its project trust question, [Project trust](#browser-view)). Since the GUI moved into the sb server, `pid` and `started` name the sb server, the process that serves the GUI, `owner` is `sb server (pid N)`, `ownerSession` is the server's intercom id, and `stopped` means the GUI was stopped on purpose (`/boss gui stop`) while the server runs on; the whole server stopped on purpose is `server.json`'s `stopped`. The file holds the token, so it is a secret: never log it. The URL is `http://127.0.0.1:<port>/<token>/`, with the trailing slash. **Ready**: the record exists, is not `stopped`, and a GET of the URL answers 200. **Moved**: a restart, an upgrade, a start after a crash or an unclean exit, a start after `/boss gui stop`, and a reboot write the record again with the same `token` and CSRF secret and the same `port` (D27: the token is kept in `gui-secrets.json` with the pair of ports it belongs to). A new `token` comes with a port that was taken (the remote port counts: one that is taken moves the listener to a new token too), a missing, corrupt or stale `gui-secrets.json`, a hand-over from a 0.45 host (which never stored one, and leaves a store from before it stale), and the boss's `/boss gui rotate`. The old token and CSRF secret then get 403, and both records carry the new token before a reader can see the server as live again. Watch the directory (or read the file every 2 s) and reload when `port` or `token` changes, once the new URL answers; a shell that loaded the old URL has no page to keep. **Gone** no longer depends on a pi session: a server that went down without a stop is started again by the next pi session's look (about 6 s while any pi runs), by its supervisor, or by `cli.mjs up`, which a shell runs at its launch; the states and what a shell does in each are in [States for a shell](#states-for-a-shell). Every write goes to a temporary file in the same directory (mode 600, created new under a random name) and is renamed into place, so a reader never sees half a file. While the server restarts, `gui.json` still names it but has no `started`: an older build adopts a GUI only when the record has one, so no pi session of 0.45 or older adopts it mid-restart, and the next server writes `started` again. The record has no schema version: pin the pi-straw-boss version, and a change to these fields reaches you only with a new pin. `server.json` (beside it) describes the whole stack and is the successor the shell moves to: it may read `pid`, `started`, `version`, `herdr`, `mode`, `desk`, `stopped`, `restarting`, `lastError`, `log`, and `gui: { port, token, stopped }`; `socket`, `secret`, `intercom`, and `intercomId` are for sessions only. `gui.json` stays on disk, and is never removed without a note in the release. A session started with `STRAW_BOSS_DESK=1` in its environment (the desk shell shows the page itself) prints the URL for `/boss gui` and opens no browser.
- **Desk mode in the page and the session** (`STRAW_BOSS_DESK=1`; the desk shell starts its Herdr server with it, so everything under it has it, and `server.json` records `desk`). A server that runs with the switch puts `<meta name="sb-desk" content="1">` beside `sb-csrf` in the page it serves, and the page, which reads it once at load, leaves out GUI remote access (the HUD's **Phone** button and its tile) and stash (each base's **Stash** button, the HUD's **Stashed** button and its list); this holds after every restart, because each server reads the switch from its own environment (`up` with the switch restarts one that runs without it). Hiding is presentation only: the routes stay, and the URL is the credential either way. A session in a desk stack prints the URL for `/boss gui` and opens no browser, and its pairing overlay has no **o** key. The folder pickers (**+ New base**, **+ Member**, **+ Main**, and Straw Link's folder steps) show a **Choose…** button when the shell's preload exposes `globalThis.strawBossDesk.pickFolder({ defaultPath, title })`, which answers a folder path or `null`: the chosen path goes through the same `POST api/dirs` as a click on a breadcrumb, so the server stays the judge of it (home only, nothing hidden, and a refusal shows in the picker's note), and `null` changes nothing. A browser has no such hook, so no button. Every session, desk or not, checks 20 s after its start whether Herdr's pi integration is in place for its agent directory: when Herdr reports an agent in its pane but no `agent_session`, it warns once, "Herdr's pi integration is missing for this agent directory, so this session cannot join the net; run `herdr integration install pi` and restart pi." (`src/integration.ts`; a failed listing says nothing).
- **Background tabs.** The page treats a stream as dead after 45 s without a message and reconnects with a backoff of 1 s doubling to 30 s (±20 %), giving up after 8 failures until the tab is used again. Coming back (visible, focus, `pageshow`, `online`) reconnects at once when the stream is closed or has been quiet for 20 s, and takes a fresh full snapshot instead of replaying what was missed. While disconnected, the map is dimmed and the banner says so with the time of the last update. A hidden tab pauses its animations, draws only the newest snapshot when it returns, and holds no timer beyond the watchdog.
- **The QR encoder** is the package's own (`src/qr.ts`), adapted in part from Project Nayuki's QR Code generator library (MIT, see [`NOTICE.md`](../NOTICE.md)); there are still no runtime dependencies.
- **Motion rests.** A page left alone costs a phone's battery in frames, so the animations that never end (the spinning rings, the waiting unit's ping, the working badge's spinner, the connection dot's blink, the packets on the map's wires) stop after 30 s without input and show a still sign of the same state instead (a frozen ring or spinner, a faint halo for a unit that waits); any touch, key, mouse move, or scroll brings them back. A wire's packet travels only while one of its two towers works, and a phone's dossier, which sits under the full-screen comms, is not drawn. With `prefers-reduced-motion` the page has no such motion and none of this runs.
- **Icons** come from [game-icons.net](https://game-icons.net) by Lorc and Delapouite, [CC BY 3.0](https://creativecommons.org/licenses/by/3.0/) (details in [`gui/ICONS.md`](../gui/ICONS.md)). Nothing is loaded from the network: no CDN, fonts, or runtime dependencies.

## Pane balance

A second extension entry, `src/balance.ts`, keeps Herdr tabs even. When a pi starts in a tab (once per process, so `/reload` does not count) and after a pi quits and Herdr closes its pane, the panes of that tab get equal widths along each split, and stacked panes equal heights. It runs in every pi inside Herdr, joined or not, and leaves a zoomed tab alone. A pane that outlives its pi (a shell you keep) changes nothing.

The work runs in `src/balance.mjs` as a detached `node` process: `balance.mjs now <pane>` at start, `balance.mjs after-close <pane> <tab>` at quit, because the quitting pi exits before Herdr closes its pane. It is started with `windowsHide`, so on Windows a detached console child gets no console window of its own. Each resize is planned from a freshly read layout, and a per-tab lock under the system temp directory (`pi-straw-boss-pane-balance/`) makes concurrent sessions take turns instead of applying the same change twice.

A local tower run's pi (started with `--sb-run`, or marked by the run mode when the server hands it a standing pane, `src/runmark.ts`) never starts `after-close`: its pane stays, so the helper would only wait out its 30 s. On Windows that wait mattered: Herdr starts `pi.cmd` with `Start-Process -Wait`, which waits for the whole process tree, so the pane showed no prompt until the helper ended and the next `herdr agent start` there ran into its own timeout. An ally run's pane is closed by the server as soon as pi is gone, so its pi keeps `after-close` and the tower tab is rebalanced as for any pane (the run mode marks the process `ally` once the claim says so).

## Blocked dialogs

Herdr's pi integration shows a pane as `blocked` while its count of `herdr:blocked` events (`{active: true, label}` up, `{active: false}` down) is above zero, and pi's own dialogs emit nothing, so a session waiting on one looked as if it were working. A third extension entry, `src/blocked.ts`, closes that for every pi in Herdr, joined or not, subagents included. It relays two sources into `herdr:blocked`:

- **rpiv's questionnaire**: `rpiv:ask-user:blocked`, once per open `ask_user_question`.
- **Every `select`, `confirm`, `input` and `editor` dialog of any extension** (an `mp-infra` command review, pi-robot-hand's selector), from pi's `ui_prompt_start` / `ui_prompt_end` events (pi 0.84.4 and later; on an older pi they never fire and nothing is relayed). This relay wraps nothing: pi wraps `ctx.ui` once per runner for all extensions and emits one pair per outermost dialog (the answer relay above wraps the same object again, and calls pi's wrapper, so the pairs are unchanged), so overlapping dialogs make one pair that spans from the first start to the last end, and a dialog that resolves, is cancelled, aborted, times out or throws ends it all the same. The label is `Waiting for your answer: <title>`, with control and format characters turned into spaces and the title cut to 80 characters (`<kind> dialog` when it has none). A session without a UI (print mode) gets pi's no-op `ui`, which is never wrapped, so it emits nothing; `/reload` and a new session load a fresh runner and a fresh relay, and the old ones are dropped with their runner.

Pi emits both events without waiting and walks the extensions one after another, so behind an earlier extension's slow handler a dialog's end can reach this relay before its start (measured against the real runner). The relay therefore keeps a signed count and reports blocked only while it is above zero: an early end and its late start cancel out, and the pairs it emits always alternate and end balanced. `custom` dialogs are left out on purpose: pi's own program status does not count them as blocking either, and the ones that do wait for the user report themselves (`ask_user_question`, `secret_drop`, the pairing QR overlay). Because pi reports only the outermost dialog, a confirm opened while a `custom` dialog is already open is not reported either. A tool that reports its own dialog as well (pi-robot-hand's `robot_hand` selector, pi-ask-user's input) adds a second, balanced pair while it is open; Herdr counts both and clears them together. Skipping the relay's pair there would drop blocked when the tool's pair closes first while another dialog is still open. A blocked pane has no question to show, so the GUI lists it as waiting with "It waits on a dialog.", and its composer refuses a prompt while Herdr reports the pane `blocked`.

## Sidebar net view

The optional Herdr plugin in `herdr-plugin/` (id `wayne930242.straw-boss`, action `net`) toggles the sidebar's Agents list between Herdr's own view and a net view.
The net view lists the head tower's workspace first, then the other workspaces in Herdr's order.
In each workspace the tower comes first, then the tabs in their order, and in each tab the main agent and then the members.
Every subagent sits directly under the session that launched it, including one that pi-herdr-agents opened in a worktree sub workspace.
Agents the net does not know come last, in Herdr's workspace, tab and pane order, so nothing is hidden and an agent that waits for you stays on the list.
The sidebar header reads `net` while the view is on.
The view is on by default: the plugin turns it on when the Herdr server starts, and the key switches it off and on again.
The same order drives the collapsed sidebar, the mobile list, mouse targets, and `focus_agent` numbering and next/previous navigation.
The view changes no notification or attention count.

**The tower between runs.**
A tower the sb server runs keeps its row when no run is live: the server reports a stand-in agent `tower` on the standing pane (idle, with `standing by`, `3 queued` or `held` as its message) while the tower prompt runs there ([The standing pane](#the-standing-pane)), so the row sits first in its workspace as the tower's mark and `agent.list` shows it.
It is a row and nothing more: no net, dashboard, stash, closer or reaper check counts it as an agent, a main, or a member, and an idle report starts no toast, sound, or attention count.
A run replaces it with pi's own row, and it comes back when the run ends.
An ally run's pane is a row too, right under the tower (`[ally] <device label>`, see [Ally runs](#ally-runs-b6)).

**The tokens.**
Every session in the net writes display tokens next to `sb_role`, in the same report, on the same 4 minute refresh and with the same 10 minute TTL.
It writes them on the panes of the subagents it launched as well, because those never join and write nothing themselves.
A session that ends clears its own and its subagents'.

- `sb_order` is the sort key.
  A tower's is `WWW.0`.
  A main agent's or member's is `WWW.1.TTT.R.PPP`: `WWW` is the place of its workspace among the base workspaces (a sub workspace does not count, and the head tower's is `000`), `TTT` the place of its tab in the workspace, `R` is `0` for a main agent and `1` for a member, and `PPP` the place of its pane in the tab.
  Each subagent adds one `.NNN` segment, its place among the live and finished subagents of its launcher, at any depth (the dashboard lists eight per session, the keys cover every live one).
  Every number is zero-padded, so plain string order is numeric order, and a subagent's key sorts after its launcher's and before the launcher's next sibling's.
- `sb_mark` says what a net member is, in a few characters: a star alone (Font Awesome's, U+F005) for a main agent, a person alone (Font Awesome's, U+F007) for a member, and `[sub] <launcher>` for a subagent, with the launcher's name cut to 24 characters. The pane of an ally run (a Straw Link message worked by the sb server) has `[ally] <device label>`; its key, branch and name are written by the sb server for it, like a subagent's by its launcher (see Ally runs).
  A tower has none: its tab already carries the radio tower glyph.
- `sb_main_tab` is a main agent's tab label and `sb_tab` a member's, one token per role because a Herdr rule sees only its own token, so a row colors each by role.
  A member's keeps the `sb_tab` name it has had since 0.7.2, so the row works with sessions that have not reloaded; every other agent carries neither.
- `sb_indent` is on a subagent alone, and is the branch to it from its launcher, drawn like the worktrees in Herdr's Spaces panel: `├─` while a later subagent of the same launcher is marked, `└─` on the last one.
  Subagents of one launcher are siblings at every depth.
  A tower, a main agent and a member carry none, and a session clears the one a pane kept from when it ran a subagent.
- `sb_name` is on a subagent alone, and is its own name as pi-herdr-agents shows it, cut to 24 characters like the launcher's name in `sb_mark`.
  The name comes from the pane's Herdr label while it has one, else from the launch script's name.
  Herdr keeps the label in the server's memory too, so after a new server the label is gone and a row would show only the workspace's name; the token comes back with the others (see below) and a row can show it instead.
  A tower, a main agent and a member carry none, and a session clears the one a pane kept from when it ran a subagent.

The tokens rest on Herdr's order as of the session's last refresh, so moving a tab or workspace shows in the net view within 4 minutes, and a subagent that has a new sibling gets its `├─` at the next refresh.
A subagent is marked while its pane runs pi: its launcher publishes again 3 and 15 seconds after a `subagent` or `subagent_resume` call returns, so a new subagent hangs under it within seconds, and its tokens go at the next refresh once it has finished.
A subagent whose pi Herdr has not detected by then (it waits at pi's trust prompt, say) is marked when Herdr reports it, not at the next refresh.
While a launched subagent has no pi pane, its launcher keeps one `events.subscribe` connection open for `pane.agent_detected` and `pane.updated` (the two events that can turn a pane into a pi on the subagent's session file), and a burst of them, from a pane the launcher has not marked, sets one timer of 1 s that reads Herdr once.
The reading writes only the subagents' tokens, and only when they differ from the last ones written, so events that change nothing cost one reading and no write.
The connection closes as soon as every launched subagent has a pi pane, and with it a session that launched none holds none; a subagent that finished in the last 10 minutes has no pane either, so the connection stays that long after it.
The 4 minute refresh stays as the safety net, and a subagent's tokens still go at the next refresh once it has finished.

**A new Herdr server.**
Herdr keeps pane and workspace tokens in the server's memory, so a server that takes over (a live handoff during an update, or a stop and a start) begins with none of them, and the net view would stay unsorted, and a tower would look absent, until each session's next 4 minute refresh.
Every session that can join the net, and every tower, therefore keeps one `events.subscribe` connection open on Herdr's socket, only to see it close; it asks for `workspace.renamed`, which almost never happens, so the connection carries no traffic and costs nothing while the server runs.
When it closes, the session reconnects after 0.25 s, 0.5 s, 1 s, and then every 2 s, and when a server answers, it writes everything again at once: first, for a tower, the workspace token `tower` and its own `sb_role`, which is how another session finds the tower (without them a `call_tower` in the gap would open a second one), then the full publish of the 4 minute refresh (its role and net tokens, and the marks of the subagents it launched).
The first connection of a session is no takeover. A session that has not finished joining (or a tower that has not taken its role) writes nothing on a takeover, and a subagent and a session in a sub workspace hold no connection.

**A Herdr restore.**
After `herdr server stop` and a new server, Herdr (with `[session] resume_agents_on_restore`, on by default) starts a new pi in every restored pane as `pi --session <file>`: the processes are new, the pane and tab ids and the session file path are the same, and `STRAW_BOSS_ROLE`, the tokens, and (for a session that had no conversation yet, since pi writes its file only after the first message, and gives the resumed one a new session id) the `straw-boss` entry are gone.
Without more, every resumed session would come back a member: the PM who quits the app and opens it again would lose the tower and every main.
A tower and a main therefore record their role in `roles/<hash of the session file>.json` of the state directory (role, pane, tab, workspace, and for a main the pane's terminal), when the tower takes its role and when a session becomes its tab's main, and drop it when the session is closed on purpose (the GUI's quit, `/boss close`, a tower asking an opened main to quit, a second tower yielding).
A session that starts in the pane, tab, and workspace it recorded takes the role back: the tower starts as the tower, which writes its tokens and the workspace token with the new session id, and the main joins and promotes itself, refused as always when the tab already has a live main (and then it drops its record, since it stays a member).
A session in another pane, tab, or workspace than it recorded, one with no record or a record that cannot be read, and one a user closed on purpose stays a member, and nobody takes the role from a record without the pane, tab, and workspace it names.
A main needs one more proof, that a restart happened: Herdr gives a restored pane a new terminal (`terminal_id` of `pane current`, while the pane id stays), and the record names the terminal the main ran in.
A pi started in the same terminal, after a `/quit` and a `pi --session` or `/resume` of the same file in the still-open shell, is no restore: it stays a member and drops the record, so the next real restore does not give the main role to a session that never held it.
A tower needs no such proof, because a tower closes its pane when it quits and its record is dropped then.
A main a tower opened (see [Closing an opened main](#closing-an-opened-main)) records its `sb_opened_by` marker too, and a restored main writes it back and registers the control channel again, so the restored tower of its workspace can close it as before: the restore is a plain start, which has neither the pane's tokens nor the opener saved in the session, and the right to close rests on the tower token of the main's workspace when the tower asks (the rule above), which a new tower session holds again once it is back. The record counts only where the main ran (the same pane, tab, and workspace), so a main restored in another workspace has no marker, and a main the boss opened has none to bring back.
The terminal is required for a main: a Herdr that reports no `terminal_id` for the pane gives it no restore, and the session warns once at its start. Herdr may reuse a pane id, so the record also names the session file, and the guard waits for a pane only while the `agent_session` Herdr reports for it (when it reports one) is that file.
A tab has one main record: the session that becomes the tab's main deletes the others for that tab, so a main that `/boss` or the guard demoted does not come back as a second main whichever pi starts first; if an older record is left beside the new one (written by an earlier version), a restore honors only the newest.
A record is not dropped when the guard turns a main back into a member, nor by a plain `/quit`: a Herdr stop looks the same from inside the process, and the tower quitting just ahead of its mains demotes them first.
The guard that crowns a tab's first member when the tab has a tower and no main (see the guard above) waits for the main a restore is bringing back: while the tab's main record names a pane that now runs in a new terminal, it crowns nobody, for 30 s from its first look at that pane. Without the wait the first pi to join a restored tab would be crowned over the recorded main, and the recorded main would then find the tab taken.
A main that came back this way does not open a tower (the first main of a workspace normally does): its tower is coming back too, and a base whose tower does not return clears its mains after the guard's grace as it always does.
A record untouched for 90 days is deleted when another is written; that tidying, and the deletion of a rival main record, cannot fail the write of the record itself.
The connection and the retry timer never keep pi alive, and `session_shutdown` closes them: a `/reload` leaves one connection, the new instance's, and a session started again in the same instance replaces its connection.
A server that refuses `events.subscribe` is treated like one that is gone, so the session retries every 2 s without effect and keeps the 4 minute refresh as before.
The sidebar plugin needs nothing more: its startup hook turns the view on when the server starts (before any token exists), and Herdr 0.9.4 and later sort the view again when tokens change.
The subagents a restore brings back are another matter: each comes back as a plain pi without the extension that makes it a child, and its launcher is asked to resume it (see [Subagents a Herdr restore brought back plain](#subagents-a-herdr-restore-brought-back-plain)).

**Sidebar rows.**
The tokens also show the roles in Herdr's own grouped view, which a plugin cannot reorder.
Add them to a row of `[ui.sidebar.agents]` in `config.toml`.
`$sb_indent` goes before the state icon, so a subagent hangs under its launcher as the worktrees do in the Spaces panel; Herdr puts its own ` · ` after it, and an agent without the token shows nothing.
`$sb_name` goes right after the state icon, so a subagent row says which subagent it is even when Herdr has lost the pane's label.
Every glyph sits in the first row; the `[sub]` mark stays hidden because the branch already says what it is. The snippet leaves the colors to your Herdr theme; add an `fg` to a rule to color a mark.
Herdr drops a row whose every item is empty, so the second row, the tab label from `$sb_main_tab` or `$sb_tab`, gives a main agent and a member a second line and leaves every other agent one line; give the two tokens the colors of the star and the person. The first row leaves out Herdr's `tab`, which the second row carries.

```toml
[ui.sidebar.agents]
rows = [
  [
    { token = "$sb_indent", dim = true },
    "state_icon",
    { token = "$sb_name" },
    { token = "$sb_mark", rules = [
      { starts_with = "[sub]", hide = true },
      { starts_with = "\uF005", bold = true },
      { starts_with = "\uF007", bold = true },
    ] },
    "machine", "workspace",
  ],
  [{ token = "$sb_main_tab", bold = true }, { token = "$sb_tab", bold = true }],
]
```

Herdr's default has a second row with the agent name; put `"agent"` back in a row of its own, or in this one, if you want it.
The token colours take hex values only, so add an `fg` to a token or a rule to taste.
`herdr config check` accepts the snippet, and `herdr server reload-config` applies it.

**Install.**
Link the plugin from a checkout and bind the action to a key.
Herdr runs the startup hook when a server starts, not when a plugin is linked, so a server that is already running shows the view after one press of the key, after the next agent Herdr detects (the `reapply` event hook, below), or after a restart:

```bash
herdr plugin link /path/to/pi-straw-boss/herdr-plugin
herdr plugin action list --plugin wayne930242.straw-boss
herdr plugin action invoke wayne930242.straw-boss.net
```

```toml
[[keys.command]]
key = "prefix+alt+n"
type = "plugin_action"
command = "wayne930242.straw-boss.net"
description = "toggle the straw net view"
```

`prefix+?` lists the keys that are taken, `herdr server reload-config` loads a new binding, and `herdr plugin unlink wayne930242.straw-boss` removes the plugin.
The plugin needs Herdr 0.9.5 or newer (the view probe is checked on it) and node; on Windows it reaches Herdr over its named pipe and has its own action, `net-windows` ([Windows](#windows)).
The tokens come from the sessions, so a session that still runs an older pi-straw-boss (before 0.6.5) has none until pi reloads it, and sorts after the others.

**How the view works.**
The view is one `agent.view.set` request on Herdr's socket, which the CLI has no command for, sorted by the `sb_order` token ascending, then by Herdr's workspace, tab and pane order.
Herdr sorts a present value before a missing one, so agents without the token come after the net, and among themselves in that place order.
The plugin writes no tokens of its own.
Herdr servers before 0.9.4 do not sort an installed view again when tokens change (0.9.4 does): the order stays as it was at the last install until the view is switched off and on again, so press the key twice to refresh it.

**On at start.**
`[[startup]]` in the manifest runs `net-view.mjs startup` once after the server has restored its session, and again when a new server takes over in an update handoff.
It installs the same view as the key and exits at once; no process stays running, and a failure (Herdr refusing the view) is in the plugin log and does not stop the server.
Every server start turns the view on, whatever an earlier server left: a press that turned it off lasts until the server stops.
The one exception is a startup that runs again in the same server, which leaves that server's own "off" alone.

**The toggle.**
Herdr has no query for the active view, but `agent.view.clear` with a source that owns nothing (`<plugin source>-probe`; Herdr accepts only ASCII letters, digits, colon, dot, underscore and hyphen in a source) leaves the view unchanged and answers with it (checked on Herdr 0.9.5), so the action reads what is shown instead of trusting what it saved: it clears when its own view is the active one and installs otherwise. A plugin unlinked and linked again, or disabled and enabled, in one server run loses its view without a startup hook, and the first press used to record "off" and change nothing; now one press always changes the sidebar. The state in `net-view.json` in the plugin's state directory ("on" or "off" and the identity of the running server, the socket file's inode and creation time) is only the wish the hooks read.
The next press clears the view with `agent.view.clear` named to this plugin's own source, so it never clears a view that another owner installed.
A restarted server drops its view; the startup hook turns the view on and records it, so the first press switches it off. `[[events]] on = "pane.agent_detected"` runs `net-view.mjs reapply` (Herdr has no hook for a link or an enable): it installs the view when no view is active and this server's own "off" has not been pressed, and leaves any active view, this plugin's or another owner's, and a pressed off alone; so after a relink the net view is back at the next agent Herdr detects.
A view another owner installed over this one also counts as off: the press installs this one again.

**Limits.**
Herdr keeps one Agents view per server, so another plugin's view and this one replace each other.
Unlinking or disabling the plugin while the view is on drops the view at once; the first press after linking it again only resets the state, and the second turns the view on.
Herdr starts plugin commands with the PATH of the process that started its server, and a Herdr launched from a macOS app has only `/usr/bin:/bin:/usr/sbin:/sbin`.
`run.sh` therefore looks for node on PATH, in Homebrew's, `/usr/local`, mise, asdf, and volta directories, and through a login shell, and says so in the plugin log (`herdr plugin log list --plugin wayne930242.straw-boss`) when it finds none.

## Worktree reaper

The second optional Herdr plugin, in `herdr-reaper/` (id `wayne930242.straw-boss-reaper`), closes the panes agents leave behind in worktree workspaces and removes the checkouts that are clean.
It is plain JavaScript that imports nothing from `src/` and talks to Herdr through the `herdr` CLI (`HERDR_BIN_PATH`) and to git directly.

**Scope.**
Only a workspace whose worktree is a linked git worktree (`worktree.is_linked_worktree`) is ever touched, whatever its label.
A workspace of the main checkout, or of no repository, is never touched, and neither is anything a pinned workspace holds; the one exception is a main-checkout shell workspace a worktree was grouped under (see the parent shell below).
An optional `config.json` in the plugin's config directory (`herdr plugin config-dir wayne930242.straw-boss-reaper`) with `{ "only_under": ["/path"] }` narrows the scope further, to repositories and checkouts below the listed directories; `{ "retain_idle_hours": 72 }` sets how long a pi-herdr-agents parent session that is open in no Herdr pane may stay silent before its worktrees are released (see the checkout below; a value that is not a positive number means the default).

**What closes a pane.**
The plugin remembers which panes ran an agent: a `pane.agent_detected` event and every sweep that sees `agent` set record the pane's terminal.
A pane that was recorded, now has no agent, and whose shell is idle (Herdr's `pane process-info` shows the shell as the only foreground process) is a candidate.
The first sweep after the plugin's state is created counts every agent-less pane in a linked-worktree workspace as recorded, so leftovers from before the plugin was installed go too, and it starts as soon as the plugin is installed (the first hook starts the ticker, which waits 20 s, and a candidate waits 60 s more: about a minute and a half).
There is no log-only first run: reaping begins at once, so run `dry-run` and pin first.
Only a pane the first sweep treats as a leftover is recorded; a pane it skipped because it was pinned, focused or running something stays the user's shell for later sweeps too.
Panes opened afterwards that never ran an agent are the user's shells and stay.
A candidate must stay one for `CONFIRM_MS` (60 s) before it is closed, so an agent restarting in the same pane, or a command started at the prompt, is not caught between two looks; the `reap-now` action skips the wait.
The focused pane is never closed, and a pane whose shell runs something (a dev server, an editor) is skipped with that process named.
Right before each close the plugin looks at the pane again: it must still be the same terminal (a pane id can be reused), have no agent, not be focused, have an idle shell, and its workspace must not be pinned (token and state file, read fresh).
Anything that changed since the plan skips the close and keeps the workspace's checkout for that run.
"Focused" is the one pane Herdr reports as focused; a second client (the web UI, say) that is viewing another pane does not count, so a pane someone watches from there can be closed.
Closing a workspace's last pane lets Herdr close its tab and then the workspace, with no dialog.

**The checkout.**
When every pane of a workspace was closed by one sweep, the plugin waits up to 5 s for Herdr to close the workspace, then reads `git --no-optional-locks status --porcelain --untracked-files=all --ignore-submodules=none` in the checkout (the options keep a repository or user setting such as `status.showUntrackedFiles=no` from hiding files).
It also keeps the checkout when `git ls-files -v` shows skip-worktree or assume-unchanged files, whose edits `status` cannot show.
Right before removing, it lists Herdr's panes and workspaces again and keeps the checkout if any live pane's cwd or foreground cwd is the checkout or below it, or any live workspace has the same checkout path: in the usual pi-herdr-agents layout the worker's pane sits in the parent's workspace, not in the linked worktree's, and it must not lose its directory. A list that cannot be read keeps the checkout too. This applies to checkouts retried from the pending list as well.
Three more guards decide, in this order, whether a clean checkout is released. Each keeps it as pending (retried every sweep, with no give-up) and logs `keep checkout <path>: <reason>, branch kept`, in a dry run as `would keep`:
1. *pi-herdr-agents holds it.* pi-herdr-agents never removes a worktree on its own: the parent session does, with `worktree_remove`, which marks the child's manifest `removed`. The manifests are `<session dir>/artifacts/<parent session id>/worktree-runs/<child id>.json`; they hold `path`, `state`, `name`, `updatedAt` and the child's `sessionFile`. The reaper reads them below every directory pi may keep its sessions in: `<pi agent dir>/sessions`, with one directory per working directory below it (`PI_CODING_AGENT_DIR`, default `~/.pi/agent`); `PI_CODING_AGENT_SESSION_DIR`; the `sessionDir` setting of the user (`<pi agent dir>/settings.json`) and of the repository (`<repository>/.pi/settings.json`, a relative path counted from the repository). With `sessionDir` set, pi puts `artifacts/` straight into that directory, and the reaper reads that layout too. A directory that does not exist is logged once per run (`pi sessions directory <path> does not exist`) and holds nothing; a settings file that cannot be parsed keeps the checkout. The reaper cannot see pi's `--session-dir` option or a variable that only a shell sets: Herdr's own environment must carry `PI_CODING_AGENT_DIR` and `PI_CODING_AGENT_SESSION_DIR`, or pi's settings must name the directory. A manifest names the checkout when its `path` is the same directory as the checkout's, compared by canonical path: a symlinked prefix (`/tmp` and `/private/tmp`), a trailing slash or `..` segment, and the letter case on a case-insensitive file system make no difference. A manifest that names the checkout and is not `removed` (`provisioning`, `provisioned`, `running`, `ready_for_review`, `needs_help`, `failed`, `cancelled`) keeps it while its parent is alive, which two things show. The first is a Herdr pane that runs pi on the parent session (`agent` is `pi` and its session file is `<time>_<parent session id>.jsonl`, read from `herdr pane list`), however long the parent has been idle. The second is activity: the newest modification time of the manifest, its `updatedAt`, the parent session's `.jsonl` and the child's session file within `retain_idle_hours` (default 72) of now. When Herdr's pane list cannot be read, the activity rule alone decides. A parent that is open in no pane and wrote nothing for longer has ended, and the checkout is then the reaper's. A newer `removed` manifest on the same path supersedes an older run. A manifest that names the path but cannot be parsed (it is matched by the checkout's directory name, in any letter case), a sessions directory that cannot be read, or a reaper wired without the reader keeps the checkout (fail closed). Closing the idle root shell of such a workspace is unchanged, but the workspace closing with it no longer leads to the removal.
2. *Another pane or workspace uses it* (the check above).
3. *A process uses it.* The plugin lists every process of the user (`lsof -d cwd` on macOS, `/proc/<pid>/cwd` on Linux), not only Herdr's panes, and keeps the checkout when one has its cwd at or below it (an editor, a dev server, a pi that was started there, a terminal outside Herdr). In a dry run the idle shells of the panes it would close are ignored. A process list that cannot be had keeps the checkout; processes of other users are not inspected, and neither are the user's own processes Linux will not let it inspect (non-dumpable ones such as ssh-agent or gpg-agent), which rarely sit in a worktree. The manifests of guard 1 and this process list are each read once and reused for 10 s (a sweep over many pending checkouts then costs one read of each, not one per checkout), and a sweep that has just closed a pane reads the process list again, so the shell that exited does not hold its own checkout.
A clean checkout is removed with `git worktree remove`, never forced; any change, tracked or not, keeps it, and so does a detached HEAD that no branch, remote branch or tag contains, because the checkout would be the last place those commits live.
Git-ignored files do not count as changes, so `.env` files, `node_modules`, caches and local databases in a clean checkout are deleted with it; keep a checkout whose ignored files matter by pinning its workspace.
The branch is never touched.
A failed removal logs git's own `fatal:`/`error:` line, not node's "Command failed" header. Git refuses a checkout with a submodule by design ("working trees containing submodules cannot be moved or removed"), so the plugin clears the way itself, and only when nothing is lost: every initialized submodule (recursively) must have no uncommitted or untracked paths (ignored files are fine) and its HEAD must be contained in a remote-tracking ref of its own repository or in a branch, tag or remote-tracking ref of the main repository's own copy (`.git/modules/...`), and no local branch may hold commits outside the remote-tracking refs. The submodule repositories of a linked worktree live in `.git/worktrees/<id>/modules/...` and are deleted with it, which is why those refs count. Then the plugin runs `git submodule deinit --all` (no `--force`), deletes that `modules` directory (git still refuses the removal while it exists), and runs the plain `git worktree remove`. A failed check keeps the checkout and logs the submodule and why, for example `keep checkout <path>: submodule community has 2 uncommitted paths, branch kept` or `submodule community HEAD abc1234 is in no ref outside this worktree (no remote-tracking ref contains it)`; a removal logs `(clean; 1 submodule deinitialized first; branch X kept)`. The main checkout and its submodules are never touched.
After a failed or timed-out removal the plugin checks whether the checkout is half-removed (the directory is still there but git no longer registers it as a worktree of the repository, or its `.git` is gone, as when git deleted them and then failed on the files, say through a self-referencing `node_modules`). If so the log says that leftover files remain at the path, git no longer tracks it and the branch is kept, and that the user can delete the directory; the plugin never deletes or moves the leftover itself.
A workspace that is still open after the wait stays pending in the state file and is retried by the next sweeps for an hour.
Each decision is a line in the plugin log with its reason (`close`, `remove checkout`, `keep checkout ... uncommitted changes`, `keep checkout ... pi-herdr-agents child ...`, `skip ... workspace is pinned`).

**The parent shell.**
When a linked-worktree workspace is open, Herdr groups it under the workspace of the repository's main checkout and opens a plain shell workspace for that checkout if none exists.
The plugin remembers a non-linked workspace as a parent once a linked worktree workspace with the same `worktree.repo_key` (else `repo_root`) was seen open, in a sweep or by the `workspace.created` hook, within `only_under`; a workspace never seen with a worktree under it is never remembered, so it is never closed.
After the checkout step of a sweep, on a fresh look at Herdr, a remembered parent is closed (`herdr workspace close`, never the group form, so Herdr refuses if a worktree workspace appeared meanwhile) when no linked workspace of its repository is left and every pane has no agent and an idle shell, none is focused, the workspace is not pinned, and its name is the one Herdr gave it (the repository or checkout directory name) and was never renamed (a rename also pins it).
**A workspace a Straw Boss tower stands in is never closed** (0.4.0), whatever its panes look like: the sb server puts the tower's tab in this very workspace, and between runs the standing pane is a shell that waits at a prompt, which is exactly what the rule above closes. The plugin reads the tokens the server writes and nothing else of Straw Boss: the workspace token `tower`, and the pane token `sb_role` with the value `tower` (the standing pane) or `ally` (an ally run's pane, split off the tower's tab). Any one of them keeps the parent, and the parent is not tracked as a candidate meanwhile; a token that is gone (the tower was closed, or the tokens' 10 minute lifetime ran out with no server alive to renew them) leaves the parent to the rule above again.
It must qualify for `CONFIRM_MS` (60 s) first, tracked in `parentCandidates`; closing the workspace closes only its panes, and the main checkout and every branch stay.
The log lines are `wait parent <label> (workspace <id>): ...`, `skip parent ...: <reason>` (worktree workspace still open, pinned, name changed, a tower stands in it, agent or running process in a pane, focused pane), and `close parent workspace ...`; a dry run prints `would close parent workspace ...`, counting the worktree workspaces it would close as gone.
A child closed by the user rather than the plugin is handled the same way, by the next sweep (up to 10 minutes later) and the confirmation wait.

**Pins.**
The `pin` action is one toggle, in the `workspace` context: it sets or clears the workspace token `pin`, a Nerd Font pin (nf-md-pin, U+F0403), through `workspace.report_metadata` under the source `wayne930242.straw-boss-reaper`.
Herdr shows a workspace token only where a row asks for it, so add `{ token = "$pin" }` to `[ui.sidebar.spaces]` rows as the README shows.
Bind it with `[[keys.command]]` (`prefix+i` in the README's example: `prefix+P` is Herdr's default `rename_pane`, and `alt` combinations are often taken by window managers such as AeroSpace); a key invokes it in the focused workspace.
A pin is also written to the plugin's state file, because Herdr drops workspace tokens when its server restarts, and a sweep puts the token back. A linked worktree's pin is keyed by its checkout path, so it outlives the workspace and the checkout is never removed; any other workspace's pin is keyed by its id (`workspace:<id>`) and goes when the workspace closes, so a later workspace on the same main checkout starts unpinned. A sweep moves a main-checkout pin an older version keyed by its path to the ids of the workspaces open on it.
A workspace is pinned when either the token or the state entry says so, and a pinned workspace is skipped by every sweep and its checkout is never removed.

A pin does nothing else: closing a pinned workspace closes it, and a linked worktree's pin keeps its checkout from being removed until the checkout is gone or you unpin a workspace on it.

**Pinning by renaming.**
Herdr's `workspace.renamed` event does not say who renamed, but nothing renames a workspace except the user: pi-herdr-agents and Straw Boss set the label when they create the workspace, and `herdr workspace create --label` and `herdr worktree create --label` fire no rename. `herdr worktree open --label` on a worktree whose workspace is already open does fire one, and counts as a rename.
So every rename pins the workspace (any workspace, linked worktree or not, within `only_under`) and marks its record `renamed`, even when a sweep recorded the new label first; a workspace already pinned stays as it is.
Unpinning clears the token and the state entry and leaves the name alone.
Herdr reuses the ids of closed workspaces, so a `workspace.created` event replaces any earlier record of its id, the `workspace.closed` event (or a `pane.exited` that took the workspace's last pane) deletes the record and any `workspace:<id>` pin of the id, and a sweep drops the records of the workspaces it closed.
Each record also stores the workspace's checkout path, and a record whose checkout differs from the live workspace's belongs to an earlier workspace on a reused id and is ignored.

**When it runs.**
A sweep runs every 10 minutes and again when an agent was released, `CONFIRM_MS` later.
Herdr has no timers for plugins, so the startup hook and the event hooks start a ticker, a small detached node process that checks the state file every 15 s and runs the `sweep` action through `herdr plugin action invoke` when one is due, which makes every sweep a normal, logged plugin command.
This departs from Herdr's guidance (0.9.5): startup hooks are meant to be one-shot rather than supervised daemons, and plugins are told to stop detached background processes before their command exits. The ticker is the only way a plugin can sweep on a schedule, and it limits the departure: it is a single process (a beat file and a lock), it keeps nothing but the beat and its log (`ticker.log` in the state directory, truncated at a start when over 200 KB), and it ends on its own after three failed invocations in a row.
After an uninstall, unlink or server exit it therefore lives until its next sweep is due, up to 10 minutes, plus about a minute for the three retries: roughly 11 minutes.
The state directory belongs to the plugin id, so two Herdr servers on one machine (a named session, say) would share it: one ticker for both, and workspace and pane ids of the two servers colliding in the state file. Use the plugin with one server.
A ticker beats in `ticker.json`; a hook starts a new one only when the beat is older than 45 s, and two started together settle it with a lock.
The ticker ends after three failed invocations in a row, which happens when the Herdr server is gone or the plugin was unlinked; the next hook of a new server starts another.
The event hooks do bookkeeping only (`workspace.created`, `workspace.renamed`, `workspace.closed`, `pane.exited`, `pane.agent_detected`), and none is hooked to `pane.updated`, so no per-output work exists.
The `pane.agent_detected` event for a release marks the pane a candidate from that moment and schedules the sweep for the end of its wait; the other events cost one `herdr` call and a state write.
Sweeps never overlap (a lock whose holder keeps touching it, so only a dead run's lock goes stale after 10 minutes, and one waiter at a time takes a stale lock over; a second sweep logs that it was skipped). Every `herdr` call has a 30 s timeout and every git call 60 s (5 minutes to remove a checkout), so a hung call fails instead of holding the lock.
`bash herdr-reaper/run.sh reaper.mjs dry-run`, run in a terminal inside Herdr, prints what a sweep would do now without changing anything, the state file included; it reads the plugin's state, so its first-sweep rule applies until the plugin has swept once.

**Limits.**
The state is `state.json` in the plugin's state directory. Only a missing file reads as empty; a damaged or unreadable one makes the sweep and the events fail with the file's path in the plugin log (and stops the ticker) instead of bringing back the first-sweep rule and forgetting the pins, so repair or remove the file.
A user's shell that outlived its agent in a linked-worktree workspace is closed like a leftover: pin the workspace to keep it.
Ignored files (`.env*`, `node_modules`, build output, local databases) do not make a checkout dirty, so they go with it; pin the workspace to keep them. A pi-herdr-agents worktree is held by guard 1 whatever it contains; the ignored-file loss is for checkouts nothing holds.
pi-herdr-agents keeps no "parent is alive" record, so the hold on its worktrees rests on two signals: a pane in which Herdr sees pi on the parent session, and the idle limit. A parent session that was resumed, forked or restarted with `/new` in its pane is another session id, so its old id no longer counts as open; a parent in a terminal outside Herdr is held only by the idle limit. A pi session of either kind left idle past `retain_idle_hours` and resumed later may find its clean worktree removed (the branch is kept).
The agent event compares its terminal with the pane's only when the payload names one (Herdr 0.9.5 documents `pane_id` and `workspace_id`), so a pane id reused within the hook's latency can still be misread there; the sweep's checks use the terminal id.
A Herdr launched from a macOS app has a short PATH; `run.sh` finds node the way the net-view plugin's does.
The plugin needs Herdr 0.9.3 or newer, git, node 18 or newer, and a Unix shell, so it runs on macOS and Linux only.
`tests/reaper.test.ts` drives the decisions and the sweeps against a fake Herdr and git.

## The sb server

The sb server is the Straw Boss backend as a process of its own, so that the towers, the link holder, and the page do not depend on which pi session happens to run them ([spec](specs/2026-10-26-sb-backend.md)). This release carries the process, its record, its control socket, its log, its start and restart rules, its connection to the intercom broker, and the GUI server (the page, its API, the dialog hub, remote access, the stash and close routes). The link holder runs in the primary server (see [the link holder](#straw-link-towers-across-computers-the-link-holder)), and the GUI asks it in-process; the towers run in the server as the tower service ([below](#the-tower-service-b4)), which is on by default; only an explicit `"towerRuns": { "enabled": false }` in `config.json` keeps them resident pi sessions as described above.

**What it is.** One server per slot: a (state directory, Herdr socket) pair. The slot of the default Herdr is the primary and keeps its files in `<pi agent dir>/straw-boss/`; a pi on another Herdr socket uses a secondary slot under `servers/<first 16 hex of sha256 of the socket>/`, whose server holds no link; the first 8 hex of that hash (`slot8`) names its tower identities (`sb-tower-<slot8>-w1`) when `towerRuns.enabled` puts the towers in the server. The server is `dist/server/cli.mjs` and `main.mjs`, built from `src/server/` by `npm run build:server` (esbuild, run by `prepack`). The build fails on a value import of `@earendil-works/pi-tui`, `typebox`, or `@earendil-works/pi-coding-agent`, which are peer dependencies that are not on disk where the server runs; type imports are erased. The one runtime dependency, `tsx`, is resolved from this package and used only through its scoped `tsImport()` to load pi-intercom's TypeScript client (pi-intercom 0.18.1 or newer, checked at start: this release requires it, and an older pi-intercom stops the server from starting), so the server's own code is never transformed. The server connects to the broker as `sb-server-<8 hex>` through the headless kit and leaves 60 s after its Herdr stops answering.

**Files** in the slot's folder, all mode 600 in a 700 folder: `server.json` (the record: pid and start time, version, mode `detached` or `serve`, whether the desk switch is on, the control socket or Windows named pipe and its hello secret, the PI_INTERCOM scope and transport the server was started with, `stopped`, `restarting {began, since, reason, by}`, `lastRestart`, `lastError`), `server.lock` (holder pid and start time; a dead holder loses it at the next look, and a lock older than 120 s is taken even from a live holder), `start-error.json` (why the last start failed: `loader`, `intercom`, or `acl`; cleared when a start attempt begins and after `hello`), `server.log` (5 MB, 3 files; events and errors only, never message text or secrets), and `server.sock` (a socket path over about 100 bytes does not fit `sun_path`, so then the socket is `/tmp/sb-<uid>/<hash>.sock`, in a private folder of the user's own; a server never unlinks a socket that still accepts a connection). The control socket answers only a connection that opens with the secret (compared in constant time); any other is closed with no answer. On Windows the state folder's ACL is set to the owner and SYSTEM, protected, and checked by SID in one PowerShell call before the server starts (a failure is `acl` in `start-error.json`); the call prints ASCII-only JSON, so an account name in any code page reads back, and it also tells the server's own start time, so the server makes no other PowerShell start. The folder is protected first, without `/T` (which would leave the files already in it, the lock and the log, with an empty ACL), and everything below it is then reset to inherit from it by one `icacls <dir>\* /reset /T /C /Q`, so the cost does not grow with the number of files; the read-back includes every slot's `server.json`. The server does not wait for its own start time to answer `hello` (elsewhere it fills it into the record when it arrives), and the lock does not wait for its holder's. Whoever starts a server writes `restarting` (reason `starting`) into the record before it spawns and touches it until the server answers, so `status` says `restarting` during a slow cold start and never `gone`; a start waits 60 s for `hello` on Windows (20 s elsewhere). `server.log` has one `phase` line each for the loader, the ACL call, and listening, and `start-requested`, `start-answered`, and `stop-done` lines with their times. A connection that sends a few KB without a complete hello line is closed. `server.log` is rotated by one writer at a time (`server.log.lock`), as the server, sessions, and the CLI all write it.

**The server outlives its starter.** On macOS and Linux the detached server leads a session of its own, so killing the starter's process group does not end it. On Windows `detached: true` does not leave the starter's job object, and a pane or an ssh session may hold its children in a kill-on-close job, so the server is created through WMI (`Win32_Process.Create`, in one PowerShell start) with `CREATE_BREAKAWAY_FROM_JOB`, hidden and with no console, and with the starter's whole environment as `Win32_ProcessStartup.EnvironmentVariables` (nothing is written to disk). The same PowerShell start makes the server's ACL check (the start time of the new pid, the reset and read-back of the state folder) and leaves it in a file only the server's `--acl-token` names; the server checks every SDDL itself before it writes its secret, so the launch and the check are one PowerShell start, not two (`serve` and the plain-spawn fallback still make their own); with the owner read before the first file is created, a cold start on Windows makes two (one if this process has already read this folder's owner, as a pi session restarting a server has). That start is the log phase `breakaway`, with `createMs` and `aclMs`. When WMI cannot start it, a plain spawn does, and that is said: `up` warns `breakaway_failed`, and `status`, `boss_server status`, and `/boss server` show that the server ends with the pane or ssh session that started it. A PowerShell that does not answer in time, or whose answer is missing after WMI may have made the server, is a failed start, with no second one; once WMI made the process, a failure of the check's marker only makes the waiting server end with `acl` at once. A PowerShell that dies before it reaches the create (a language mode that refuses a method, an AMSI or EDR block) is told apart by a line the script prints before the create, and falls back to the plain spawn, visibly. PowerShell failure texts are read from the error records of its CLIXML stderr, never shown as XML; the calls are started with `-OutputFormat Text` and the progress stream off. Known: a `Win32_Process.Create` that throws after WMI made the process still falls back (an RPC drop), and the second server then ends on the lock. The state folder is read (`whoami`, `icacls /save`, no PowerShell) at every start before the first file in it, the lock, the placeholder record, or the log, is created, and protected and read back when its permissions are wrong (a new one is made under a temporary name and protected before it takes its name); a folder that is a link is refused. A folder that is not there is made under an unpredictable name beside it, protected and read back there, and renamed into place, so the server's own creation of `straw-boss\` never stands under its name with the parent's broad permissions (other modules, such as the sidecar, board, stash, link and handover code, still create that folder with a plain `mkdirSync` when they get there first; that code is older than this and is known). The temporary folder stands for 35 to 130 ms with the parent's inherited permissions under a name nobody looks for; the final name never does. The rename is tried again for about two seconds when a scanner holds the folder, and a temporary folder a crash left is removed after a minute. The launch script also reads the starter's own start time, and nothing else asks for it; a cold start's other PowerShell is the owner read. A server that runs but refused this process for lack of permission (an elevated server seen from a filtered token of the same user) is shown as live and unreachable and is never started over or marked stopped; `stop` says to stop it from an elevated shell. `stop`, `status` and a second `up` start no PowerShell beyond that one owner read: a server that answers hello is proof enough. Constrained Language Mode is told as that. The control connection proves that the server knows the secret (a keyed answer to a fresh nonce), and a refusal for lack of permission counts only for the process the record names. The scripts walk what is below the state folder ONCE, without following links, reading each entry's link type and owner as they go (the read-back reuses the list, and reads each SDDL through .NET rather than one `Get-Acl` per file: 3,000 files in `link\inbox` had made the check take 7 to 9 s), and refuse a junction or symbolic link (cloud placeholders such as OneDrive's are walked as ordinary files); every folder below, and the files the read-back names (the five top-level files, every file under `link\`, each secondary slot's `server.json`), must be the user's. A refusal lists the first five problems and how many more. No native call changes an owner (a successful `/setowner` would take over a folder another account made and granted the user the right to take; the temporary folder of a new start could be swapped for such a folder): an existing folder is read with `icacls /save` and left alone when its permissions are already the owner's and SYSTEM's, and a wrong one is changed only after one PowerShell has read its owner as a SID and found the user, `BUILTIN\Administrators` or SYSTEM (and the folder is checked to be the same one right before the call; a swap in that one process start is a documented residual). The owner is gated again in PowerShell before any secret exists, and the folder's own owner and every entry's owner are read before anything below it is changed; the same three owners are accepted everywhere. Before the first file is created in a state folder (an existing one, or a newly made one right after it is made), one PowerShell reads its owner (remembered by the folder's file identity, so a pi session reads it once): another account's folder is refused with nothing created or written in it, the reason going to stderr and the JSON of `up`, not into the folder. A look at a folder that holds a record (a session's look, `status`, `up`, `stop`, `restart`) passes the same owner gate before it asks whether the pid lives, sends a hello to the record's pipe, or tells anything the record says: another account's folder is refused with the same `acl` error, and nothing is sent or written. The read is the memo's, so a pi session spends one PowerShell on it at its first look (a refusal and a failed read are remembered too, so a look every 2 s starts none), and a shell command, being a new process, spends one; a folder with no record is not read. A cold `up` and a `stop` of a server that is down spend one as before. The read never holds a pi session's event loop: it is an asynchronous child process (a PowerShell start is 2 to 5 s on the VM), the requests that come while it runs (a look, a link request, the GUI) wait for the one read and get its verdict, and a folder replaced while it was read is read again instead of remembered. Where there is no ACL (macOS and Linux) the same gate is a stat of the state folder, the slot's folder and the record, before the record is read: one that another uid owns is refused with the same `acl` error and the same words ("belongs to another account", exit 3 in a shell), and no process is started. The walk and the reset calls are not atomic: an entry planted between them is a known, bounded residual. A start refused because the folder belongs to another account writes nothing: the reason is in the error and the JSON of `up` (a folder that is not ours gets no `start-error.json`). A record is no longer trusted without the owner read (R13-F003, closed before the server carries session content). `icacls /T /L` descends a junction, so the refusal of junctions in the walk is what protects their targets; a junction planted between the walk and the calls is a known, bounded residual. An account that can write the parent of the state folder can always win the swap of the temporary folder and make the first `up` fail (nothing is taken over). A server that cannot protect the folder writes `start-error.json`, so `up` exits 3 with `acl`. A `server.lock` that cannot be opened is repaired with `icacls /reset` once. The stopped record of a server that is gone does not pin the pi-intercom scope for the next start. The folder's exact owner (`O:`) is checked in PowerShell: before the server is created (a folder another account owns ends `up` with `acl`, exit 3) and again before any secret is written; the folders below are made the user's and checked too. A failing `icacls` is told by a fixed message for its step and exit code with what to do (for a folder an elevated run made: run pi once elevated, or delete it), and the program's own text only as printable ASCII detail. The system's programs (`powershell`, `whoami`, `icacls`, `cmd`, `clip`) are called from `%SystemRoot%\System32` by absolute path, and every other program the package starts (`herdr`, `git`, `tailscale`, `ps`, `sh`, the opener and clipboard commands) is found by a PATH search that skips empty, `.`, and relative entries and never looks in the current folder, then spawned by the path found, so a `git.exe` planted in a repository is never run.

**The owner gate costs PowerShell starts on Windows.** Before a request trusts a record, or writes into an existing state folder, one PowerShell reads the owner of the state folder, the slot's folder and the record (a foreign owner is refused with exit 3 and nothing is sent or written; a read that runs out of time is a wait, exit 1, and is read again). A pi session reads it once per folder identity (its first look; later looks cost none); a shell command is a new process and reads it itself. Each read is followed by one `icacls /save` that checks the folder is closed (the owner's and SYSTEM's DACL only): a folder that is open is protected right there (`icacls /inheritance:r /grant:r`, then another `/save`), and then remembered. If that protect fails it is told once (a process warning for `cli.mjs`; in a pi session the look tells it once, since pi silences process warnings), and the folder is read again at most every 60 s (at once when a record in it changed identity), not at every look. Counted per command, in PowerShell starts and (in brackets) `icacls /save` calls (a count pinned by fake runners; the Windows time is not measured): a session's first look at a folder with a record 1 [1], later looks 0; `status` 1 [1] (and a `whoami`); `stop` of a live server 1 [1] (and a `whoami`); a second `up` 1 [1]; `restart` of a live server 2; a cold `up` 2 [2: the gate's, then `secure`'s DACL read; a new folder is protected and read back before the gate, so its gate adds one more]; an open folder adds one protect call and one more `/save` to its first read. Before the gate `status`, `stop` and a second `up` cost none, so a shell that polls `status` on Windows pays one start (2 to 5 s) per poll; this is accepted. Where there is no ACL the gate is a stat of the owner (a link's own owner first, then its target's; root counts as the user's), and costs no process. A folder that a `sudo` run made and the user cannot use is told as that (`sudo chown -R` it, or remove it with sudo).

**Starting.** A pi session with a screen in Herdr looks at session start and every 2 s: when no live server runs for its slot, it starts one detached (`detached: true`, `stdio: "ignore"`, `windowsHide: true`) from its own package, under `server.lock`, and holds the lock until the server's `hello`. The environment it builds drops the session's identity (`PI_INTERCOM_SESSION_ID`, `PI_INTERCOM_STABLE_ID`, `PI_SUBAGENT_*`, `STRAW_BOSS_ROLE`) and keeps `PI_INTERCOM_SCOPE_ID`, `PI_INTERCOM_TRANSPORT`, and `PI_INTERCOM_TCP`, which the record keeps; a session on another scope or transport uses no server and says so once. A failed start is told once with its reason and tried again after a minute. A subagent and a session without a screen start nothing.

**Versions.** A session never starts a server from an older package than the one that runs; it says so once. A session on a newer package asks the live server to upgrade, which restarts it from the newer package (`restart reason=upgrade` in the log). Going back to an older package happens only through `/boss server restart --downgrade` (or `cli.mjs restart --downgrade`), after a confirm that says it is older.

**Restarting.** Every restart keeps the server's port when it is free and the GUI's token (see [Browser view](#browser-view)). The requester takes `server.lock` and asks the server to restart with a reason; the old server writes `restarting {began, since, reason, by}` into `server.json` and exits (code 75 for a `serve` server), and the requester then touches `since` every 2 s until the new server's `hello` (the starting server touches it too), writing only while the record is still the old server's, so it never overwrites a newer server's record. A `restarting` record not touched for 10 s counts as gone. The requester holds the lock until the new server answers, except for a `serve` server: its supervisor starts the next `serve`, which needs the lock, so the requester lets go of it for that wait and takes it again only to start a detached server itself when no supervisor did; if a `serve` holds the lock past the start budget (20 s, 60 s on Windows) while it starts, the requester reports the restart as done once that server answers, not `busy`. A server that is down starts whatever the once-a-minute limit says; a `serve` server that is down while another requester's `restarting` is fresh is waited for the same way instead of being replaced by a detached one. A restart is refused when the requester's broker scope or transport is not the record's (`serve` taking over a detached server likewise), and `serve` never replaces a server of a newer package (started from an older package, a `serve` therefore exits 1 each time its supervisor launches it again, under `KeepAlive` or `Restart=always`, until the package is upgraded or the newer server is gone). `stop` is refused from another scope or transport the same way. Only a restart someone asked for (an agent, `/boss server restart`, `cli.mjs restart`) counts for the once-a-minute limit that agents are held to; an upgrade or a `serve` takeover does not, and the limit is checked under the lock, so two asks at once get one restart. A session judges an upgrade by the version of the package on disk beside the `cli.mjs` it would start, not by the code it loaded, and treats an upgrade whose new server is not newer than the old one as a failure (told once) instead of asking again at every look; it asks again only when the server's version or the package's changes, never as time passes, so a stale `dist/` cannot restart the server once a minute.

**`cli.mjs`** (`node dist/server/cli.mjs …`, or `npm run server -- …` in a checkout, which runs `src/server/cli.ts` through tsx; a session in a checkout without `dist/` starts the server as `node src/server/cli.ts`, which needs Node 22.18 or newer):

| Command | Effect |
|---|---|
| `up [--dir FOLDER --label NAME] [--timeout SECONDS] [--exact]` | Make sure a server runs; print one JSON line (`url` (the GUI's, from the server's own answer once it answers 200), `pid`, `started`, `version`, `package`, `mode`, `desk`, `server` = `found`, `started`, `restarted`, or `upgraded`, `log`, `steps` (herdr, version, server, gui; with `--dir` also integration, base, tower), `warnings`). `up` is the boss's own start, so it starts a GUI that was stopped on purpose; remote access that cannot resume is the `remote_off` warning. `--timeout` bounds the whole call, the lock wait and the start wait together, and every Herdr call of the desk steps (90 s by default on Windows, 30 s elsewhere); when a wait runs out the JSON on stderr names it beside `step` as `wait`: `lock`, `start`, `hello`, or `exit`. A running newer server is `server_newer` in `warnings`, or exit 1 at step `version` with `--exact`. `--dir` and `--label` add the desk steps and need `STRAW_BOSS_DESK=1` ([Desk mode](#desk-mode-up---dir)): `integration`, then `base` and `tower` before `gui`, and `workspace`, `pane`, `tower`, `created`, `integration` in the output. |
| `serve` | Run the server in the foreground, for a supervisor (systemd, launchd). It takes over a detached server on the same port (under the same token); another live `serve` makes it exit 4. |
| `stop` | Stop the server on purpose (`stopped` in `server.json`); pi sessions do not start it again (their looks leave a stopped server alone), and only a boss command (`up`, `serve`, `/boss server`) clears it. Refused for a `serve` server, exit 5: stop its supervisor. |
| `status` | Print one JSON line: `state` (`live`, `restarting`, `stopped`, `gui-stopped`, or `gone`, [States for a shell](#states-for-a-shell)), the record's facts (never the secret), the GUI's `url`, the live server's uptime and remote access (`remote`), and the last start error when it is gone. Works with the server down. |
| `restart [--reason TEXT] [--by TEXT] [--downgrade]` | Restart on the same port, under the same token (a `--downgrade` to a package from before D27 draws a new token and unpairs every device). The reason is 1 to 200 characters on one line; `--by` names the asker in the log (the GUI's Restart button uses it). |
| `logs [--lines N] [--follow]` | Print the log's tail (200 lines by default). |

Exit codes: 0 done; 1 a step failed (one JSON line on stderr); 2 usage; 3 the server cannot run (`start-error.json` says why); 4 `serve` found a live `serve`; 5 `stop` found a `serve` server.

**In a session.** After `cli.mjs stop` the sessions do not restart the server: it was stopped on purpose, and only `up`, `serve`, or `/boss server` start it again. `/boss server` shows the state and starts the server when it is down, also when it was stopped on purpose. `/boss server stop` stops it on purpose after a confirm that says every workspace then loses its live tower and mains are demoted 15 s later. `/boss server restart [--downgrade] [reason]` restarts it after a confirm. The `/boss server restart` command also clears a stop on purpose (it is the boss's own start). The `boss_server` tool, registered in a joined session with a screen, gives an agent `status` (works with the server down), `logs` (`lines`, at most 200), and `restart` with a reason of 1 to 200 characters on one line, which goes into the log with the asking session. A restart through the tool is refused while the boss stopped the server on purpose, is taken once a minute for the whole machine, and starts a server that is down. A remote turn cannot call `boss_server` at any level, dispatch included. That block is on the tool only: a peer at `dispatch` level still has `bash`, so it can run `cli.mjs stop` or `restart`, or kill the server's pid. Until the server checks run tokens (the tower steps), the block is not a boundary at that level.

### States for a shell

A program that shows the GUI (the straw-boss-desk shell) tells the stack's state from `server.json` (and `gui.json`), or reads it from `cli.mjs status`. `restarting.since` is touched every 2 s by the server that is starting, so a restart counts as under way only while that touch keeps coming, however long the start takes; there is no fixed overall limit.

| State | How to tell from the files | `cli.mjs status` | What the shell does |
|---|---|---|---|
| live | `server.json` has no `stopped` and no `restarting`; its `pid` is alive and started at `started`; a GET of the URL answers 200 | `{"state":"live", …}` | Show the page. |
| moved | live, but `gui.port` or `gui.token` differs from the URL the shell loaded (a taken port, a lost store, or `/boss gui rotate` changes the token; a plain restart does not) | `live`, with the new `url` | Load the new URL once it answers 200; the old one answers 403. |
| restarting | `server.json` has `restarting` whose `since` is within the last 10 s | `restarting`, with `reason` | Keep the page until the restart ends; it reconnects to the same URL (the token is kept), and a new URL appears as moved only when the token changed (D27). |
| gui stopped | live, and `gui.stopped` (`gui.json`'s `stopped`) is set | `gui-stopped` | Say the GUI was stopped; `up` starts it again. |
| server stopped | `server.json` has `stopped` | `stopped` | Run `up` at the next launch (it clears `stopped`). |
| gone | none of the above: the PID is dead or started at another time, or `restarting.since` is older than 10 s, or the URL has not answered for 10 s while nothing touched `since` | `gone`, with `lastError` and the `start-error.json` reason when there is one | Run `up`. |

On the happy path the shell reads no file at all: `cli.mjs up` prints everything it needs (`url`, `pid`, `server`, `steps`, `warnings`), and `cli.mjs status` prints the state above as one JSON line. Files are for watching between launches, and `cli.mjs logs` for debugging.

**Migration**, in three releases that the shell pins one at a time: S1 (the server ships) writes `gui.json` under the unchanged contract and `server.json` as its documented successor, with `up`, `status`, and `logs`, and nothing has to change in the shell; S2 (one minor later) makes `server.json` the documented contract, which the shell uses through `up`'s output and `status`, keeping `gui.json` as a fallback; S3 (after the shell confirms S2 in its pin) drops the fallback, and `gui.json` stays on disk for older shells, marked deprecated here, and is never removed without a note in the release. No schema version is added: the shell keeps pinning the pi-straw-boss version.

### Desk mode: `up --dir`

A shell that shows the page itself (straw-boss-desk) starts `herdr server` with `STRAW_BOSS_DESK=1` and runs one command, which makes the shell's home base and finds its tower ([desk spec](specs/2026-10-26-desk-mode.md), S3 to S6, as [the sb server spec](specs/2026-10-26-sb-backend.md), *Desk mode: what changes*, has them):

```sh
node <pi-straw-boss>/dist/server/cli.mjs up --dir <folder> --label <name> [--timeout <seconds>] [--exact]
```

The GUI no longer waits for a tower pi: the sb server serves the page from its own start, so `up` returns as soon as the server, the base, and the tower's standing pane are there. **What the shell can count on:**

- **The switch** is `STRAW_BOSS_DESK=1` in the environment that started `herdr server`, so every pane inherits it, and in the environment of `up`. `up --dir` refuses with exit 2 when `up`'s own environment lacks it, which catches a shell that forgot it; `--dir` and `--label` go together (exit 2 otherwise). A server that runs without the switch is restarted with it (`server: "restarted"`); one that runs with it, found by an `up` without it, is left alone with the `desk_on` warning. Nothing changes for a machine that does not set it.
- **The state directory** is `$PI_CODING_AGENT_DIR/straw-boss/` and no other variable moves it (a second variable that one pane missed would split one machine into two GUIs). Files a shell may read there: `gui.json` and `server.json` ([the contract](#browser-view), [States for a shell](#states-for-a-shell)), and `desk.json`, `{workspace, dir, label}`, the home base (written by rename, mode 600). `desk.lock` and everything else is for pi-straw-boss.
- **The steps**, each named in a failure (one JSON line `{step, reason, steps, warnings, log}` on stderr, exit 1; the exit codes of `up` otherwise stand):
  1. `herdr`: Herdr's socket answers.
  2. `integration`: `herdr integration status` is read, and `herdr integration install pi` is run unless its `pi:` line says `current` (an outdated one is installed again, so a Herdr update brings it along); the line must say `current` afterwards. Herdr's install fails (exit 1, "extension directory not found") when `<agent dir>/extensions/` does not exist (a fresh agent directory), so `up` makes the folder first: the folder of the file Herdr's own `pi:` status line names, wherever the environment points. Without the integration Herdr never names a pane's pi session and the pane stays out of the net, which every session also warns about 20 s after its start. The output says `current` or `installed` (the `integration_installed` warning). Normal mode never installs anything.
  3. `version`, `server`: as without `--dir` (start, find, restart for the switch, or upgrade).
  4. `base`: under `desk.lock` (a second `up --dir` while one holds it fails here with "busy"; a lock of a dead process, or of one that started at another time than the lock says, or older than ten minutes is taken over, one run at a time, as `server.lock` is; on Windows a process's start time arrives from a background read that takes seconds, later than a short `up` lasts, so there a lock whose pid a live process now holds is not told apart from its holder and stays until the ten minutes are up, rather than every busy `up --dir` waiting for the read), `--dir` must be an existing folder (make it first, and put it in a visible folder under home such as `~/Straw Boss`: a hidden folder is not pickable, so the page's folder steps in that base would start at home). While Herdr lists the workspace `desk.json` names, it is the base, whatever `--dir` and `--label` say this time (a Herdr restore keeps workspace ids), as long as it still matches the record: its label is the recorded one (the label `up` made it with) and is not just the folder name of one of its panes (Herdr gives an unlabelled workspace that name and follows a `cd`, so such a label proves nothing), or a pane of it starts in the recorded folder (compared as real paths; case-folded on Windows, which is not verified on a real machine). A base renamed by hand whose panes have all left the folder no longer matches: a new base is made, with `desk_base_replaced`. A tower tab proves nothing, since every workspace's tower tab carries the same label; so a base whose tower was quit and whose other tabs work elsewhere is still the base and gets a new tower, and a workspace of the person's with a tower of its own is not taken for it. Herdr numbers a new workspace from the highest id it restored, so a quit base's id can return as a workspace of the person's; that one is left alone, a new base is made, and the `desk_base_replaced` warning says so. A kept base opens its tower in the recorded folder; `--dir` is checked only when a base is made. Otherwise `up` creates a workspace in `--dir` with `--label`, labels its first tab as a tower tab and marks its root pane `sb_role=tower`, so the base has no stray shell tab, and records it. Its shell gets no Straw Boss environment. A base that cannot be marked is closed again. A `desk.json` that is no record is told in the `desk_json_unreadable` warning and the base is made again.
  5. `tower`: `ensure-tower` on the base's workspace ([The tower service](#the-tower-service-b4)): the server takes that pane as the standing pane, registers the tower's identity, and writes the `tower` token; no pi starts and nothing waits for a restored one (a pi a restore resumes in the standing pane is quit). When `up` made the base in this run it tells `ensure-tower` the root pane and the time; the server believes that only when the pane is the workspace's only pane, marked as a tower, holds no agent, and was made within 30 seconds, and then the pane counts as a fresh shell, so on Windows (where Herdr cannot tell an idle shell from a busy one) the `tower>` prompt is typed into it once; any other pane is never typed into there. The same claim also drops a tower service still registered for that workspace id (Herdr killed with its session unsaved numbers the new base like the lost one), so the new tower gets its tokens at once instead of at the next 4-minute refresh. A tower the person closed has dropped its record, so the next `up` opens a new one in the same base; a base the person quit is made again. It needs the tower service (`towerRuns.enabled`, on by default): with it off the step fails with the server's own words.
  6. `gui`: the URL answers 200 ([`gui.json` as the contract](#browser-view)).
- **The output** is the JSON of `up` plus `workspace` (the base), `pane` (the tower's standing pane), `tower` (its intercom id), `created` (whether this run made the base or the tower), and `integration`. A second run prints the same base and `created: false` and opens no tab; after `herdr server stop` and a new server, `up` finds the base by its workspace id and the restored tower, and opens nothing.
- **What the page hides** in a desk stack: GUI remote access (the HUD's Phone) and stash (each base's Stash, the HUD's Stashed), as presentation only (the routes stay); `/boss gui` prints the URL and opens no browser; the folder pickers offer the shell's native dialog when its preload exposes `strawBossDesk.pickFolder` ([in the page and the session](#browser-view)).
- **Stopping** is the shell's: `cli.mjs stop`, then `herdr server stop`. Its next launch runs `up` again. The server `up` starts is detached and recorded in `server.json` (`pid`, `started`), which is what the shell stops with `cli.mjs stop`.
- **Straw Link** keeps one state directory, so `link/` sits beside `gui.json`; the link holder is the primary server. The home tower works in the shell's folder, so it holds no team's messages (delivery goes to a tower whose folder is inside a team's project); they wait in the inbox until a base in the project is open.

### The tower service (B4)

One switch, `towerRuns` in `~/.pi/agent/straw-boss/config.json`: `{ "towerRuns": { "enabled": false } }` (`max`, the most pi runs at once, default 4, is for the runs of B5). **It is on by default** (since B6, the release that carries ally runs): a missing `config.json`, or a `towerRuns` without `enabled: false`, means on. A `config.json` that cannot be read or parsed also means on, but the server says so once: an `error` line with `code=config` in the log and the status's `lastError`, since the file's own `enabled: false` is not obeyed meanwhile. With `enabled: false`, towers stay resident and nothing in this section happens; the flag is removed in the release after B6. The server reads it at start and at every `ensure-tower`, so changing it needs no restart. Turning it off takes effect for the server within one refresh (4 minutes): it releases its tower identities, clears its `tower` tokens, and purges every `service.json`, queue, and ledger; until then a session that finds the live identity's token still reaches it, and what it sends is queued and never read. A server that starts with the switch off purges the leftovers too. The service stands in for the tower; what wakes a pi for the events it gets is [the local runs](#local-runs-b5) below ([spec](specs/2026-10-26-sb-backend.md), **The tower service**).

**A workspace gets one.** `openTower` (a promotion, a member that dispatches, the two-member rule, `/boss tower`, `call_tower` from a main, a sidecar's `call-tower`) asks the server `ensure-tower {workspace}` over the control socket instead of starting a pi; a live tower token is the tower and is not asked about. The server reuses a marked tower tab or a bare one (the radio tower glyph, one shell pane, no agent), else makes the tab with no Straw Boss environment, moves it first, marks its pane `sb_role=tower` (the **standing pane**, left at its shell prompt), registers the **tower identity** with pi-intercom (id `sb-tower-<workspace id in lowercase>`, or `sb-tower-<slot8>-<id>` on a secondary slot; name `tower · <label>`; cwd `<slot>/tower/<workspace id>`, a folder no pi runs in; `herdrPaneId` = the standing pane), and writes the workspace token `tower` and `tower/<workspace id>/service.json`. A sub workspace is answered with its parent's tower. `/boss tower` is the boss's own command, so it also starts a server that was stopped on purpose; an automatic open against a stopped server fails with "the sb server was stopped on purpose; /boss server starts it again".

**What the server keeps up.** The `tower` token and the pane's `sb_role` and sort key every 4 minutes (their TTL is 10). The head watch: on one events connection, a change of the head workspace is noted as a digest line in every tower workspace. The opener (`boss_open_main`) and the `close-main` ask run in the server for the identity: the identity registers the `straw-boss/control` channel, so a main's check that the sender is the workspace's `tower` token holder holds, and the opener's ledger (sender, a hash of sender and request, outcome, tab, main) is kept in `tower/<workspace id>/opened.json` for 24 hours, so a request already tried is not tried again after a restart. Control commands: `ensure-tower`, `close-tower`, `open-main`, `close-main`.

**Resident towers, restarts, and the queue.** A resident tower of an older build keeps its workspace: the service waits while it lives, and a read that fails (the server's own broker connection is not up yet) counts as "may live". A live service checks before each publish and yields to a foreign holder of the token. A hand-over whose first ask failed asks once more. A `roles/` record becomes a service only when its pane is in the recorded tab and that tab carries the tower glyph, or the pane runs the record's own session file. Every events reconnection after the first (Herdr restarted) opens the one-minute recovery window, whichever of it and the watch's takeover comes first. The queue keeps at most 1000 events per workspace (the oldest go first) and none older than 24 hours.

**When a tower ends.** Closing the tower's tab (or the pane, or the workspace) in Herdr, or `close-tower`, ends the service: the identity leaves, the tokens go with `sb_tower_quit=<members it left>` as a quitting tower writes it, and `service.json` is deleted; the queue stays 24 hours for a tower reopened in that time. A pane or tab list that Herdr fails to answer is unknown, not a tab that is gone: the service stays and nothing is demoted. A server that stops or restarts only releases its identities: tokens and files stay, and the guard counts a tower identity of its own slot as live while that slot's `server.json` has a fresh `restarting` that began less than 30 s ago.

**A Herdr restart.** A new Herdr server has no tokens. The server finds each tower tab again by the recorded pane and tab, else (for a minute after the takeover or the server's start) by a tab labelled with the glyph that has one pane in the workspace, writes the marks again, and registers the identity again when the pane changed. A tab not back within that minute ends its service.

**Resident towers.** A live resident tower (an older pi holding the `tower` token) keeps its workspace: the service waits and registers only once that session leaves (and ends if it closed its tab). A resident tower of this build, started by an older session or brought back by a Herdr restore, asks `ensure-tower` for its own pane at its start, quits once the server has written the token, and leaves the pane as the standing pane; a server that cannot take it leaves it resident, with a notice. The same ask is made at every `session_start` of a tower, whatever its reason, so a live resident tower of this build that the boss reloads (`/reload`), resumes, forks, or replaces with `/new` is retired by that: it asks, the server takes the pane, and the tower quits. Nothing in the build opens a resident tower with the service on: `openTower` (a promotion, `call_tower`, a broadcast to towers, `/boss tower`) asks the server, which makes the tab and starts no pi until an event wakes a run. **A resident tower of an older build that is never reloaded keeps its workspace until it leaves** (the service waits for it, as above); to retire one, close its tab in Herdr (or quit it with `/quit`): the service registers the identity once its token is gone, and the next promotion or event gets the server's tower. `roles/` records with role `tower` whose pane is in this Herdr become `service.json` and are deleted (main records are left).

**What is queued.** A message to the identity is written to `tower/<workspace id>/queue/<seq>-<id>.json`, flushed to disk, with the text as received; the log holds no text. The receipt `queued` goes to the sender only after the fsync, and a message already taken (same sender, base message id with a retry's `~r<n>` cut off, and text hash; `seen.jsonl`, 48 hours, 5,000 per workspace) is not queued again but still gets its receipt. A send to a tower identity that fails is retried for up to 30 seconds by Straw Boss's own sender (`src/reach.ts`), under `<request id>~r<n>`. B4's queue, written before `seen.jsonl` existed, is read as it is: retry suffixes are cut, events older than a day are dropped, at most 1,000 are kept per workspace. A link message for a tower the server runs waits in `link/inbox/` and is offered to no session; the boss sees one notice (`a Straw Link message waits … ally runs come with the next step`) until B6.

### The standing pane

Between runs the tower's pane (the **standing pane**) is not a bare shell. The server types the tower prompt into its idle shell, and while the prompt runs there it reports a stand-in agent `tower` on the pane ([spec](specs/2026-10-26-sb-backend.md), **The standing pane**). The tower thus keeps its row in Herdr's Agents list and in the [net view](#sidebar-net-view), at the head of its workspace, between runs.

**The prompt.** `node "<cli.mjs>" prompt --workspace <id> --state-dir "<dir>"` (`src/towerprompt/`), a first word every shell takes, so Windows needs no bash and the node on the `PATH` is the one the boss runs pi from. It shows `tower · <label>: standing by` (or `3 queued`, `waking up`, `running`, `closing`, `held`; redrawn above what the boss is typing when the state changes), two hint lines, and `tower> `. The words are English, and Traditional Chinese when the shell's `LC_ALL`, `LC_MESSAGES`, or `LANG` says `zh_TW`, `zh_HK`, `zh_MO`, or `zh-Hant`. It polls the server every 2 seconds over the control socket with the secret of the state folder's record, as the CLI does (the record is read once the folder's owner is judged), starts nothing, and holds no run token; a server that is down or loading is waited for and said once.
- **Enter** posts the line as a `boss` event (`present`) through the endpoint of the GUI's composer and `/boss tower`, prints `waking the tower…`, and the prompt stays, asking every quarter second (instead of every 2) for as long as the server shows a wake pending, however long the start takes (a Windows claim took 10 to 46 s), until the server starts the run's pi in the pane and tells it to leave (a tower that stands by with nothing queued 3 seconds after the post has no wake pending, and the asking is slow again): the [boss conversation](#the-boss-conversation). What the boss types in that second is held on the prompt's line and posted as a second event at the leave; a prompt that exited at once let those keys land in the shell's line, where the run's start typed over them and timed out. `/new` alone makes the next one a new session and the prompt stays; `/quit` alone leaves the pane to the shell, as Ctrl+D does (no conversation is live at the prompt, so Leave would have nothing to end). Any other first line that starts with `/` (a `/reload` typed from habit) is not posted: the prompt answers with one line that lists what it takes, and a message that begins with `/` is written with a space before it (a line that begins with `//` is posted as typed). Inside a paste the lines are one message, whatever they begin with. Lines that arrive within 40 ms are one paste, one message; a paste between the terminal's bracketed-paste markers stays open until they end, however far apart its pieces arrive, and a paste whose last line has no line end yet (Windows PowerShell sends the text, then the Enter a moment later) waits for that Enter and is posted whole with it, never as two messages. The last line is held as part of a paste only when it arrived in the same group of input reads as the paste's lines. A group is the reads of a bracketed paste, from its start marker to its end marker, plus any read that follows the one before within 40 ms and carries more than one key, and a single key that follows a read that left a line unfinished (a pty may split a big paste into reads, and may leave only its last character for one). A key is one character (one code point, `é` or `中` as well as `x`; the bytes of a split character are put together first, so a half character is never a key) or one complete escape sequence (an arrow, Alt+b). A typed `/quit` and a key typed a moment after it, even a few ms later, are two groups, and `/quit` is obeyed; one read that holds both `/quit⏎` and more than one further key cannot be told from a paste and is held. A paste whose last line is a single character in a read of its own, after a line end, is two messages. A bracketed paste whose end marker never comes is closed 2 seconds after its last data. The prompt does not turn bracketed paste on itself (the shell sets that mode at each of its prompts, a prompt killed before it could turn it off would leave the boss's shell in a mode it did not ask for, and a Windows console may not know it): the markers are honoured when the terminal sends them. An empty Enter wakes the tower with a line that says the boss is at the keyboard and wrote nothing: it is how the boss talks to the tower now (see [The boss in a run](#local-runs-b5)). A line the server refuses is shown (`the tower did not take it: …`) and the prompt stays.
- **Ctrl+D or Ctrl+C** leaves the pane to the boss's shell, whatever the prompt holds (a paste not yet posted or a post on its way; what was held is dropped, never posted later), and a closed input ends the prompt the same way, so the prompt is never left running with dead input: the server is told, the stand-in goes, and nothing is typed there again, however long the boss stays, until a tower run takes the pane and ends or Herdr restarts (no clock gives the pane back: a prompt typed into a shell the boss is using would join their half-written line or take their next command for a message). The boss gets the prompt back by waking the tower (`/boss tower <message>` from any pi session, or any event); when that run ends the prompt returns. The boss may start `pi` there by hand: a run of their own. A tower prompt the boss starts by hand there ends the park as soon as it polls; Retry does not end it.
- A run that is starting makes the prompt's next poll say so; it prints `waking the tower…` (once: not again when the boss wrote a moment ago), posts what the boss had typed on the line (and the lines in the 40 ms paste window) as their `boss` event first, so nothing they were writing is lost (if the server does not take it, the words are printed under the refusal), and exits 0. Keys the boss types after the prompt has exited, before the run's pi has started, still land in the shell (the prompt cannot hold a terminal it has given to pi); the window is the start of pi, not the second between Enter and the run.
- When the server has no tower for the workspace (the tower closed), the prompt says so and exits.

**What the server does.** A look at every standing pane each 3 seconds. It types the command only into a pane whose foreground is its shell at an idle prompt (Herdr's `pane process-info`), that has no agent, was not parked by Ctrl+D, and did not get the command in the last 15 seconds (and not for 15 seconds after the prompt posted the boss's words and exited: a run starts in a second), and no run is about to take the pane (an event waits and its wake is due within 5 seconds: a prompt typed then would have to start, poll, and leave before the run's pi can, 29 s in a PowerShell pane on the VM): a build or an editor the boss left there is theirs. "Idle prompt" is proven by the shell's pid and the foreground process group Herdr gives on macOS and Linux (the group is the shell's own). Windows lists the shell alone whether a build runs under it or not (and its `foreground_process_group_id` is always the shell's pid, so the server does not believe it there: a `ping -t` in the pane still looked idle), so a pane without a believed group is typed into only when the server knows it is fresh: the tab it made, a pane a run freed, the pane a resident tower handed over (the hand-over carries the pi's PID: the pane counts as a bare shell once that process is gone, within a minute of the hand-over and for a minute after, so the prompt is typed after a `/reload` too and never while the pi still runs behind a `cmd.exe /c` wrapper that Herdr lists as a shell), or any pane after a Herdr restart, and then only if every foreground process is a shell; an empty list is unknown, never idle. A prompt that dies on Windows is therefore not typed again until the next run or Herdr restart; the server logs `prompt-lost` once (a prompt typed there that never started is logged `prompt-not-starting` once instead, and not typed again). A prompt that never starts (no `node` on the shell's `PATH`, a shell that cannot take the quoting) is typed again after 15 seconds, then 30, 60, and so on up to every 10 minutes, and the server logs `prompt-not-starting` once, after the third try; a poll ends the backoff. A typing that Herdr refuses (`pane run` fails) is no try: the server logs `error code=prompt-typed` with Herdr's exit code and whole stderr, tries again 15 seconds later while the pane is still believed fresh, and after three refusals in a row logs `prompt-not-typed` once and types nothing more, on any platform, until the next run, a resident tower's hand-over, or a Herdr restart. Only an exit code Herdr itself gave is a refusal: a `pane run` that the 5-second timeout cut off may have typed the command already, so it counts as typed (one `error code=prompt-typed` line with the signal) and is not typed again. A service held because the pane runs a program of the boss's is started again by itself once that program is gone: where Herdr gives the foreground group, when the group is the shell's; on Windows, when the program's PID is gone and the list shows the shell alone at two looks in a row (the program is found in the process table below the pane's shell, since the foreground list shows the shell alone there). A hold with any other cause waits for the boss's Retry or a word to the tower. **Retry** with no event waiting and no run gives the pane back as a run's end would, so the prompt is typed again; it changes nothing while the prompt polls (a prompt that runs is never typed into, whether or not Herdr kept its label), and it never ends the boss's Ctrl+D park (the pane stays theirs). On Windows, where the foreground list cannot tell an idle shell from a running program, Retry reads the process table first and types only when that read succeeds and finds no program of the boss's below the pane's shell (the tower prompt aside): a read that fails says so and types nothing, a program found holds the service on it again and names it, and Retry asks again. The give-back marks the pane fresh for a minute at most, and not at all while the pane is parked. A notice of a start that failed goes when Retry is pressed, when the boss writes to a held tower, and when a later run claims. It reports the stand-in while the prompt has polled in the last 6 seconds, again when the message changes and every 4 minutes. Before a run starts pi in the pane it releases the stand-in (Herdr refuses `agent start` in a pane with an agent: `agent_pane_busy`), tells the prompt to leave, waits up to 3 seconds for it to be gone, and sends Ctrl+C only when the pane's foreground is that very prompt (by PID); a run ends, and the next look types the prompt again, as it does after a Herdr restart (every pane is a fresh shell) or a crashed prompt.

**Why a process, and why the label is `tower`.** Herdr (0.9.5) drops a reported agent whose label it does not know within a second of finding the pane's foreground at an idle shell; while a process other than a shell holds the foreground, the label stays (52 minutes with no refresh were watched), and it goes 0.3 seconds after that process ends. A known agent kind would stay on a bare shell, but it would put another agent's name on the row. So the prompt is a process that holds the foreground, and the label is the tower's own. If Herdr does not keep the stand-in (three reports in a row that the next look does not find), the server logs `standin-unsupported` once and stops reporting for that prompt: the tower has no row between runs, as before, and nothing else changes. The report has no resume command and no session, so a Herdr restore never relaunches it, and a report after pi's exit works at once (Herdr does not bring it back by itself).

### When a main calls the tower

The boss decided (D18, D19) that coordination goes through the tower, and that a main calls it at three points only. The main's prompt (`prompts/main.md`) names them, and `call_tower` takes the reason as `why`:

| `why` | When | Reply |
|---|---|---|
| `milestone` | A task landed, a deliverable is ready, or what a tower asked is done. | `reply: false` unless the main needs an answer. |
| `shared` | Before the main touches anything outside its tab: a port, a database, a shared branch, a deploy target, another app's checkout, a running service. It says what and for how long, then waits for the answer. | Expected. |
| `blocked` | The main waits on someone outside its tab, or on a decision its authorizations do not cover. A member reports coordination friction the same way. | Expected. |

Routine progress is on the work board and wakes nothing. The code writes the reason into the header (`why=<kind>` after `reply=`). In pi's tool `why` is required for a main; the sidecar's `call-tower` takes `--why` as optional, and without it the header says `why=unspecified` and the event wakes as `blocked` does. A word outside the set is refused before anything is sent.  A tower's `call_tower` takes `why` as optional (it is a `blocked` call); the resident tower prompt (`prompts/tower.md`, `towerRuns` off) is left without `why=` guidance on purpose, to stay in its word budget. Non-blocking incidents go on the work board and wake nothing.

**The hold.** An intercom event whose header says `why=milestone` and `reply=none`, with no local run live, waits up to 30 seconds (`hold`) for others, counted from the first such event, so mains that finish together land in one run. Every other event (`shared`, `blocked`, unspecified, a reply expected, the boss, a notice, a timer) wakes at 1 second as before and takes any held milestones with it. A live run gets each event at its next idle moment, with no hold. The server reads the header at the very start of the event text only, so a message that spells out `why=milestone` further in, or in a quoted name, is not held.

The tower's run prompt (`prompts/tower-run.md`) says what to do with each reason: a `milestone` updates its obligations, tells whoever waits on it, and closes a main it opened; a `shared` call (a main writing to or changing something outside its tab, not reading) is checked against the board and its obligations and answered go or wait with the owner named; a main that gets no answer in 10 minutes tells the boss and leaves it alone; a `blocked` call is routed to its owner, except a decision only the boss can make, which the tower names in its handoff note as waiting on the boss and tells the main so, not sending it back. A main opened by a tower reports its done report with `call_tower` (`why: milestone`, no reply). It never asks a main for progress, since `board_read` has it.

### Local runs (B5)

With the tower service on (the default), an event for a tower identity wakes a pi in the tower's standing pane ([spec](specs/2026-10-26-sb-backend.md), **The wake protocol**, **Tower tools in a run**). One local run per workspace at a time and at most `towerRuns.max` (default 4) across the machine; a burst of events starts one run (the wake waits 1 second; a finished milestone waits up to 30 seconds, see [When a main calls the tower](#when-a-main-calls-the-tower)). `boss` events (the GUI's composer, `/boss tower <prompt>`) go first.

**Start.** The server runs the settings check (`assertSettingsSafe`) on the pane's folder before every run and starts nothing when it refuses: the events stay queued, the tower card shows an error notice, and the next try comes with the next event, at most once a minute. It starts `pi --name "tower run · <label> · <run8>" --sb-run <run id>` in the pane with no Straw Boss environment, and records the run's PID and start time.

**Claim.** A pi with `--sb-run` asks the server `claim {run id, pane, pid, start time}` over the control socket before it joins anything. The server answers a run token (kept in memory), the run's kind, and the brief, only when the run id is one it started and has not ended, the pane, PID, and start time are the recorded ones (the server finds pi's own process itself, in its process table: when Herdr lists only the wrapper pi was started through, such as `cmd.exe /c pi.cmd` on Windows, the recorded PID is the first process below the wrapper that carries the run id and is not itself a wrapper, and a stop or a timeout ends pi and then the wrapper, each checked in the process table at that moment; a run whose start failed ends only a process in its pane whose command line carries the run id), every Herdr takeover it saw is processed, and the run was not claimed already; a refused pi quits with the reason. A pi without the flag in a standing pane asks `pane-role` (a resident tower, which carries `STRAW_BOSS_ROLE=tower` and has its `tower` entry in the session, never does, and neither does a process that already became a resident, which the process remembers: the server answered `none`, or no server was there to answer. Its `/reload`, `/new`, `/resume` or `/fork` is its own switch, and the new branch has no entry yet. A pi that is undecided or plain is no resident, whatever its switch; the env alone is not enough, since it stays in a migrated standing pane's tab and a pi the boss types there is a hand run: a `/reload` that finds its pane already marked by the server would otherwise make it a hand run that never hands over; it hands over itself): it is told to quit for 2 minutes after a Herdr restart (Herdr's pi integration resuming the old run) or becomes a run of its own (`hand`; one whose pi is gone before its first poll, a claim nothing released because the pi quit while a late answer was on its way, ends as `quit`, not as a crash, so it does not count toward the crash loop). For a pi with only the env the ask is bounded (2.5 s) but an answer after the bound is not a guess to act on: the session stays undecided (it joins nothing, hands nothing over, quits nothing), the ask stays in flight, and the answer is acted on when it comes (`hand` makes the hand run with that claim, `none` or an older server makes it the resident that hands over, `quit` quits), a session that ended meanwhile releases the late claim, and an ask that fails or never answers leaves a plain session with one notice. An undecided or plain pi that is `/reload`ed, `/new`ed, `/resume`d or `/fork`ed keeps its one ask (a second ask of a pane whose hand claim was given is told the pane is held) and the plain one stays plain; a `/quit` of a pi that never became a normal session leaves the standing pane open, and waits up to 2 s for an ask in flight so that the hand claim it carries is released; the process start time is read once, before the bound's clock (on Windows the read takes seconds). A hand run keeps its claim across `/reload`, `/new`, `/resume` and `/fork` (same process, same pane: asking again would be told the pane is taken, and the run ended crashed after 30 s). The boss's words in a run protect its turn from the abort whether or not the server heard them. A claim goes through the session's look at the server, so the record is passed through the owner gate before a secret is sent anywhere. A run whose server stays out of reach aborts its turn before it ends, unless the boss is in it (a hand run, or their words in the run): there it waits for idle. A `quit` the server orders while the run's turn is busy is held by the run until the turn ends: pi keeps a deferred quit with no way to take it back, so a server that restarted meanwhile (the run then claims again with its run id) would otherwise end a run it never stopped, as crashed. A claim again drops the held quit.

**The run.** It joins no net, publishes no tokens, runs no guard. Its role section is `prompts/tower-run.md` and the brief the server built (who and why, mains it supervises, open obligations, the memory, the digest, the last handoff note, the tools, flags; 8,000 characters at most). It polls the server once a second, and at each idle moment takes one waiting event as a `straw-tower` message with `triggerTurn`, then confirms it `taken`. Its tools are the tower's own (`boss_status`, `call_tower`, `tower_list`, `board_read`, `tower_send`, `boss_open_main`, `boss_close_main`, `boss_server`) plus `tower_reply`, `tower_memory` ([Tower memory](#tower-memory)), and `tower_done`, each a request to the server over the socket under the run token: the server does the work as the tower identity, so everything leaves under `id=sb-tower-<ws>` and replies come back to the server. pi-intercom's `intercom` tool is blocked with a pointer to `tower_reply`. A run ends with `tower_done {note, wakeAfter?}` (the note, 1 to 1,200 characters, goes to the next local run; `wakeAfter`, 5 to 240 minutes, asks for a follow-up run, one pending per workspace); it is refused while events are still for the run. An intercom event reaches the model under a sender line the code writes (`[intercom from <name> (<id>)]`), so text that claims to be the boss's instruction is told apart from a real boss event. The name and id keep only letters, digits, spaces and `._@-` (80 characters each), so the line stays one line and the real id is always the last group in ASCII parentheses; known limits: a name may hold letters that look like brackets (e.g. `ᐸ…ᐳ`), and scripts written with combining marks (e.g. Devanagari) lose their marks. A run dispatches no subagents (`subagent` and `subagent_resume` are blocked), takes no `/boss` command, and looks at nothing of the server (it starts or upgrades none). A server restart does not end a run: its next poll finds the token unknown and claims again with its run id; while the new server has not loaded the runs or registered the identity it answers the claim `wait`, and a run that gets no answer or only refusals waits up to 30 seconds before it ends. `/boss server stop` (not a restart) tells every live run to quit, ends the PID that stays, and records the run `quit`. A pi in a standing pane that Herdr resumed without the flag (even when its pane lost its tokens, if its tab has the tower label) asks the server for its role and waits up to 30 seconds for a live server, so the server's two-minute quit rule reaches it.

**Kinds of token.** The server holds every request that carries a run token to the run's kind. A local run may read `status`, use the link holder for `list`, `board-read`, `send`, `confirms`, and the approved-request ops (always as its own tower identity), and `open-main` and `close-main` for its own workspace. An ally run's token gets none of them. `gui`, `gui-remote`, `gui-pair`, `close-tower`, `restart`, and the rest of the control socket are refused to any run token: the hello secret is the credential of a session or a shell, a run token only of a run.

**The boss in a run.** Once the boss speaks in a run, it does not end on its own. They speak by writing at the [tower prompt](#the-standing-pane) (the run it wakes is theirs from its claim), by typing in the run's pi (its extension tells the server at the first word and at most every 15 seconds after: input from the keyboard only, never an event or a steer of the server's), or by starting pi by hand in the standing pane. While the boss is in the run, `tower_done` answers that they are here, keeps no note, and the run goes on, so the model keeps answering them. The run ends when the boss quits it (`/quit` ends it as done with the note `(the boss left the run)`, `(boss quit)` in a [boss conversation](#the-boss-conversation); the events it had not taken wait for the next run; a quit of a run the boss is not in is a crash as ever) or after 10 minutes of their silence (no input, no turn), when the run gets the wrap-up below. **The bound:** the cap and the idle limits below do not apply while the boss is in the run, in the middle of a turn too, for 4 hours from their first word at the longest (counted from the first word of the run, not restarted by a return after their silence); after that the cap applies at once, and a later sign of the boss changes nothing. After the boss's silence the run has the idle wrap-up to itself (6 minutes), and the cap does not cut it short. A server restart forgets who was in a run until their next word.

**Limits.** A run that has not polled for 30 seconds is lost and ended as crashed, unless the computer slept: when the server's own watch finds a gap of more than that between the end of one of its ticks and the start of the next (a slow tick is no sleep), no run could poll in it, so every run's silence is counted from that tick. A run that settles idle without `tower_done` gets one steer after 60 seconds and `quit` 5 minutes later; at 18 minutes it is asked to wrap up, at 20 minutes it is quit (a pi that has not exited 10 seconds after `quit` gets Escape and `/quit` through Herdr, and 5 seconds later SIGTERM to the PID `herdr pane process-info` reports). **On Windows** a pi ended with `TerminateProcess` leaves its pane's console in a mode where the next `herdr agent start` there types a mangled command and times out, so the waits are 30 seconds and 20 seconds, a stopping server waits 8 seconds for its runs to leave and never signals a pi that stays (the run is left without an outcome, as a restart leaves it: that pi reclaims it from the next server, or ends itself at its next idle moment once the server has been away for `lostMs`: a pi in the middle of a turn aborts the turn first, since pi keeps a shutdown until its next idle moment and a model call can last minutes, and the next server records the run `quit`, not `crashed`, when that pi is gone), a pane in which a pi was signalled is replaced by a fresh standing pane before the next run, and only the standing pane is closed, and only when it holds a shell or the run's own pi (a pane running the boss's program, and the other panes of its tab, stay; the tab then loses the tower label; the service keeps its queue and notices), and a start that Herdr reports with the error code `timeout` is tried once more in a fresh pane without counting toward the crash loop (any other failure ends the run). A crash returns its events to the queue, flagged `possibly handled by a run that crashed: check before acting`; an event taken by two runs that both crashed or timed out is parked (the card shows **Deliver again** and **Drop**); three crashed or timed-out runs in 10 minutes hold the service (the card shows **Retry**). A start that fails while a program of the boss's (not a shell, not the tower prompt) runs in the standing pane is the pane's doing: nothing of theirs is closed (and a start that is not Herdr's `timeout` code gets no new pane), the run counts toward the loop like any crash, the one start notice names the program (its executable's file name, no path or arguments; on Windows, where Herdr's foreground list shows the shell alone, the program is looked for below the pane's shell in the process table when Herdr answers `agent_pane_busy`), and the held service starts again by itself once the pane's foreground is back at its shell, as it does on **Retry** or a word from the boss.

**`boss_server` and the restart limit.** In a local run `boss_server` goes through the server: it refuses `restart`, `status`, and `logs` for an ally token, and the one-restart-a-minute limit is kept by the server itself, so two agents asking at once cannot both pass it.

**The GUI.** The tower unit stays on the map as the identity: `working` while a run works, `waiting` on a dialog, **standing by** (待命) when no run is live. The service's own state has its own word on the map, in the dossier, and in the comms header (**waking**, **closing**, **held**, **ally run · device**), followed by how the last run ended (crashed, timed out, quit) and how many runs failed lately; the map card carries a count chip of the messages waiting. Waiting events show as the unit's queued rows (kind, sender, first line), labelled as waiting for the next run, with no Edit (the server's queue is not pi's). The notices, with their **Retry**, **Deliver again**, and **Drop** buttons, show on the map card and again in the tower's comms; a button is off and says "Working…" until the server answers, and a refusal shows under the row. A run's events are `custom_message` entries of type `straw-tower`, and the comms read each by the `kind` the server sent it with (`details.kind`: `boss`, `intercom`, `notice`, `timer`, `link`; a steer is a server notice): the boss's own message is a YOU bubble with the server's marker line taken off (a crash flag after it shows as a note inside the bubble), an intercom message, a server notice, and a wake-up call are incoming notes with their labels and no marker line, and a teammate's message (an ally run's input, a main's `link_reply`, an answer from a local session) is labelled by what it is (request from, reply to your ask from, answer from, message from the device) with its text inside and the verified header folded behind "details". Only `details.kind` makes a message the boss's, never its text, and only in a run of a tower the sb server runs: in any other session (a main, an ally run's comms) a `straw-tower` entry of kind `boss` shows as a labelled notice with its text as written, never as YOU. An intercom message shows the sender's name and id from the server's own sender line (cleaned to letters, digits, spaces and `._-@`, at most 80 characters) and says it is from this computer; a teammate's message through Straw Link says teammate, so two senders with one name never read alike. A tower that stands by with nothing said yet explains what standing by is and that the first message starts a run. **Ally runs** show beside the tower's state: the state reads `ally run · <device label>` (or a count) instead of "standing by" while one works, and a chip per run (`ally run · <device label>`, with a count first when there are several) sits on the map card, in the workspace view, and under the comms header. A chip opens the run's comms read only while the run's session file is known: the net makes each such run a unit of its own (key `ally-<run id>`, no pane, so input, keys, and focus answer 409 `not_live`), keeps the path off the page, and drops the key from the allow list ten minutes after the run left the net, as for any session; the header says "read only" instead of an open channel, the box and the attach button are off, and the composer says a teammate's message drives the run. The run reports its pi session id with its file, and the server keeps the file only when it is named for that session (`<time>_<session id>.jsonl`); the run reports both, so this stops a slip and not a run that lies, which is the shared residual of reading files by path. The workspace view carries the same queue chip and notices (Retry, Deliver again, Drop) as the card. A message that waits for an ally run (`served`) says an ally run has not taken it and points to the tower's card; a forwarded confirm names the teammate's tower it comes from. The dialog of a `link_request` stays in the language the extension wrote it in (English): its title is one string of the server's wording, the agent's reason, and the names of the asker and the device, and a page that took the fixed words out of it would break silently with the next rewording, so the page shows it as written beside its own localized chrome. The composer says "Wakes the tower" and **Send** posts a `boss` event (nothing is typed into a shell); its keys, mirror, and focus answer 409 `standing` while no run is live, and the Terminal tab says so in a sentence instead of showing a key pad. The unit's comms are the boss session once there is one (the live conversation's file while it works), else the live run's session, else the last run's; event runs are chips beside it, read only (see [The boss conversation](#the-boss-conversation)).

**`/boss tower <prompt>`.** Ensures the tower as a bare `/boss tower` does, posts the prompt as a `boss` event with `present` (it starts or continues the [boss conversation](#the-boss-conversation), as the GUI's composer does), and answers "Handed to the tower" with no change of focus. `/boss tower status`, `parked`, `retry`, `deliver <id>`, `drop <id>`, `leave`, and `new` are the commands of that section. A bare `/boss tower` still opens and focuses the tab.

**`link_request` and asking for a main.** A local run has `link_request`: the server opens the request, the boss's approval dialog (the same one a main gets: action, every argument, the reason, the asking session) is shown by this run's pi, and the action is carried out by the holder only on a yes; the server is given the approval's call id and takes it only against an explicit yes (the run's dialog closed with `allow`), so a run cannot approve itself. `tower_send` takes `device`, `reply: true`, and `for`, a live main of the workspace that asked: the server records the ask (`tower/<workspace id>/awaiting.json`, 24 hours) and the device's answer goes to that main directly (see [Ally runs](#ally-runs-b6)). A mailbox flush from pi-intercom's broker is marked delivered without a receipt; the proposed fix is written up in [the pi-intercom proposal](specs/2026-10-27-pi-intercom-mailbox-flush.md).

### The boss conversation

A **boss conversation** is the local run a `boss` event with `present` (the tower prompt's Enter, the GUI's composer, `/boss tower <prompt>`) starts when no local run is live ([spec](specs/2026-10-26-sb-backend.md), **The boss conversation**; D23). It **resumes the boss's last session**; every other local run, an **event run**, starts a fresh session and ends with `tower_done`, as before. One conversation per workspace, whatever the boss wrote it from: the GUI's composer is the same server function as the prompt (`runs.boss(…, {present: true})`), so a message from either continues the one conversation.

**Which session.** `tower/<workspace id>/boss-session.json` (`{file, run, startedAt, lastAt, turns, fresh?}`, mode 600) names it. Only a conversation moves it, by its own `run-file` report and only for a `.jsonl` under pi's `sessions` folder (real path, so a link out of it is not followed). pi writes a new session's file only at its first assistant message, after the run reported it, so a `.jsonl` under that folder that is not on disk yet is held back (no error) and kept, with the same checks, at the run's next poll, the boss's next word, or the run's end; a file that never appears leaves no pointer, and a path that could never qualify is refused and logged when it is reported. The wait, the turns taken meanwhile, and a New asked meanwhile (`/new` of the tower prompt, the GUI, or pi's own) are kept in the run record, so a server restart does not lose them, and the file is kept marked fresh. An event run never moves it, and neither does the boss typing into an event run's pi. A boss message that arrives while an event run is live goes to that run (it does not wait for the boss), and the tower's comms then show that run until it ends; the run record keeps when the boss first spoke in it (`bossIn`), and the next conversation's brief names the run and its handoff note. The server starts the conversation with `pi --name "tower · boss · <label>" --sb-run <id> --session <file>` when every one of these holds, else with no `--session` and the brief says why: the file is a regular file under `sessions` with no symlink anywhere in its path below that folder and the boss's own (POSIX uid), it is at most 4 MB, the boss's last turn in it was at most 7 days ago, no live pane's `agent_session` names it, and the boss did not ask for a new one. `turns` counts the boss events the conversation took and the boss's typing in its pi (at most every 15 seconds). The claim, the run token, and the run mode are the event run's; **an ally run never resumes it**. A run token cannot start, leave, or restart a conversation, or write as the boss: `tower-event`, `tower-leave`, `tower-new`, and the other boss commands are refused to every run token (`rungate.ts`), so a resumed session's agent traffic gains no standing; the run's prompt says only an event that opens with the boss line is the boss's, however old.

**During.** The boss is in the run from its claim, so everything under [The boss in a run](#local-runs-b5) holds: events that arrive are delivered to it at its idle moments, `tower_done` is answered with a stay, and the 20-minute cap and the 60-second idle steer do not apply. The brief's first section says `Boss conversation: the boss is at this pane. Resumed session from <date>, <n> boss turns` or `New session: <why>`, and, for a resumed one, `Since you last talked with the boss:` with the first line of up to 3 event-run notes written since (1,200 characters together, 1,400 for the section). A live run is given a **newer brief** (a `brief` in the poll's answer) when the memory or the last local note moved; its next turn reads it. The boss's silence for 10 minutes while the run is idle, or the 4-hour cap, gives the wrap-up: a steer ("The boss has left: call tower_done with your handoff note."), then `quit` 5 minutes later with the note `(ended idle)` or `(ended at the 4 h cap)`, recorded `quit` (a conversation is never a timeout, so the cap never counts toward the crash loop). `tower_done`, and the boss's `/quit` in the conversation's pi (note `(boss quit)`, recorded `done`, also after a long silence), end it at once. A server restart keeps a conversation on its feet, counted from its start.

**Leave and New.** `/boss tower leave` (the GUI's **Leave conversation**, a `/quit` typed in the tower's composer, `tower-leave` on the socket) tells the pi to quit and ends it as `/quit` does; `/boss tower new` (the GUI's **New conversation**, `/new` in the composer or at the tower prompt, `tower-new`) marks the pointer so the next conversation is a new session, and ends a live one the same way. `/new` typed in the conversation's own pi has the same effect. Leave is refused when no conversation is live (an event run is not one) or it has not claimed yet. The words are exactly `/quit` and `/new`: with more words they are a message.

**`/boss tower`.** `status` (the service state, the conversation with its deadlines, notices, parked events, recent runs), `parked`, `retry`, `deliver <id>`, `drop <id>`, `leave`, `new`; anything else is a message for the tower. Each is one control command the GUI's buttons reach too (`tower-retry`, `tower-deliver`, `tower-drop`, `tower-leave`, `tower-new`, and `status`), with the server's refusals; the writes are refused in a pi with no screen, as `/boss memory`'s are. The words come in English and Traditional Chinese. A prompt that is exactly one of these words is a command.

**The GUI.** The tower's comms are the boss session (stable across runs; the live conversation's file while it works): a divider opens each conversation run (`Boss conversation · resumed · 10:04` or `· new session ·`, with how the run ended and its note once it has), and the event runs are chips under the header (`event run · 10:12`, a read-only unit of the net while their session file is known, the outcome and note in the tooltip). The state word says `boss conversation · ends after 10 min idle`, `… · waiting for you · …` while the run waits for the boss (the tower then shows idle, not working), or `… · closing`; the box above the composer says how it began (resumed with the turns, or new and why), what it does now, the idle deadline, and the hard cap, with **Leave conversation** and **New conversation**. The composer's `/quit` and `/new` ask for no confirmation in a tower. The marker line of a boss event (`BOSS_MARK`) is unchanged, byte for byte: a resumed session holds the old lines, and the page reads them by that text; the writer (GUI, prompt, pi) is not told to the model, so there is no `via`.

### Tower memory

Event runs start fresh, so what has to outlive a run is kept apart in `tower/<workspace id>/memory.json` ([spec](specs/2026-10-26-sb-backend.md), **Tower memory**): the boss's **standing instructions** (up to 12) and **decisions** (up to 24), each at most 300 characters, the tower's **waits** (up to 12 open, 200 characters), and the **proposals** runs made that the boss has not answered (up to 12). Every local run's brief carries them in a Memory section (4,900 characters at most, after the open obligations; the standing instructions always fit whole, within a 2,400-character budget; the pending proposals come last, labelled as not confirmed). When the brief as a whole passes 8,000 characters the memory is cut first, so the tools, the `tower_done` line, the crash flags, and the 20-minute line always stay. An ally run's brief never carries memory, and `server.log` holds only the op and the id of a write.

**Who writes.** The boss does, with **`/boss memory`** in any joined pi session of the workspace: `/boss memory` lists (the tower's proposals first, each with the boss message it cites), `/boss memory confirm P3` and `reject P3` answer a proposal, `add standing|decision <text>`, `edit S2 <text>`, `delete D4`, and `resolve W1 [outcome]` change the rest (`-w <workspace>` names another workspace; the words are English or Traditional Chinese by your locale). pi is the first interface: the **Memory** panel of the tower's comms and the tower card in the GUI call the same server function with the same `rev` check and add nothing of their own. A local run, through `tower_memory`, can only **propose** a standing instruction or a decision, or retiring one: the proposal waits, apart from the live entries, for 7 days, and takes effect only when the boss confirms it (a confirm that a full list or a changed entry cannot apply is refused and the proposal stays). The tool has no confirm, the control socket's `tower-memory` command is refused to every run token, and a run takes no `/boss` command, so no run's tool, ally, link envelope, or message can make an instruction. That is the whole guarantee: it holds against those routes, not against a same-user process with a shell. Any agent with a shell (a main as well as a run) can read the secret in `server.json` and send the control socket a `tower-memory` command, write `memory.json` directly, type `pi -p "/boss memory …"`, or send text into a pane. `/boss memory` refuses every write when its pi session has no screen (`pi -p`, RPC), which closes the `pi -p` path only; the rest is the same-user trust the whole server rests on (limit T3R-F005, which covers mains too). A run can read the whole memory and the proposals with `read`. At a full cap the boss's own add is refused with a message; nothing is dropped. An ally run is refused the tool by its token's kind.

**Waits** are the tower's own notes, never instructions. A wait `for: "boss"` shows on the tower card as a notice ("waits for you") with an **Answer** link to the composer; a wait `for: "agent"` names a live session, and a message from it marks the wait *answered* (the run judges whether it answers). An open wait expires after 7 days (shown once in the next brief as expired); a resolved or expired one stays 24 hours, struck through in the panel. The standing pane's "waits for you" line comes with the tower prompt.

The memory file is the boss's text, so it is kept when the tower service is switched off or its tab is closed; delete its entries with `/boss memory delete` or in the panel to clear it.

### Ally runs (B6)

A Straw Link message for a tower the server runs is worked in an **ally run**: a fresh pi in a pane split off to the right of the tower's standing pane (same tab, no new tab, no new workspace), at the sender's trust level, with no local context ([spec](specs/2026-10-26-sb-backend.md), **Ally runs**). This amends the Straw Link rule that an attended device opens no *session* for a remote message: it opens a session, never a tab or a workspace. A message for a project with no workspace that has a tower service still waits in `link/inbox/` for 7 days with one notice; the server opens nothing for it.

**Its pane in the net view.** The ally pane is a row of the Agents list like a subagent's (0.47.0): the server writes `sb_role=ally` and the four display tokens on it at the split, and writes them again with the tower's 4 minute publish (a run lasts up to 20 minutes, the tokens 10). `sb_order` is the tower's key plus one segment (`000.0` → `000.0.000`, the second ally run's `000.0.001`), so the row sits right under the tower; `sb_mark` is `[ally]` and the device's label (cut to 24 characters); `sb_indent` is `├─` while a later ally pane is marked and `└─` on the last; `sb_name` is `ally run`. The server clears them before it closes the pane when the run ends, and the panes of the other ally runs move up. Without them the row fell to the end of the list among the agents the net does not know, and its role token lapsed after 10 minutes.

**One run per device.** The holder leaves the inbox item where it is; the server lists the messages waiting per sender, and starts one run for the device with up to 5 of them, oldest first (a message that comes during the run waits for the next run). One ally run per workspace beside its local run, and it counts toward `towerRuns.max`. A sender that left the roster has its messages dropped and starts nothing; one that leaves during the run gets the run ended with `quit` (the server looks at every watch tick and every tool call) and its tool calls refused meanwhile.

**Level.** The run is claimed at the sender's level, from `link.trust` or the unattended policy; the run's hooks read the policy again and take the lower. The whole session is one remote turn pinned to that sender: the same allowlist, deny list, gate, and `forward` confirm as a tower's remote turn (`src/link/hooks.ts`). A gated call is asked of the boss through the server (the run's pi shows the dialog; at `forward` the confirm goes to the sender's device and its answer comes back at the poll), and the server runs a gated tool call of an ally run only against the gate's recorded yes for that call id over arguments with that digest, once. At `dispatch` the gate is off. The server holds the run to the lower of its claimed level and the device's level now (lowering trust takes effect on a running run; a raise does not lift it). A claim that names no sender, or a session that cannot pin the turn, shuts the run down. `tower_done` is free at every level. The server notes the boss's yes from its start, whether or not the GUI listens, so a terminal answer works with the GUI stopped.

**Tools.** Free at every level: `boss_status`, `tower_list` and `board_read` (both scoped to the sender's team: its project's workspaces and that team's boards), `tower_send` to the sender's device (`device` is required; any other device or target is refused, an Allow or not), `tower_done`, and the run's own `read`, `grep`, `find`, and `ls` inside the project's tracked files, as in a remote turn. Anything else of the tower's own tools (`tower_reply`, `boss_open_main`, `boss_close_main`) the server runs only against the gate's recorded yes (below), except at `dispatch`, where they run without a confirm. `call_tower`, `boss_server`, `link_request`, and a `tower_reply` to a tower identity of this computer are refused whatever the level; `close-tower` and the other control commands are refused to every run token, and so are the link holder ops that need a session's identity (`taken`, `gui`, `request-open`, `request-run`, sending as a tower; B3R-F003). Everything the run sends to a local session carries `origin=remote:<sender device id>`, stamped by the server.

**Questions to local sessions.** What a local session says back to an ally run's `tower_reply` (with `reply: true`) or to a main it opened is stored for the device (`ally-routes.json`, `ally-answers.json`, 24 hours), not queued for the local run, and waits for the device's next ally run; the mains an ally run opens have their own ledger (`ally-opened.json`). The local brief never lists them. A main an ally run opened keeps sending its reports to the device for 24 hours, not just the first answer. The terminal's yes of a gated call reaches the server even when the server serves no GUI: it names its session in `hub.json` for the bridges.

**Brief and thread.** The run's role section is `prompts/ally-run.md` plus a brief the server builds (who and at which level, what the sender may see of the workspace, the last handoff note for this device, the asks the run carries, the last six rows of the device's thread, and its tools; 4,000 characters at most). The **thread store** (`link/threads/<device id>.jsonl`, mode 600) keeps both directions, the last 20 messages per device, none older than 7 days, and is deleted with the device's roster entry. It holds peer text at rest.

**Replies for a main (D4).** `caps` is a team-wide message each holder sends at each stream start, when its build changes, and hourly: the features it takes (`tower.awaitsReply`, `tower-reply`); one older than 2 hours counts as none. `tower_send` with `for` (above) sends a plain 4-field `tower` to a device whose `caps` lack `tower.awaitsReply`, and a `tower` with the ask id as its fifth field to one that has it; the tool's answer says which. A message that carries an ask id shows `asks=<id>` in its header, and the ally run answers it with `tower_send({ device, text, inReplyTo })`; an `inReplyTo` that is not one of its own asks is refused. The answer goes as kind `tower-reply` to a device whose `caps` list it, else as a plain `tower` (also when the relay refuses the kind with `unknown-kind`; logged once per device and hour). The asking computer takes a `tower-reply` as a reply only for an open, unused ask from that device, closes the ask, and offers it over `straw-boss/link` to the main that asked, which holds it until idle and puts it into its session as a `straw-link` message with `triggerTurn` under the verified header plus `kind=link_reply` and `for=<tower>`. That main then runs a remote turn at the replying device's level. A main that has gone, or that has not taken the offer within 5 minutes, gets an ally run instead, whose brief says which main asked; so does any other reply. Against an older build nothing is dropped: the ask comes back as a plain `tower` and gets an ally run.

**`boss_server` and the restart limit.** An ally run's `boss_server` is refused by its kind; for any run the server keeps the limit of one restart a minute itself, so two agents asking at once cannot both pass.

**Crashes and limits** are the local run's (settles idle, 20 minutes, three failures in 10 minutes hold the service), per device.

**The wire.** `caps`, the 5-field `tower`, and `tower-reply` are in `src/link/kinds.ts` and `tests/link/vectors.json` (the Straw Link spec's **Message kinds** table has the rows); straw-relay carries the same two rows and a copy of the vectors, and is redeployed first.

### Stash and pop

`/boss stash` puts a whole base away and `/boss pop` opens it again ([spec](specs/2026-10-22-stash/spec.md)). The stash runs in the sb server's GUI, which `/boss stash` asks to run (no browser opens; a GUI stopped on purpose is not started: the command says so, and `/boss gui` starts it): only the server can ask every session's bridge. It first checks, closing nothing: Herdr's view (every pi pane is a tower, main, or member that is `idle` or `done` and has a session file; no subagent in the base or its sub workspaces; no shell with anything but the shell in its foreground; the base is not itself a sub workspace) and each session's own, through its bridge's `stash-check` (no running turn, no queued message, no open dialog, no running monitor). A session that does not answer within three rounds counts as a refusal, so a session on an older pi-straw-boss is never closed by a stash. Every reason is listed in one refusal. Then it writes `stash/<name>.json` in the state directory (the label and folder, each tab in order with the tower's tab first, each pane's role, session file, name, and folder) and closes the base as **Quit** on a base does. A batch that stops half way (an agent refuses or stays up) deletes the manifest and names each session's `pi --session` file instead, because popping it would run a session file twice. `/boss pop` opens a new workspace with the same label and resumes each pi with `pi --session <file>`: the tower first (its session carries its tower mark), then per tab the main (with the one-time `sb_open_main` token, as a main the page opens) and then the members, each awaited in its role for up to 60 s; shells reopen in their folders. On success the manifest moves to `stash/popped/`; on a failure the new workspace closes and the manifest stays for another try. Monitors, pending intercom asks, and pane sizes are not carried over.

`/boss close all` (`POST close/all {by}`) closes the base of the session that asks, without stashing (and, like a stash, it does not start a server stopped on purpose); other bases, sub workspaces, and workspaces outside the net are never touched. It uses the stash check without what only a pop needs (session files, folders); any refusal closes nothing and lists every reason. Then the base closes as **Quit** on a base does, each session quitting only while it can still be stashed. The base is surveyed again just before it closes, and when the server's own session sits in it, that session (which its batch does not ask) is checked again too. A session that is not in a base on the net closes nothing; an invoker still alive when the server does not answer is told to check what is still open.

## What it writes

- The sb server's files (`server.json`, `server.lock`, `start-error.json`, `server.log`, `server.sock`) in the state directory, or `servers/<hash>/` for another Herdr's slot, and its intercom identity `sb-server-<8 hex>` ([The sb server](#the-sb-server)).
- Herdr pane token `sb_role` (`main`, `member` or `tower`; a tower tab is also marked right after it is created; a tab opened for a request is created with the environment variable `STRAW_BOSS_ROLE=main`, which makes its pi promote itself) and workspace token `tower` (the tower's intercom session id), both refreshed every 4 minutes with a 10 minute TTL, written again at once when a new Herdr server takes over (see [A new Herdr server](#sidebar-net-view)), and cleared at shutdown (a tower that quits then closes its own tab if it holds only that pane).
- Herdr pane tokens `sb_opened_by` (the sender's intercom session id, on a pane a tower opened for a request; refreshed by its main and cleared at shutdown, so the open limits count only live opened mains) and `sb_open_main` (a one-time mark the opener sets, consumed by the first pi that promotes itself from it).
- On a tower's standing pane, Herdr's `pane.report_agent` and `pane.release_agent` (source `straw-boss`, agent `tower`, idle, the state as the message, no resume command or session) while the tower prompt runs there, and that prompt's command typed into the pane's idle shell ([The standing pane](#the-standing-pane)).
- Pane tokens `sb_order` (a sort key), `sb_mark` (a role label) and, on subagents, `sb_indent` (a tree branch) and `sb_name` (the subagent's name) next to `sb_role`, and the subagent ones on the panes of the subagents the session launched, with the same refresh, TTL and takeover rewrite; they feed the sidebar net view and the optional rows below (see [Sidebar net view](#sidebar-net-view)).
- `roles/<hash>.json` in the state directory, one record per tower or main by pi session file: its role, pane, tab, and workspace, so a Herdr restore gives the role back (see [A Herdr restore](#sidebar-net-view)).
- A pi session entry `straw-boss` (`tower`) so a resumed tower keeps its role. Members write no entry for their role: every session joins at start, so entries saved by 0.4.0 (`asked`, `joined`) are ignored. The other entries carry `nudged`, a subagent run that was asked to report, or `closing`, `unclosed`, `resumed` and `gaveUp` (a restored subagent run that was closed, found still open after all, handed to the launcher for resuming, or given up on), and `seen` with `terminal` (the terminal a running child's pane was in) (see [Subagents a Herdr restore brought back plain](#subagents-a-herdr-restore-brought-back-plain)).
- When a team is set up: the files under `<pi agent dir>/straw-boss/link/` and the intercom channel `straw-boss/link` (not owner-eligible), registered by the sb server and by every tower ([the link holder](#straw-link-towers-across-computers-the-link-holder)).
- The control channel `straw-boss/control` (not owner-eligible, so it has no owner): registered by every tower and by a main a tower opened, and used for the `close-main` ask and its answer ([Closing an opened main](#closing-an-opened-main)).
- Every message it sends through intercom (`boss_broadcast`, `call_tower`, `tower_send`, the nudge, the request handed to an opened main) has a message id with a nonce of the current process: pi-intercom refuses an id it saw from a session again with other content, and a restarted pi keeps its session id.
- A net sidecar (see [From Claude Code or Codex](#from-claude-code-or-codex)) writes the same `sb_role`, `sb_order`, `sb_mark`, `sb_main_tab`/`sb_tab` tokens for its pane with the same refresh and takeover rewrite, the digest line `<name> joined tab <label>`, and, in the state directory, `agents/<sha256 of the pane id, 16 hex>.json` (its pid, session, and kind; a `.reap` lock beside it while a leftover is removed), the `.sock` control socket (mode 600, in a 700 directory; on Windows a named pipe of random name instead, recorded in the state file as `pipe`, see [Windows](#windows)), and the `.log`; it holds one `straw-boss/tab/…` channel and never the GUI's. It types net messages into its pane with `herdr agent prompt`, and keeps one `events.subscribe` connection for the pane's events besides the takeover watch.
- One `events.subscribe` connection to Herdr's socket per joined session or tower, which carries no events of interest and is read only for its closing (see [A new Herdr server](#sidebar-net-view)).
- A tower keeps one more `events.subscribe` connection to watch the head workspace (`workspace.created`, `closed`, `moved`, `reordered`), whether or not it has a UI; it reconnects like the one above and closes with the session ([Talking between towers](#talking-between-towers)).
- A tower with a UI keeps one more `events.subscribe` connection for its dashboard (panes, tabs, and workspaces changing, see [Tower dashboard](#tower-dashboard)); it reconnects like the one above, and closes with the dashboard.
- While remote access is on, one `tailscale serve` entry (HTTPS 8443, proxying to the GUI server's remote listener), removed when it goes off or the server stops; `paired.json` (the identity the devices were paired under, whether remote is wanted on, and the paired devices as cookie hashes with name, paired, last-seen, and expiry times) is written at each change and deleted only when there is nothing to keep: no device and remote not wanted (the last unpair after remote off, or remote off with no device), or no remembered identity. Remote off alone keeps the devices; unpairing the last device while remote is wanted keeps the wish; a different Tailscale identity turning remote on drops the devices; a stop, a takeover, a `/reload`, and the end of the session never touch it; an expired device is dropped when it is next used or when the file is read.
- One intercom extension channel per tab, `straw-boss/tab/<hex of the tab id>`, registered by every joined session and tower; the channel's owner (the first to join) only records the main, and it is not the main by that. Tab ids over 24 characters are refused.
- `trust/<uuid>.json`, `<uuid>.answer.json`, and `<uuid>.result.json` in the state directory (a 700 directory, files 600, each written by rename): the project trust question of a pi that has not joined the net yet, the server's answer, and which side answered ([Project trust](#browser-view)). The asking pi removes its request and answer when it is decided or when it ends; the server removes a request whose process is gone, results after 2 minutes, and anything left half-written. `gui.json` carries `trust: 1`: the sb server reads them.
- The dialog channel `straw-boss/gui/<sha256 prefix of the server's session id>`: registered owner-eligible only by the sb server (its intercom id is `gui.json`'s `ownerSession`), and joined by every session (subagents included) while `gui.json` names a server whose process is alive; each session checks `gui.json` once every 2 s from its start. Besides dialogs it carries the session's document list (pi-herdr-doc-review's ids, paths, display names, reasons, revisions; the bridge asks the owner for the list again when it starts, so a session that reloads lists what is open) and form answers addressed to one document and once per answer id, and the key pad's editor check: the server asks a session's bridge what Enter would submit, and the bridge answers with a class (empty, text, another slash or `!` command, or unknown) and at most the name of a command that ends or replaces the session, never the draft, and only to the server `gui.json` names now whose process is alive.

The tower tab is labelled with the radio tower glyph (U+F043B) alone and its Herdr agent is named `tower-<workspace id>` in lowercase (Herdr agent names are unique per server).

## From Claude Code or Codex

A Claude Code or Codex main-agent session joins the net through a **net sidecar**: one small Node process per pane, started by [straw-boss](https://github.com/wayne930242/straw-boss) when the session starts (the design record is `docs/specs/2026-10-23-claude-codex-net/spec.md` in the straw-boss repository). Dispatched straw-boss workers and coworkers never get one, and nor does a session in a sub workspace (the sidecar checks, as a pi does, and leaves). The sidecar needs pi-straw-boss and pi-intercom in pi's `npm/node_modules`; without them straw-boss starts nothing and the session works as before.

The sidecar is not a pi, so it has no tools, no prompts, and no terminal of its own. It registers with the pi-intercom broker as a session (id `claude-<provider session id>` or `codex-<provider session id>`, name `claude-<first 8>`, model `claude-code` or `codex`, the pane as its Herdr pane, no intercom status, so its state in the net is Herdr's own `agent_status` for the pane) and then runs the same modules a pi session does: the tab channel and its election, the guard, the pane tokens, `boss_status`/`boss_broadcast`/`call_tower` underneath, and the digest. A small headless kit (`src/agent/kit.ts`) gives those modules the only two things they ask pi for: the extension channel and the outbox, over a raw pi-intercom client. It never hosts the GUI server and never registers the GUI's dialog channel, so the GUI's takeover cannot pick it.

**Starting.** straw-boss's SessionStart hook runs, and returns at once:

```bash
node --import <tsx loader> <pi-straw-boss>/src/agent/cli.ts join \
  --pane "$HERDR_PANE_ID" --kind claude|codex --session <provider session id> \
  [--record <orchestrator record file>] [--cli <straw-net.py>]
```

`<tsx loader>` is the one pi-intercom starts its own broker with, found beside pi-intercom (`STRAW_BOSS_INTERCOM` names pi-intercom's directory when it is not beside this package or under pi's `npm/node_modules`). `join` starts the sidecar detached and returns once its state file exists, or after 3 s with exit 1 and the log's path. A pane holds one sidecar, and its holder is the process that answers `hello` on the pane's socket with the state file's own pid and session; a pid alone is not one (a crash leaves the file behind and the pid may belong to any process by now), so a file whose process does not answer holds nothing once it is 15 s old, and a signal goes only to a process that answered. The same session joining again does nothing; the same session joining while its sidecar is leaving, or another session in the pane (`/clear`, or a resume), stops the old sidecar if it is not leaving already, waits for it to be gone, and starts a new one (after the wait, SIGTERM for one that answered and stays). The sidecars of one pane claim the state file by linking a complete temporary file into place, and a leftover is removed under a lock only while it is still the very file judged stale. The `PI_INTERCOM_*` and `PI_SUBAGENT_*` variables and `STRAW_BOSS_ROLE` in the agent's environment are ignored: a Claude Code started from a pi's shell is not in that pi's pool or role.

**Roles.** The sidecar joins as a member, like every pi, and can own its tab's channel (so it decides pi claims and runs the guard, and opens the tower, which is always a pi). It becomes the tab's main only by promotion, never by force: when the orchestrator `--record` file straw-boss keeps for the session already exists at the join (a resumed main agent), appears or changes (`register-orchestrator.py`, or the session's first dispatch), or when it runs `promote`. A tab that has a live main refuses it and the session stays a member. `/boss` stays a pi command; a pi can take the tab over from a Claude main. A main demoted because its tower quit is promoted again on the next record change, or by `promote`.

**Commands.** `straw-net.py` runs `cli.ts <command>` for the pane it is in (`--pane`, else `HERDR_PANE_ID`); each command sends one request to the sidecar over the socket and prints the answer.

| Command | Same as | Effect |
|---|---|---|
| `status` | `boss_status` | The tabs' mains, this workspace's tower, the head tower, and the other towers, as JSON. |
| `promote` | `boss_promote` | Ask to be the tab's main; refused while it has a live main. |
| `call-tower --message M [--why milestone\|shared\|blocked] [--reply true\|false] [--workspace W]` | `call_tower` | Send to the tower; a main opens the tower tab when none runs. Without `--why` the header says `why=unspecified`. |
| `broadcast --message M [--scope tab\|workspace\|towers\|all]` | `boss_broadcast` | One message to every other session in the scope; default `workspace`. |
| `send --to ID --message M` | intercom `send` | One message to one session; this is how it replies. |
| `rename --name N` | `boss_rename` | The session's name in the net and a digest line. |
| `board --now N [--item '[x] T']… [--item '[ ] T']…` | `board_set` | The main's work board entry (a done step is `[x]`, an open one `[ ]`); refused for a member. |
| `stop` | | Leave the net now. |

Exit codes: 0 done; 1 refused or failed, or the sidecar was reached and did not answer in time (60 s; `call-tower`, which may open a tower first, 120 s), with the reason on stderr: the request may still be carried out, so check before sending it again; 2 a usage error, or no sidecar for this pane (nothing listens on its socket).

**Receiving.** Each intercom message sent to the sidecar is typed into its pane with `herdr agent prompt`, as one line, newlines and control characters folded to spaces:

```text
[straw net from=<name> id=<session id> role=<tower|main|member|session> reply="<straw-net.py> send --to <session id> --message '…'"] <message>
```

From an idle or done pane it uses Herdr's own gate (`--wait --until working --until blocked`), so a clean exit means a turn started; into a working pane it is a plain submission (the provider queues it). A **blocked** pane (a permission prompt is open) refuses input, so its messages wait in memory, in order, until Herdr reports the pane free; a message still waiting when the sidecar leaves is lost. A message id seen twice is typed once. A message from a pi session already opens with its own header ([Talking between towers](#talking-between-towers)); it follows the sidecar's line. The path and the id in the reply hint are shell-quoted. A message relayed from another machine comes `from=<name>@<machine> · unverified cross-machine` as pi names it, with no reply hint (a sidecar sends only within this machine's intercom), and attachments are named at the end of the line (`[1 attachment: notes.md — not carried into this pane]`), not typed in. A message whose typing stalls or times out is not typed again; only Herdr's own `agent_blocked` makes it wait.

**Leaving.** The sidecar leaves within about 10 s of Herdr reporting the pane closed or exited, or its agent no longer `claude`/`codex` (read again once, 1.5 s later, so a flicker is not a quit; an agent Herdr has not detected yet at the start is waited for up to 30 s), and at once on `stop`, SIGTERM, or a join that fails. It clears the pane's tokens (not when the pane runs another agent by then: a pi that took the pane over owns them, and a new Herdr server's rewrite skips such a pane too), then disconnects from the broker, so no role token outlives the session, and removes its files (the state file only if it is its own). A rename is kept when the connection is made again. A broker that goes away is reconnected to with a backoff of 1, 2, 5, 10, then 30 s.

**In the GUI** the unit is on the map in its tab's squad, as main or member, under its name, with its state from Herdr (a permission prompt shows as waiting, answered in the terminal) and a small badge naming the agent. It has no control: the composer says the page cannot type into it, Quit is disabled, no comms log or terminal mirror opens (both need a pi session file), and stash and close-all of its base refuse, naming the pane. It counts toward its base's mark and appears in the dashboard, the sidebar net view, and the digest.

**Limits.** The broker finds a non-pi session by the pane it launched in, so a pane moved to another tab drops out of the net until its next session start. One more Node process runs per Claude or Codex main-agent pane.

Without a sidecar, read-only discovery still works from any shell in a Herdr pane:

```bash
herdr workspace get "$HERDR_WORKSPACE_ID" | jq -r '.result.workspace.tokens.tower'
herdr pane list --workspace "$HERDR_WORKSPACE_ID" | jq -r '.result.panes[] | select(.tokens.sb_role) | [.pane_id, .tokens.sb_role] | @tsv'
node ~/.pi/agent/npm/node_modules/pi-intercom/cli.mjs ask --to "$TOWER_SESSION_ID" --text "<message>"
```

Opening a missing tower needs a pi session or a main sidecar.

## Windows

Windows support is experimental. Herdr's API there is a named pipe, and the file at the socket path (`%APPDATA%\herdr\herdr.sock` by default) is only a marker holding the server's pid and start time. Every client in this package (the extension, its watches, a net sidecar, the sidebar plugin) connects to `\\.\pipe\` followed by the socket path, as Herdr's own CLI does. The socket path is found as Herdr finds it: `HERDR_SOCKET_PATH`, else the socket of the `HERDR_SESSION` session, else the default one in Herdr's config directory (`XDG_CONFIG_HOME`, else `%APPDATA%`).

A net sidecar's control socket is a named pipe too. Pipe names are one namespace for every account on the machine, and the 700 directory that guards a Unix socket has no part in it, so each sidecar names its pipe at random when it starts (`\\.\pipe\straw-boss-<32 hex>`) and records the name in its state file, in your profile, where the commands read it. Another account cannot learn the name before the pipe exists, and once it exists the pipe's default access lets only its creator, administrators, and SYSTEM write to it or make another instance of it. A pipe ends with its server, so there is no file to remove.

A process's start time has no Node API and Windows has no `ps`, so there it is read through PowerShell's CIM query (`powershell.exe -NoProfile -NonInteractive -Command "$ErrorActionPreference='Stop'; (Get-CimInstance Win32_Process -Filter 'ProcessId=<pid>').CreationDate.ToUniversalTime().ToString('yyyy-MM-ddTHH:mm:ss.fffZ', [cultureinfo]::InvariantCulture)"`, hidden, 15 s limit), which answers without elevation for a service or an elevated process too, where `Get-Process` would not. One call takes 3.5 to 4 s on a Windows 11 ARM VM, more under load, so nothing waits on it: a pi reads its own start time in the background when its session starts, retrying after 1, 2, 4, 8, and 15 s while it fails, and keeps it for its life; another process's is cached by PID for ten minutes, forgotten when that PID is seen dead, and a failed read is asked again after 5 s, then 10, 20, 40, and at most 60 s. Until the first answer the start time is unknown, which counts as "cannot be told" (the record stands). A record written before the own start time is known (`gui.json`, `remote.json`, the link holder's `holder.json`) is written again when it arrives; the "could not record its own start time" warning comes only when the reads give up or that write fails. With start times, a survivor adopts a GUI whose owner died, as on macOS, and the link holder's record and lock are no longer taken for a PID another process reused. Both sides of a comparison read through the same function, so the ISO text only has to be stable. The detached `node` that balances panes is started with `windowsHide`, so no console window appears.

The sidebar plugin declares `windows`. Windows has no bash, so its startup hook and action each have a Windows twin that runs `node` (which Herdr finds on `PATH`) instead of `run.sh`, and since an action id is unique across platforms, the Windows action is `wayne930242.straw-boss.net-windows`. Herdr's plugin support on Windows is itself a preview.

The tower prompt is typed as `node "<cli.mjs>" prompt …`, which cmd and PowerShell take as they take `sh`, and it talks to the server's named pipe through the same client as `status` (the record is read once the owner of the state folder is judged). Its exit keys are Node's: Ctrl+D and Ctrl+C in raw mode. Not run on Windows.

Closing a pane after pi quits (a tower's quit, `/boss close`) waits for pi's exit in a `node` process rather than `sh`, so it works without a POSIX shell.

The worktree reaper stays macOS and Linux only. It closes a pane only when the pane's shell runs nothing in its foreground, and on Windows Herdr's `pane process-info` reports the shell alone unless an agent runs under it, so a pane running a build, a server, or an editor would look idle and be closed. Removing a checkout also needs each process's working directory, which `lsof` and `/proc` give and Node cannot read on Windows without native code.

`tests/platform.test.ts` checks these on every platform, and the `Windows` workflow runs it on a Windows runner against real named pipes, after loading every module a session, a sidecar, and the sidebar plugin load. Herdr itself does not run in CI, so pi starting inside Herdr on Windows is checked by hand.

```bash
npm install

npm run gui:build  # builds the page into dist/gui (npm test and npm pack do this first)
npm run build:server # bundles the sb server into dist/server (npm pack does this; the build fails on a value import of pi's packages)

npm test           # node --test, against a fake Herdr and a fake intercom broker, in a temp home of its own per test process (tests/setup.ts)
npm run test:one -- tests/x.test.ts # one file, isolated the same way
npm run gui:dev    # the page with hot reload against a demo net; see below
```

The dashboard has its own file (`src/dashboard.ts`, budget 162 lines) and its rendering is a pure function of a snapshot, so tests drive it without a terminal. What it shows without drawing (the marks, the rows, and the subagent reading) is in `src/netdata.ts`, which reaches no value import of pi-tui, typebox, or pi-coding-agent so the server can load it; `tests/pure-imports.test.ts` walks the import graph and fails on one. The browser view's data and server (`src/net.ts`, `src/gui.ts`) share a budget of 300 lines; `buildNet` turns sessions, panes, and workspaces into the JSON snapshot as a pure function (and fills the registry of readable session files), and `collectNet` reads Herdr and intercom and reuses the subagent linking of `src/netdata.ts`. The session reader (`src/history.ts`), the entry-to-item mapping (`src/items.ts`), and the stream and API glue (`src/watch.ts`) are tested against fixture files.

The page is vanilla TypeScript in `gui/`, built by Vite (a development dependency only) into `dist/gui`, which ships in the npm package; `dist/` is not committed. The page diffs the DOM by element id, animates with CSS on `transform` and `opacity` (the map's packets are `transform` keyframes along each wire, `gui/packets.ts`; `gui/calm.ts` rests the endless ones), and its reconnect logic (`gui/stream.ts`) is tested with a fake stream and a fake clock.
The map's chunk holds the map, the header, the router, and the alert spotting (`gui/alerts.ts`).
The focus views (`gui/views.ts` coordinates `gui/workspace.ts`, `gui/session.ts`, and `gui/dossier.ts`), the comms log with the markdown renderer (`gui/chat.ts`, `gui/markdown.ts`), and the overlay layer's DOM and tiles (`gui/layer.ts`) load on first use.
The overlay rules (`gui/overlay.ts` for the dialog stack, `createTiles` in `gui/layer.ts`) are pure and tested without a browser (`tests/overlay.test.ts`); phase 2 and 3 dialogs (ask_user, robot_hand, secret_drop) and show_doc documents (`gui/doc.ts`, its rules tested in `tests/doc-page.test.ts`) plug into the same stack and tiles.
Size budgets are checked by `tests/imports.test.ts`: the map's chunk ≤ 15 KB (6 KB gzipped), the lazy chunks together ≤ 35 KB (12 KB), the stylesheet ≤ 22.1 KB (6.1 KB).

The sidebar plugin is plain JavaScript in `herdr-plugin/` and imports nothing from `src/`, so the folder works wherever Herdr links or installs it.
`tests/netview.test.ts` drives it against a fake Herdr that keeps tokens and the one active view, and against a real Unix socket.
The reaper plugin in `herdr-reaper/` is built the same way: its decisions (`decide.mjs`) are pure functions, its runs (`sweep.mjs`) take Herdr, git, the state store and the clock as arguments, and `tests/reaper.test.ts` runs them against fakes.

`npm run gui:dev` serves the page on a local port with hot reload, fed by a demo net with invented names that changes state every few seconds. The demo includes a session with every kind of chat entry (open any unit), and the fixture's toolbar (bottom left) has **drop stream**, **go silent** (no messages, no error: the 45 s watchdog), **restore**, to review the disconnected page, and **doc arrives**, which has billing-main show one more document: on its comms it opens as a tile, elsewhere its badge counts up. billing-main lists a markdown plan and an HTML review whose form posts nowhere in the demo. Its `/boss gui` then starts a second sb server from the checkout, recorded in the scratch directory, and opens no browser.
